# 测试技术库

本目录维护本仓库可复用的测试技术（Test Techniques）。测试技术不是输出模板，而是同时支持测试分析和测试设计。

| 阶段 | 回答问题 | 使用测试技术的方式 | 主要产物 |
|---|---|---|---|
| Test Analysis 测试分析 | what to test | 从需求和设计方案中识别测试条件、覆盖项、风险、接口契约、测试点候选、测试点明细分支和非成功失败类型 | `ME-*` 方法证据、测试点候选、`TP-*-*` 测试点明细、`TP-*-*-*` 失败类型明细、过程缺口候选 |
| Test Design 测试设计 | how to test this point | 将评审后的普通测试点明细或失败类型明细展开为代表性条件、具体数据值、数据槽位、状态、接口返回或组合，并继承叶子节点预期结果 | `TDI-*` 测试设计项 |

`test-analysis-agent` 只输出测试分析方案，不输出 `TDI-*`；`test-design-agent` 复用本目录把普通测试点明细或失败类型明细扩展为测试设计项。

本目录中的测试设计项示例只表达 JSON canonical 中 `designItems[]` 的内容形态。示例统一使用 JSON 片段表达 `id` 与 `content`；不得把示例改回测试设计项表格或 Markdown 列表，也不得引导模型直接维护 Markdown 主交付件。

每个技术文件都应回答四个问题：

1. 该技术适合识别哪类测试条件、测试点或测试点明细。
2. 分析阶段如何从需求、设计方案或测试点中抽取建模元素。
3. 设计阶段如何把建模元素派生为不含预期结果的测试设计项。
4. 如何控制覆盖数量，并判断预期结果是否有依据。

本目录不维护完整测试用例写作规则，不输出前置步骤、测试步骤、自动化脚本或执行数据。完整测试用例写作知识不在本 Agent 内维护。

## 技术分类

| 分类 | 分析层用途 | 设计层用途 |
|---|---|
| 基于规格的测试技术 | 从需求规则、流程、状态、接口、数据范围等规格信息识别测试条件、覆盖项和测试点明细 | 作为大多数测试点明细的主测试设计项展开技术，生成具体数据值或数据槽位 |
| 基于经验的测试技术 | 根据历史缺陷、专家经验、易错点识别补充风险和遗漏分支 | 作为补强技术，不替代规格建模 |
| 基于风险的测试策略 | 根据业务影响和失败后果识别优先级、覆盖深度和风险确认点 | 调整测试设计项数量和高风险补充方向 |
| 基于质量属性的测试技术 | 从性能、可靠性、恢复性等质量属性识别专项测试点和明细 | 生成质量属性相关测试设计项，并提供叶子节点预期结果依据 |

## 分析层与设计层调用

| 调用层 | 使用方式 | 不做什么 |
|---|---|
| `testing-method-router` | 根据需求/设计信号选择专项方法参考，不提前生成测试点明细或 TDI | 不选择设计项数量，不替代生成 |
| 专项方法参考 | 读取相关测试技术，产出 `ME-*` 方法证据和测试点候选 | 不把方法产物直接写入主交付件 |
| `test-analysis-solution-generation` | 消费方法证据，归并为场景、测试点、测试点明细和非成功失败类型明细；按本 README 获取 Oracle 启发 | 不输出代表性具体数据、组合、TDI 或步骤 |
| `test-design-agent` | 读取评审后的测试分析方案和本目录技术示例，在叶子分析节点下生成不含预期结果的 `TDI-*` | 不回写测试分析方案的结构标准 |

## 选择规则

1. 分析阶段先选能解释需求信号的专项测试技术，再产出方法证据和测试点候选。
2. 当前测试分析方案生成阶段只抽象为测试点明细，不展开代表性具体数据或组合。
3. 如果测试点同时命中多个基于规格的技术，按“状态/周期/判定/组合/范围/场景”的顺序优先选择更结构化的技术。
4. 如果测试点只有“验证功能正常”之类泛化描述，应登记过程缺口或降级为场景测试，不直接扩展大量测试点明细。
5. 如果缺少生成测试点明细所需的业务规则、状态、入口或判定依据，使用中性分支描述；如果缺少判定依据，预期结果写 `待人工分析确认`。

## 专家审视顺序

1. 先确认需求边界：模块、角色、业务对象、状态、接口、数据对象和非范围。
2. 再识别高风险：资金、权限、不可逆、批量、外部依赖、历史缺陷和恢复成本。
3. 再选择主技术和辅助技术，避免只凭经验直接生成测试点明细。
4. 再检查预期结果：每个叶子分析节点都应有可观察结果依据；没有依据时写 `待人工分析确认`。
5. 最后控制数量：合并同路径、同风险、同预期结果的低价值测试点明细或失败类型明细。

## 测试点明细数量控制

| 明细类型 | 默认策略 |
|---|---|
| 核心明细 | 覆盖每个转测试版本必须验证的核心规则分支，必要时补充关键异常、边界或防护分支 |
| 关键明细 | 覆盖特性关键功能和关键可靠性，建议每个迭代验证 |
| 重要明细 | 覆盖系统重要功能，适合 TR 点或对外发布版本进行完整验证 |
| 一般明细 | 用于较完整的版本全量测试，按变更范围选择相关明细回归 |
| 低频明细 | 覆盖低频应用场景和特殊预置条件，建议新特性首次验证后按需回归 |

## 预期结果与 Oracle 规则

预期结果只写分析级简短判定，不展开完整用例预期清单。优先从需求、设计方案、context pack 或明确业务不变量中寻找依据。

| Oracle 类型 | 适用场景 | 预期结果依据方向 |
|---|---|
| 规则 Oracle | 业务规则、校验、限制、优先级 | 规则命中、拦截、默认处理、优先级结果 |
| 状态 Oracle | 生命周期、审批流、终态和非法迁移 | 源状态、目标状态、终态保护、非法迁移拒绝 |
| 数据 Oracle | 主数据、派生数据、缓存、统计和日志 | 主数据与派生数据一致、缓存刷新、审计可追踪 |
| 契约 Oracle | 接口字段、错误码、回调和幂等 | 响应结构、错误码、幂等响应、回调语义 |
| 权限 Oracle | 角色、资源、动作、数据范围 | 授权通过、越权拦截、数据隔离、权限变更生效 |
| 风险 Oracle | 历史缺陷、不变量和高损失失败模式 | 不重复、不泄露、不破坏、可恢复、可追踪 |

缺少判定依据时：

- 不创建假的预期结果。
- 不新增 `未明确规则` 章节。
- 相关叶子分析节点的 `预期结果` 写 `待人工分析确认`。

不应作为 Oracle 的内容：

- 纯实现猜测，例如需求未说明的数据表变化。
- 真实生产数据或需求未说明的业务事实；测试设计项可以使用由规则推导的代表值或稳定数据槽位。
- UI 操作步骤，应改写为可观察业务结果。
- 通用最佳实践本身，例如“应该有日志”，除非需求、风险或 project memory 支撑。
