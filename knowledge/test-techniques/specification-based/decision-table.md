# 判定表测试技术 DTT

## 方法定义

判定表测试技术用于描述“多个条件组合共同决定动作或结果”的业务规则。它把条件列为条件桩，把动作或结果列为动作桩，再将每一种有效规则组合转化为测试用例。

DTT 适合业务规则清晰但组合较多的场景，能防止遗漏互斥规则、缺省规则和冲突规则。

## 适用场景

- 多个条件共同决定是否允许、是否计费、是否审批、是否拦截。
- 存在业务规则矩阵、准入矩阵、费用矩阵、权限矩阵。
- 每个条件的取值有限，结果动作明确。
- 规则中存在优先级、互斥、缺省或例外。

## 不适用场景

- 只有单个判断点，应使用 DPT。
- 重点是状态从 A 到 B 的迁移，应使用 STT。
- 重点是周期边界和重复处理，应使用 PCT。
- 条件取值很多且结果相同，可先用 DCoT 裁剪。

## 建模输入

| 元素 | 说明 |
|---|---|
| 条件桩 | 影响结果的条件，例如角色、状态、金额、开关 |
| 条件项 | 条件的具体取值，例如是/否、通过/拒绝 |
| 动作桩 | 系统要执行的动作，例如允许、拒绝、计费、通知 |
| 规则列 | 一组条件项到动作项的映射 |
| 约束 | 互斥、不可能、优先级、缺省 |

## 设计步骤

1. 列出所有条件桩，只保留会影响结果的条件。
2. 列出动作桩，动作必须可观察或可验证。
3. 枚举条件组合。
4. 删除业务不可能组合，并记录原因。
5. 合并动作完全相同且风险较低的等价规则。
6. 标记冲突规则和缺省规则。
7. 每条有效规则至少派生一个测试用例。
8. 高风险规则补充异常输入、边界值或审计验证。

## 测试用例派生规则

| 规则类型 | 派生方式 |
|---|---|
| 正常允许规则 | 生成成功路径测试用例 |
| 正常拒绝规则 | 生成拦截或拒绝测试用例 |
| 缺省规则 | 生成未命中其他规则时的默认处理测试用例 |
| 冲突规则 | 生成优先级或冲突处理测试用例 |
| 不可能组合 | 不生成测试用例，在设计方案中说明 |

## 数量控制

- 条件数量小于等于 3 且风险高时，可覆盖全部有效规则。
- 条件数量较多时，优先覆盖不同动作结果和高风险规则。
- 同动作、同风险、同路径规则可合并为一条代表测试用例。
- `Level 0` 规则不得只用摘要覆盖，必须有可落地测试用例。

## 输入条件与数据依赖关注

- 准备能够满足该规则列条件的数据状态。
- 明确用户角色、业务状态、配置开关和输入值。
- 若条件无法从界面设置，需要说明后台或数据准备方式。

## 测试用例生成关注

- 按规则列逐步构造条件。
- 触发业务判定动作。
- 不在同一个测试用例中混入多个规则列。

## 预期结果依据

- 命中的规则正确。
- 执行动作正确，例如允许、拒绝、计费、通知、流转。
- 拒绝原因或提示明确。
- 审计、日志或状态变更符合规则。

## 常见误区

- 条件列不完整，遗漏缺省规则。
- 不删除不可能组合，导致生成不可落地测试用例。
- 把单个判断点硬扩展成大判定表，造成冗余。
- 只关注允许规则，遗漏拒绝和冲突处理。

## 测试用例示例

以下示例展示判定表类规则如何从“多条件组合”落到测试用例。示例中的 `TC-*` 只用于展示编号方式；实际输出必须按主交付件全局连续编号。

### 示例：优惠券使用资格判定

- 测试场景：用户提交订单时，系统判定优惠券是否可使用。

- 规格摘要：

- 条件 A：用户为会员。
- 条件 B：订单金额大于等于 100。
- 条件 C：优惠券未过期。
- 条件 D：商品不属于排除品类。
- 只有 A、B、C、D 全部满足时允许使用优惠券。
- 任一条件不满足时拒绝使用，并返回对应拒绝原因。
- 如果多个条件同时不满足，拒绝原因优先级为：优惠券过期 > 商品排除 > 金额不足 > 非会员。

- 测试点：验证优惠券使用资格的规则组合、拒绝原因和优先级。

```json
{
  "testCaseHints": [
    {
      "id": "TC-001",
      "condition": "userType=会员；orderAmount=100.00；couponStatus=未过期；productCategory=普通商品"
    },
    {
      "id": "TC-002",
      "condition": "userType=非会员；orderAmount=100.00；couponStatus=未过期；productCategory=普通商品"
    },
    {
      "id": "TC-003",
      "condition": "userType=会员；orderAmount=99.99；couponStatus=未过期；productCategory=普通商品"
    },
    {
      "id": "TC-004",
      "condition": "userType=会员；orderAmount=100.00；couponStatus=已过期；productCategory=普通商品"
    },
    {
      "id": "TC-005",
      "condition": "userType=会员；orderAmount=100.00；couponStatus=未过期；productCategory=排除品类"
    },
    {
      "id": "TC-006",
      "condition": "userType=非会员；orderAmount=99.99；couponStatus=已过期；productCategory=排除品类"
    }
  ]
}
```

- 设计要点：

- `TC-001` 覆盖唯一允许规则。
- `TC-002` 到 `TC-005` 每条只改变一个条件，便于定位拒绝原因。
- `TC-006` 专门覆盖多条件冲突时的优先级，不应被前几条单条件拒绝规则替代。
- 如果规格未说明拒绝原因或优先级，相关预期结果只写输入可支撑的保守拒绝结果，不要编造原因顺序。
