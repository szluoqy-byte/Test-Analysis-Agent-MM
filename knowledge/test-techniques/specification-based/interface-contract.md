# 接口契约测试技术

## 方法定义

接口契约测试技术用于验证系统对 API、消息、回调或第三方交互契约的遵守情况。契约包括请求字段、响应字段、错误码、鉴权、幂等、超时、重试和数据落库规则。

该技术可以指导接口测试，也可以指导前后台交互或消息驱动场景的测试设计项设计。

## 适用场景

- HTTP API、RPC、消息队列、回调通知。
- 字段必填、类型、枚举、格式、长度、范围校验。
- 鉴权、签名、权限、租户隔离。
- 错误码、错误信息、响应结构。
- 幂等、重复请求、超时、重试、回调补偿。
- 第三方系统或外部依赖交互。

## 不适用场景

- 纯页面流程且无明确接口契约，应使用场景测试。
- 多条件业务规则矩阵，应使用判定表。
- 重点是稳定性恢复，应叠加可靠性与恢复性技术。

## 建模输入

| 元素 | 说明 |
|---|---|
| 接口/消息 | 名称、路径、主题或回调地址 |
| 请求契约 | 必填字段、类型、格式、枚举、范围 |
| 响应契约 | 状态码、业务码、字段、错误信息 |
| 鉴权契约 | token、签名、角色、租户 |
| 副作用 | 数据落库、状态变化、通知、日志 |
| 异常契约 | 超时、重试、幂等、依赖失败 |

## 设计步骤

1. 明确接口入口和调用主体。
2. 识别请求字段和响应字段。
3. 设计合法请求成功测试设计项。
4. 设计字段级校验测试设计项：必填、类型、格式、枚举、范围。
5. 设计鉴权和权限测试设计项。
6. 设计错误码和错误信息测试设计项。
7. 对高风险接口补充幂等、重复请求、超时、重试和回调测试设计项。
8. 验证接口副作用：数据库、状态、消息、日志。

## 测试分析落点

当用户任务、需求或设计方案明确要求接口测试/API 契约覆盖时，测试分析方案应先按接口、端点、消息、回调或集成点建立 `TP-*`，再在该 `TP-*` 下拆契约维度。这样后续测试设计项能明确知道自己瞄准哪个接口。

推荐测试分析结构：

```markdown
### SC-001 外部接口集成

#### TP-001 E2E场景测试

##### TP-001-001 外部接口集成主流程成功闭环

- 测试点详情：验证外部接口集成场景的认证、业务请求和结果确认主流程能够按预期闭环。

- 预期结果：接口集成主流程按预期完成或待人工分析确认。

#### TP-002 接口：POST /customers/{customer_id}/transactions/

##### TP-002-001 合法支付请求创建交易

- 测试点详情：验证添加支付接口在 customer_id、amount 和 reference 符合契约时能够创建支付交易。

- 预期结果：HTTP 201 Created；响应内容以设计方案为准。

##### TP-002-002 支付请求字段不满足契约

###### TP-002-002-001 amount 格式无效

- 测试点详情：验证添加支付接口在 amount 不满足金额格式契约时能够拒绝请求。

- 预期结果：待人工分析确认。
```

跨多个接口共用的鉴权、状态码或错误处理规则可以单独建 `TP-*`，但必须写清适用范围，例如 `通用接口鉴权规则（适用于所有外部 API）`，不能只写“鉴权规则”或“状态码规则”。

## 测试设计项派生规则

| 契约类型 | 派生方式 |
|---|---|
| 成功契约 | 合法请求返回成功响应并产生正确副作用 |
| 字段契约 | 字段缺失、非法类型、非法格式、越界值 |
| 鉴权契约 | 未登录、token 失效、角色无权限、租户越权 |
| 错误契约 | 业务失败时返回指定错误码和错误信息 |
| 幂等契约 | 重复请求不产生重复副作用 |
| 回调契约 | 回调成功、失败重试、重复回调 |

## 数量控制

- 字段很多时，优先测试必填、高风险和会影响金额/权限/状态的字段。
- 同类字段校验可选择代表字段。
- `Level 0/1` 接口必须覆盖成功、关键失败、鉴权和副作用。
- 可靠性场景较多时，转交可靠性与恢复性技术补充。

## 输入条件与数据依赖关注

- 准备调用凭证、角色、租户和业务数据。
- 准备接口依赖数据和外部系统状态。
- 明确如何观察副作用，例如后台记录、状态或日志。

## 测试设计项生成关注

- 明确请求方法、入口、关键字段和触发方式。
- 对非法请求只改变一个关键字段。
- 对幂等测试设计项需要重复发送相同业务请求。
- 对回调测试设计项需要模拟回调成功、失败或重复。

## 预期结果依据

- HTTP 状态或消息消费结果正确。
- 业务错误码和错误信息正确。
- 响应字段完整且类型正确。
- 副作用正确且可追踪。
- 无权限或越权请求被拦截。
- 重复请求不产生重复订单、重复扣款或重复状态变化。

## 常见误区

- 只检查响应成功，不检查数据副作用。
- 字段校验只测缺失，不测类型、范围和枚举。
- 忽略鉴权、租户和幂等。
- 把接口错误统一写成“返回失败”，缺少错误码和可判定结果。

## 测试设计项示例

以下示例展示接口契约如何同时覆盖请求字段、响应错误码、副作用和幂等。示例中的 `TDI-*` 只用于展示编号方式；实际输出必须按主交付件全局连续编号。

### 示例：创建交易接口的订单 ID 字段契约

**测试场景**：第三方系统调用创建交易接口并传入 `orderId`。

**规格摘要**：

- 请求字段 `orderId` 必填，总长度为 13 位。
- `orderId` 格式为 3 位业务前缀 + 10 位数字流水号。
- 请求字段 `requestId` 作为幂等键。
- 合法请求返回 `SUCCESS` 并创建一条交易记录。
- `orderId` 缺失返回 `ORDER_ID_REQUIRED`；格式非法返回 `ORDER_ID_INVALID`。
- 相同 `requestId` 重复提交不重复创建交易记录。

**测试点**：验证创建交易接口的订单 ID 字段契约和幂等契约。

| 测试设计项 ID | 条件/数据/状态/组合 |
|---|---|
| TDI-001 | orderId=ABC1234567890；requestId=REQ-20260602-0001；requestId唯一 |
| TDI-002 | requestId=REQ-20260602-0002；请求体不包含orderId字段 |
| TDI-003 | orderId=AB1234567890；总长度=12位；requestId=REQ-20260602-0003 |
| TDI-004 | orderId=A#C1234567890；前3位包含特殊字符；requestId=REQ-20260602-0004 |
| TDI-005 | requestId=REQ-20260602-0001；orderId=ABC1234567890；重复提交相同业务内容 |

**设计要点**：

- 字段契约测试设计项必须说明关键字段和契约规则。
- 失败契约必须验证副作用：不落库、不产生状态变化或不重复创建。
- 幂等与字段校验是不同契约，不要合成一条泛化“异常请求”。
- 如果规格没有错误码或响应结构，预期结果写 `待人工分析确认`，不得编造。
