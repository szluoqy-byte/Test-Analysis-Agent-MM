# 等价类与边界值测试技术

## 方法定义

等价类划分将输入或业务条件划分为若干“系统应以相同方式处理”的集合，从每个集合中选择代表值生成测试用例。边界值分析关注集合边界附近最容易出错的位置，例如最小值、最大值、刚好等于、刚好小于、刚好大于。

在测试用例设计中，等价类和边界值通常一起使用：先划分有效/无效等价类，再为关键等价类选择边界值。

## 适用场景

- 数值范围：金额、数量、年龄、比例、库存、次数。
- 长度范围：文本长度、文件大小、列表数量。
- 时间范围：开始时间、结束时间、有效期、截止时间。
- 枚举集合：状态、类型、渠道、角色、币种。
- 格式规则：手机号、邮箱、证件号、编码、URL。
- 空值和缺省值：必填、选填、默认值。

## 不适用场景

- 多个条件组合共同决定结果，应优先使用判定表。
- 对象生命周期或状态迁移，应优先使用状态转换。
- 周期性批处理或账期问题，应优先使用处理周期。
- 端到端业务路径，应优先使用场景测试。

## 建模输入

从测试点中抽取：

| 元素 | 说明 |
|---|---|
| 参数/条件 | 被划分的输入项或业务条件 |
| 有效范围 | 系统允许并正常处理的取值 |
| 无效范围 | 系统应拒绝、提示或忽略的取值 |
| 边界点 | 最小、最大、临界、刚好等于、刚好越界 |
| 处理结果 | 每类输入对应的判定口径 |

## 设计步骤

1. 明确被测对象和输入域。
2. 列出有效等价类，例如合法金额、合法日期、支持的枚举值。
3. 列出无效等价类，例如空值、非法格式、越界值、不支持枚举。
4. 识别边界点：`min`、`min - 1`、`min + 1`、`max - 1`、`max`、`max + 1`。
5. 对每个高风险边界生成独立测试用例。
6. 对低风险等价类选择代表值，不做无意义穷举。
7. 若多个参数同时存在，只保留一个参数变化，其他参数保持有效默认值；多参数组合交给 DCoT。

## 测试用例派生规则

| 类型 | 派生方式 |
|---|---|
| 有效等价类 | 每类至少 1 条代表性成功测试用例 |
| 无效等价类 | 每类至少 1 条拦截、提示或拒绝测试用例 |
| 下边界 | 覆盖最小值、低于最小值 |
| 上边界 | 覆盖最大值、高于最大值 |
| 缺省/空值 | 覆盖必填为空、选填为空、默认值 |
| 格式 | 覆盖合法格式、非法格式、特殊字符 |
| 容量边界 | 覆盖小于容量、等于容量、大于容量 |

## 数量控制

- `Level 0`：覆盖有效代表值、关键上下边界、关键无效类。
- `Level 1`：覆盖有效代表值和主要无效边界。
- `Level 2`：覆盖一个有效类和一个最关键无效类。
- `Level 3/4`：只覆盖最有代表性的有效或无效路径。

## 输入条件与数据依赖关注

- 准备满足其他条件的有效业务对象。
- 固定与当前参数无关的配置、角色和状态。
- 明确边界数据来源，避免测试用例落地时临时造数不可控。

## 测试用例生成关注

- 明确输入哪个字段或选择哪个枚举值。
- 每个测试用例只改变一个核心参数，便于定位失败原因。
- 对非法输入说明提交、保存或触发校验的动作。

## 预期结果依据

- 合法输入被接受并产生正确业务结果。
- 非法输入被拒绝，提示内容明确。
- 越界数据不被保存，不产生副作用。
- 边界值按规则归属到正确区间。

## 常见误区

- 只测最大值和最小值，不测刚好越界。
- 多个参数同时取边界，导致失败原因不可定位。
- 把每个枚举值都展开成测试用例，造成低价值膨胀。
- 缺少对空值、默认值和非法格式的考虑。
- 列表、分页、批量处理等容量类规则只测“大于容量”，遗漏“小于容量”和“等于容量”的边界。

## 测试用例示例

以下示例展示“测试场景 + 规格摘要 + 测试点 + 测试用例”的完整设计粒度。示例中的 `TC-*` 只用于展示编号方式；实际输出必须在 run 内保持全局唯一和增量稳定。

### 示例 1：订单 ID 总长度边界

- 测试场景：外部系统下发订单，系统解析 `orderId` 并识别交易类型。

- 规格摘要：

- `orderId` 总长度必须为 13 位。
- 第 1 到 3 位为业务前缀，格式为 `[A-Z0-9]{3}`。
- 第 4 到 13 位为 10 位原订单流水号，格式为 `[0-9]{10}`。
- `orderId` 长度不等于 13 位时，拒绝解析，返回 `INVALID_ORDER_ID_LENGTH`，不生成交易记录。

- 测试点：验证下发订单 ID 总长度边界和分段结构。

```json
{
  "testCaseHints": [
    {
      "id": "TC-001",
      "condition": "orderId=ABC1234567890；总长度=13位；业务前缀=ABC；订单流水号=1234567890"
    },
    {
      "id": "TC-002",
      "condition": "orderId=AB1234567890；总长度=12位；其余字符集保持合法"
    },
    {
      "id": "TC-003",
      "condition": "orderId=ABCD1234567890；总长度=14位；其余字符集保持合法"
    }
  ]
}
```

- 设计要点：

- 这是输入字段长度规则，不是对系统生成结果强行构造“小于 13 位”的输出。
- `TC-002` 和 `TC-003` 只改变长度这一项，前缀字符集和流水号格式保持可解释，避免失败原因混杂。
- 如果规格未给出错误码或副作用处理，预期结果只写输入可支撑的保守拒绝结果。

### 示例 2：业务前缀格式等价类与边界

- 测试场景：管理员维护 Reason Type 的 `Order ID Business Prefix`。

- 规格摘要：

- `Order ID Business Prefix` 必填。
- 当前局点配置 `Order ID Business Prefix Format = [A-Z0-9]{3}`。
- 合法值只能由 3 位大写字母或数字组成。
- 校验失败时页面阻止保存，返回 `PREFIX_FORMAT_INVALID`。

- 测试点：验证 Order ID Business Prefix 的必填、长度和字符集校验。

```json
{
  "testCaseHints": [
    {
      "id": "TC-004",
      "condition": "businessPrefix为空字符串"
    },
    {
      "id": "TC-005",
      "condition": "businessPrefix=123；长度=3位；字符集=数字"
    },
    {
      "id": "TC-006",
      "condition": "businessPrefix=12A；长度=3位；字符集=数字+大写字母"
    },
    {
      "id": "TC-007",
      "condition": "businessPrefix=1AB；长度=3位；字符集=数字+大写字母"
    },
    {
      "id": "TC-008",
      "condition": "businessPrefix=ABC；长度=3位；字符集=大写字母"
    },
    {
      "id": "TC-009",
      "condition": "businessPrefix=AB；长度=2位"
    },
    {
      "id": "TC-010",
      "condition": "businessPrefix=ABCD；长度=4位"
    },
    {
      "id": "TC-011",
      "condition": "businessPrefix=Ab1；包含小写字母"
    },
    {
      "id": "TC-012",
      "condition": "businessPrefix=A#1；包含特殊字符"
    }
  ]
}
```

- 设计要点：

- 合法等价类按“全数字、数字+大写字母组合、全大写字母”选择代表项，不枚举所有字符。
- 非法等价类拆成“空值、短于长度、长于长度、小写、特殊字符”，每条失败原因单一。
- 如果需求只写“页面报错，提示信息正确”但没有错误码或文案，预期结果只写输入可支撑的保守错误结果，不要编造 `PREFIX_FORMAT_INVALID`。

### 示例 3：交易金额范围与精度边界

- 测试场景：用户发起钱包转账，系统校验转账金额。

- 规格摘要：

- 转账金额最小值为 `1.00`。
- 转账金额最大值为 `5000.00`。
- 金额最多保留 2 位小数。
- 金额低于最小值返回 `AMOUNT_BELOW_MIN`；高于最大值返回 `AMOUNT_EXCEED_LIMIT`；精度超过 2 位返回 `AMOUNT_PRECISION_INVALID`。

- 测试点：验证转账金额范围和精度边界。

```json
{
  "testCaseHints": [
    {
      "id": "TC-013",
      "condition": "amount=1.00；边界=最小值"
    },
    {
      "id": "TC-014",
      "condition": "amount=0.99；边界=小于最小值"
    },
    {
      "id": "TC-015",
      "condition": "amount=5000.00；边界=最大值"
    },
    {
      "id": "TC-016",
      "condition": "amount=5000.01；边界=大于最大值"
    },
    {
      "id": "TC-017",
      "condition": "amount=1000.00；范围=合法范围内；精度=2位小数"
    },
    {
      "id": "TC-018",
      "condition": "amount=1000.001；范围=合法范围内；精度=3位小数"
    }
  ]
}
```

- 设计要点：

- 范围边界和精度边界是两个输入域，应分别设计，避免一条测试用例同时越界又精度非法。
- 金额范围测试用例默认其他条件有效，例如账户状态、余额、权限和币种均满足需求，否则失败原因不可定位。
- 如果规格未说明错误码，只能表达确定行为；连失败处理也未说明时，预期结果只写输入可支撑的保守预期。
