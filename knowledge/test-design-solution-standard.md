# 测试设计方案标准

本文档定义本 Agent 的核心输出粒度：`测试设计方案`。它承接测试分析阶段识别出的测试场景和测试点，并使用测试技术选择代表性的条件、数据、状态或组合，形成可供后续完整测试用例写作使用的设计方案。

## 分层关系

```text
需求 + 设计方案
  -> 测试场景
      -> 测试点
          -> 测试设计项
              -> 完整测试用例（不由本 Agent 输出）
```

## 核心定义

| 对象 | 定义 | 本 Agent 是否输出 |
|---|---|---|
| 测试场景 | 从需求和设计方案中识别出的业务使用、系统触发或专项质量验证情境 | 是 |
| 测试点 | 场景下需要验证的规则、路径、风险、接口契约、状态或质量关注点，回答 what to test | 是 |
| 测试设计项 | 由测试点结合测试技术派生出的代表性条件、数据、状态或组合，回答 how to test this point | 是 |
| 预期结果 | 需求或设计方案明确支持的简短判定结果；依据不足时固定写 `待人工分析确认` | 是 |
| 完整测试用例 | 可执行产物，包含前置步骤、测试步骤、测试数据和完整预期结果 | 否 |

## 测试设计项字段

| 字段 | 要求 |
|---|---|
| 测试设计项 ID | 使用 `TD-001` 起全局连续编号 |
| 测试设计项 | 代表性条件、数据、状态或组合，不写执行步骤 |
| 预期结果 | 明确、简短、可由需求/设计方案支撑；依据不足时写 `待人工分析确认` |

## 测试设计项命名规则

推荐结构：

```text
<对象/字段/状态/组合> 为 <代表条件>
<角色/状态/配置> 下 <业务动作或系统触发>
<接口/任务/消息> 在 <请求/触发条件> 下
```

示例：

- 下发订单 ID 总长度为 13 位
- 下发订单 ID 总长度为 10 位
- 下发订单 ID 为空
- 普通用户在库存充足且地址有效时提交实物商品订单
- 订单已支付状态下重复提交支付请求
- 创建订单接口缺少必填字段

测试设计项必须能独立回答三个问题：

1. 代表条件、数据、状态或组合是什么。
2. 它覆盖的是哪个测试点下的差异化风险或路径。
3. 后续完整用例写作可以据此补步骤和数据，而不需要重新分析覆盖目标。

## 预期结果规则

预期结果不是完整测试用例里的长清单，只写设计级简短判定。

适合写入：

- 订单下发成功。
- 订单下发失败。
- 订单取消成功，订单状态更新为已取消。
- 请求被拒绝，返回需求或设计方案明确的错误码。
- 不生成重复支付记录。
- 待人工分析确认。

必须写 `待人工分析确认` 的情况：

- 需求和设计方案没有说明错误提示。
- 需求和设计方案没有说明错误码。
- 需求和设计方案没有说明失败后的状态变化。
- 需求和设计方案没有说明接口返回内容、消息发送结果或数据记录变化。
- 需求和设计方案存在冲突，无法确定哪个结果应作为判定依据。

不适合写入：

- 具体操作步骤。
- 完整测试数据表。
- 接口调用代码或自动化断言脚本。
- 编造出来的错误码、提示文案、状态枚举、接口字段或数据库字段。
- “按需求”“同上”“见设计方案”等非自包含占位。

## 粒度规则

- 一条测试设计项应对应一个清晰的代表性条件、数据、状态或组合。
- 高风险测试点可以拆成多条测试设计项，例如主路径、关键异常、边界、权限和幂等。
- 同一测试点下仅输入取值不同但系统处理结果一致的内容，可以合并为一条测试设计项。
- 不同状态迁移、错误类型、接口契约、权限边界或缺陷定位方向，应拆成不同测试设计项。
- 不为了覆盖每个按钮、字段或具体数值机械生成测试设计项。

## 禁止项

- 不输出前置步骤、测试步骤、操作步骤或自动化脚本。
- 不使用旧版主交付件字段作为主输出表头；字段禁用清单以 `bin/lint-test-design-solution.py` 为准。
- 不设置 `未明确规则` 章节。
- 不设置独立待确认信息清单。
- 不把测试技术名称直接塞进测试设计项，例如“边界值测试订单 ID”。
- 不把“正常/异常/校验通过/功能正确”作为测试设计项主体。
- 不编造需求或设计方案没有给出的阈值、状态、错误码、错误提示、接口路径或业务规则。
