# 测试设计方案标准

测试设计方案回答 how to test，输出：

```text
测试场景 SC -> 测试点 TP -> 测试用例 TC
```

它继承测试分析方案的场景树和测试点，并在每个测试点下生成完整步骤级测试用例。

## 层级边界

| 层级 | 编号 | 定义 |
|---|---|---|
| 测试场景 | `SC-*` | 从测试分析方案继承，最多 3 层 |
| 测试点 | `TP-*` | 从测试分析方案继承，不在设计阶段重写 |
| 测试用例 | `TC-*` | 可执行实例，包含前置条件、测试数据、步骤、步骤预期和最终预期 |

`TP-*` 和 `TC-*` 均全局连续编号。

## 测试用例字段

每个 TC 必须包含：

```json
{
  "id": "TC-001",
  "title": "普通用户取消本人待支付订单成功闭环",
  "preconditions": ["用户 A 已登录", "订单 ORDER_1001 属于用户 A"],
  "testData": [
    {"name": "order_id", "value": "ORDER_1001", "description": "本人待支付订单"}
  ],
  "steps": [
    {"stepNo": 1, "action": "用户 A 发起取消", "expected": "系统接受取消请求"}
  ],
  "expectedResult": "订单取消成功，库存释放并记录取消原因。",
  "sourceRefs": [
    {"source": "requirements.md", "location": "订单取消", "description": "依据摘要"}
  ]
}
```

## 粒度规则

- TC 必须具体到一个可执行实例，而不是抽象条件标签。
- `testData[]` 必须给出具体值或稳定数据槽位，并说明含义。
- `steps[]` 按执行顺序排列，`stepNo` 从 1 连续。
- `expectedResult` 是最终预期；步骤级预期写在 `steps[].expected`。
- 如果输入没有明确错误码、提示文案、状态值或阈值，不补写具体值，只写输入可支撑的保守预期。
- 接口类 TC 不写完整裸 URL，使用 `接口=METHOD /path`、`参数名=参数值`、`响应状态=...` 等字段片段。
- E2E 测试点生成端到端主流程 TC，其他规则、异常、接口、权限、状态、回滚或补偿 TC 保留在同级测试点下。

## 禁止项

- 不新增、删除、合并或改写分析方案中的 `SC-*` 与 `TP-*`。
- 不输出 schemaVersion 2.0 之外的结构字段。
- 不输出 schemaVersion 2.0 之外的编号或术语。
- 不输出自动化脚本、SQL 修改脚本或真实生产数据。
- 不编造需求或设计方案没有说明的业务事实。
