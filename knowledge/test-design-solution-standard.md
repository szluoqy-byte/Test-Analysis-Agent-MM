# 测试设计方案标准

本文档定义 `test-design-agent` 的核心输出粒度：`测试设计方案`。它回答 how to test，在已评审测试分析方案的基础上，为每个普通测试点明细或失败类型明细补充代表性条件、数据、状态或组合。

## 分层关系

```text
需求 + 可选设计方案
  -> 测试场景
      -> 测试点
          -> 测试点明细
              -> 失败类型明细（仅分析方案中已有第四层时继承）
                  -> 测试设计项
              -> 测试设计项（普通测试点明细）
                  -> 完整测试用例（不由本 Agent 输出）
```

## 核心定义

| 对象 | 定义 | test-design-agent 是否输出 |
|---|---|---|
| 测试场景 | 从已评审测试分析方案继承的业务使用、系统触发或专项质量验证情境 | 是，继承 |
| 测试点 | 从已评审测试分析方案继承的规则、路径、风险、接口契约、状态或质量关注点 | 是，继承 |
| 测试点明细 | 从已评审测试分析方案继承的规则分支、路径分支、状态分支、权限分支、接口契约分支或风险分支 | 是，继承 |
| 失败类型明细 | 从已评审测试分析方案继承的非成功分支第四层，用于区分不同失败来源或失败类型 | 是，继承 |
| 预期结果 | 从测试分析方案继承到普通测试点明细或失败类型明细层的简短判定结果；依据不足时保留输入可支撑的保守预期 | 是 |
| 测试设计项 | 基于测试点明细或失败类型明细选择的代表性条件、数据、状态或组合，回答 how to test，不重复写预期结果 | 是 |
| 完整测试用例 | 可执行产物，包含前置步骤、测试步骤、测试数据和完整预期结果 | 否 |

## 术语与缩写

主交付件只使用中文术语和固定缩写，不展开英文全名。

| 中文术语 | 固定缩写/ID | ID 规则 |
|---|---|---|
| 测试场景 | `SC` | 继承分析方案，`SC-001` 起连续编号 |
| 测试点 | `TP` | 继承分析方案，`TP-001` 起连续编号 |
| 测试点明细 | `TP-*-*` | 继承分析方案，例如 `TP-001-001` |
| 失败类型明细 | `TP-*-*-*` | 继承分析方案，例如 `TP-001-002-001` |
| 测试设计项 | `TDI` | `TDI-001` 起全局连续编号 |

不得在主交付件中使用 `TD-*`、`TC-*`、`TCT-*`、`TI-*`、`ITP-*` 或 `ITDI-*` 作为编号体系。

## JSON 字段结构

每个普通测试点明细下必须使用 `designItems[]` 表达测试设计项。若分析方案中某个非成功测试点明细已拆出 `TP-*-*-*`，则 `designItems[]` 必须挂在第四层失败类型明细下，不挂在父级 `TP-*-*` 下。主交付件 JSON 不使用测试设计项表格；派生 Markdown 会渲染为 `- TDI-001 <条件/数据/状态/组合>` 列表节点，便于转脑图时保持层级。

`expectedResult` 固定保留在普通测试点明细或失败类型明细层，只写一次；`designItems[].content` 只写代表性条件、数据、状态或组合，不重复写 `expectedResult`。

```json
{
  "id": "TP-001-001",
  "title": "<测试点明细>",
  "description": "<来自测试分析方案的测试点详情。>",
  "expectedResult": "<明确预期结果，或输入可支撑的保守预期>",
  "failureDetails": [],
  "designItems": [
    {
      "id": "TDI-001",
      "content": "<代表性条件、数据、状态或组合>"
    }
  ]
}
```

| 字段 | 要求 |
|---|---|
| `designItems[].id` | 使用 `TDI-001` 形式，全局连续编号 |
| `designItems[].content` | 说明覆盖该测试点明细或失败类型明细的代表性条件、具体数据值、状态、接口返回或组合，不写步骤 |
| `expectedResult` | 写在普通测试点明细或失败类型明细层；依据不足时只写输入可支撑的保守预期；不得写入 `designItems[].content` |

## 粒度规则

- 测试点明细回答“这个测试点下有哪些规则分支或行为分支”。
- 测试设计项回答“这个分支用哪些代表性条件、数据、状态或组合覆盖”。
- 测试设计项应优先给出具体数据值、数据槽位、接口返回、状态值或组合，例如 `amount=1000.00；category=PAY；customer_id=AGT_CUSTOMER_001`。
- 不要只写“有效MSISDN”“有效金额”“错误PIN”“接口超时”等抽象标签；应补充具体取值、数据依赖或模拟返回条件。
- 测试设计项不得写成结果或动作描述，例如“发送通知”“显示错误提示”“自动填充”“接口调用正确”“系统完成支付流程”；这些内容属于预期结果、验证点或执行行为，不能作为 `TDI-*` 正文。应改写为条件、数据、状态、接口返回或依赖组合，例如 `渠道=APP；号码来源=客户查询返回；telephone_exact=%2B225070000001`。
- 同类条件在多个场景、渠道或流程中重复出现时，`TDI-*` 必须补充能区分语义的维度，例如 `场景=Add Payment`、`渠道=APP`、`操作=Delete Favorite`、`接口=POST /payments/`、`数据依赖=预验证已失败`；不得只复制相同的条件片段凑数量。
- 接口类测试设计项不得写完整裸 URL，例如 `GET https://api.example.com/customers/?telephone_exact=...`。应拆成同一行字段片段，例如 `接口=GET /customers/；telephone_exact=%2B225070000001；响应状态=HTTP 500`，避免 Markdown 转脑图时被自动识别为链接或因长 URL 换行破坏层级。
- 接口契约类叶子节点应根据需求或设计方案已明确的字段约束展开代表性条件。若设计明确 `amount` 为两位小数、`category=PAY`、`customer_id` 必填，则除有效组合外，应按适用性补充 `amount=1000`、`amount=1000.0`、`amount=1000.001`、`amount=abc`、`category=REFUND`、`缺少customer_id` 等不同契约风险的设计项；未被输入说明的字段或枚举不得编造。
- 超时、回滚、补偿或依赖恢复类叶子节点应把业务设计中的可观察分支数据化，例如 `查询返回count=1；payment_status=SUCCESS`、`查询返回count=0；payment_status=FAILED`、`查询超时；payment_status=TIMEOUT`、`查询返回count>1；处理状态=输入未说明具体终态`；不要只写“接口超时”或“补偿成功”。
- 如果不允许暴露真实测试数据，使用稳定数据槽位命名，例如 `AGT_REGISTERED_MSISDN_01`、`MM_VALID_PIN_01`、`PAYMENT_AMOUNT_VALID_01`。
- 普通测试点明细至少应有一个测试设计项。
- `E2E场景测试` 从分析方案继承为独立同级测试点，只维护端到端主流程成功闭环设计项；不得把其他规则、异常、接口、权限、状态、回滚或补偿设计项挂到 E2E 测试点下。
- 如果分析方案包含接口测试或集成覆盖场景，测试设计方案必须继承其接口优先组织结构：先目标接口、端点、消息、回调、集成点或通用接口范围，再契约维度叶子节点，再补充 `TDI-*`。不得把多个接口的代表性条件混在无法定位目标接口的泛化测试点下。
- 如果测试分析方案中某个非成功测试点明细存在 `TP-*-*-*` 第四层，不得合并或删除第四层；每个失败类型明细至少应有一个测试设计项。
- 如果测试分析方案中的单一弱结果分支停留在 `TP-*-*`，例如未注册、未找到、返回空列表、count=0、无记录、回滚或补偿状态确认，测试设计方案直接在该 `TP-*-*` 下生成测试设计项，不为了设计阶段机械新增第四层。
- 设计阶段发现分析方案缺少接口归属、E2E 误挂分支或第四层拆分不合理时，应记录输入质量问题，必要时回到 `test-analysis-agent` 修正，不在测试设计方案中静默改写分析层级。
- 如果多个输入取值代表同一等价类、同一业务判定和同一风险，可合并为一个测试设计项。
- 如果输入取值代表不同边界、不同错误类型、不同状态迁移、不同权限判定或不同接口契约，应拆成多个测试设计项。
- 如果同一叶子节点下不同测试设计项需要不同预期结果，说明分析层叶子粒度不足，应回到测试分析方案拆分测试点明细或失败类型明细；不要在 TDI 下追加预期结果来掩盖分支混杂。
- 测试设计项不应包含前置步骤、点击路径、接口调用脚本、SQL、自动化断言或执行数据清单。

## 预期结果规则

预期结果不是完整测试用例里的长清单，只写叶子分析节点级简短判定。测试设计方案继承测试分析方案中的判定语义，并在普通测试点明细或失败类型明细层保留 `expectedResult`。`designItems[].content` 不再重复写预期结果。

适合写入：

- 下发成功。
- 下发失败。
- 订单取消成功，订单状态更新为已取消。
- 请求被拒绝，返回需求或设计方案明确的错误码。
- 不生成重复支付记录。
- 请求被拒绝，系统不产生成功态数据变更。

只能写输入可支撑的保守预期的情况：

- 需求和设计方案没有说明错误提示。
- 需求和设计方案没有说明错误码。
- 需求和设计方案没有说明失败后的状态变化。
- 需求和设计方案没有说明接口返回内容、消息发送结果或数据记录变化。
- 需求和设计方案存在冲突，无法确定哪个结果应作为判定依据。

不适合写入：

- 具体操作步骤。
- 完整测试数据表。
- 接口调用代码或自动化断言脚本。
- 编造出来的错误码、提示文案、状态枚举、接口字段或数据库字段。
- “按需求”“同上”“见设计方案”等非自包含占位。

## 禁止项

- 不输出前置步骤、测试步骤、操作步骤或自动化脚本。
- 不使用旧版主交付件字段作为主输出表头；字段禁用清单以 `bin/lint-test-design-solution.py` 为准。
- 不设置 `未明确规则` 章节。
- 不设置独立信息清单。
- 不使用 Markdown 加粗语法，例如 `**文本**` 或 `__文本__`。
- 不把“正常/异常/校验通过/功能正确”作为测试设计项主体。
- 不在 `TDI-*` 下一层重复写 `预期结果`。
- 不在 `TDI-*` 中输出 `http://` 或 `https://` 裸链接；接口、参数和响应状态必须拆成同一行的字段片段。
- 不编造需求或设计方案没有给出的阈值、状态、错误码、错误提示、接口路径或业务规则。
