# 测试设计方案标准

测试设计方案回答 how to test，输出：

```text
测试场景 SC -> 测试点 TP -> 测试用例 TC
```

它继承测试分析方案的场景树和测试点，并在每个测试点下生成完整步骤级测试用例。

生成过程必须按已冻结 `TP-*` 逐项生成 `process/test-case-slices/<TP-ID>.md`。TC 切片只允许填写当前 TP 的测试用例内容，不得新增、删除、合并或改写 `SC-*` 与 `TP-*`。

## 层级边界

| 层级 | 编号 | 定义 |
|---|---|---|
| 测试场景 | `SC-*` | 从测试分析方案继承，最多 3 层 |
| 测试点 | `TP-*` | 从测试分析方案继承，不在设计阶段重写 |
| 测试用例 | `TC-*` | 可执行实例，包含用例级别、前置条件、测试数据、步骤、步骤预期和最终预期 |

`TP-*` 和 `TC-*` 均在 run 内全局唯一且增量稳定。补充设计时保留既有编号，新编号从历史最大值后追加，退役编号不复用。

## 测试用例字段

每个 TC 必须包含：

```json
{
  "id": "TC-001",
  "title": "普通用户取消本人待支付订单成功闭环",
  "level": "Level 1",
  "preconditions": ["用户 A 已登录", "订单 ORDER_1001 属于用户 A"],
  "testData": [
    {"name": "order_id", "value": "ORDER_1001", "description": "本人待支付订单"}
  ],
  "steps": [
    {"stepNo": 1, "action": "用户 A 发起取消", "expected": "系统接受取消请求"}
  ],
  "expectedResult": "订单取消成功，库存释放并记录取消原因。",
  "sourceRefs": [
    {"source": "requirements.md", "location": "订单取消", "description": "依据摘要"}
  ]
}
```

## 用例级别

`level` 是 TC 的执行优先级和风险等级，取值固定为 `Level 0` 到 `Level 4`。

| 级别 | 定义 |
|---|---|
| `Level 0` | 失败会导致版本核心功能受损，且没有继续验证价值 |
| `Level 1` | 失败会阻塞特性内关键功能、关键可靠性或关键业务链路 |
| `Level 2` | 失败会影响系统重要功能，需要在 TR 点或对外发布版本完整验证 |
| `Level 3` | 失败影响一般功能，适合在版本变更较大或全量验证时纳入回归 |
| `Level 4` | 失败只影响低频应用场景或特殊预置条件，适合新特性首次验证后按需回归 |

用例级别来自需求影响、失败后果、风险技术判断、历史缺陷、动态来源和当前测试点的重要性；没有明确风险依据时，默认不高于 `Level 2`。

## 粒度规则

- TP 是验证目标簇，TC 是测试实例。每个 TP 下应生成覆盖该验证目标所有适用测试设计因子的最小充分 TC 集合；只有当输入依据、业务不变量和模型测试经验都不能支持额外独立因子拆分时，才允许该 TP 下只有 1 个 TC。
- 生成 TC 前必须先识别当前 TP 的必选因子、候选因子和模型补充必要因子，包括但不限于输入条件、等价类、边界点、角色权限、业务状态、配置开关、外部依赖返回、消息顺序、异常类型、接口参数变体、数据组合和预期结果差异。
- rules、当前用户明确指令和输入文档明确事实中的因子是必选覆盖项；knowledge、project/personal 动态来源和方法参考中的因子是重要候选与启发，需要结合当前 TP 判断适用性。
- 已加载来源中的既有测试设计因子不是封闭上限。除非更高优先级指令明确限定仅使用指定因子集合，否则不得因为因子库、checklist、knowledge 或方法参考未列出某类情况，就忽略该 TP 下有判定意义的独立测试实例。
- 最小充分 TC 集合应覆盖：该 TP 的代表性成功路径、代表性拒绝/失败路径、高风险边界或异常、状态/权限/配置差异，以及输入依据明确要求和模型基于 TP 目标可合理推导的关键组合；不要求穷举无业务意义的笛卡尔积。“最小充分”不是“最少”，而是覆盖所有对该 TP 判定有意义的独立测试实例。
- TC 必须具体到一个可执行实例，而不是抽象条件标签。
- TC 公共写作必须遵守 `knowledge/test-case-writing-standard.md`；执行形态差异必须遵守 `knowledge/test-case-writing-styles/` 下对应规范。生成和评审前应按 GUI、API、CLI 或通用可执行动作判定主执行形态。
- TC 必须保持原子性：一个 TC 只覆盖一个可独立执行、独立判定的测试实例。
- TC 原子性适用于接口、页面、业务流程、权限、状态、配置、批处理、消息、外部依赖、数据组合和异常处理等所有测试类型。
- 不同输入条件、数据组合、等价类、边界点、角色、权限、状态、配置、外部依赖返回、消息顺序、异常类型或接口参数变体必须拆成独立 TC。
- 如果某个 TP 只生成 1 个 TC，必须能从输入依据、业务不变量、模型测试经验、切片评审结论或 coverage 结论说明该 TP 不存在可支持的额外独立因子拆分；不得为此在 `test-design-solution.json` 的 TC 内新增 schema 未定义字段。
- `steps[]` 只表达同一个测试实例内的顺序动作与观察点，不得用多条步骤枚举多个互斥请求、多组替代数据、多种角色/状态/配置切换或多条独立路径。
- 例如同一接口的 `orderNo` 缺失、`channel` 缺失、`amount` 缺失、`clientRequestId` 缺失是 4 个 TC，不是 1 个 TC 的 4 个步骤；不同角色取消订单、不同订单状态取消订单、不同开关配置下创建订单也同理拆分。
- `testData[]` 必须给出具体值或稳定数据槽位，并说明含义。
- `steps[]` 按执行顺序排列，`stepNo` 从 1 连续。
- `steps[].action` 只写用户、测试人员、外部调用方或测试工具可执行的操作或取数动作，不单独写检查项、断言项、观察结论或系统内部行为。
- 不得把系统行为写成测试步骤动作，例如 `MM系统判断count=0后取消交易`、`系统返回错误提示`、`服务端释放库存`、`定时任务触发补偿` 都不应出现在 `action`；这类内容应写入同一步或后续取数步骤的 `expected`。
- 字段值、状态、记录、事件、响应内容等检查要求写入同一步的 `steps[].expected`；例如不要把 `检查响应体字段` 写成独立步骤。
- `expectedResult` 是最终预期；步骤级预期写在 `steps[].expected`。
- 如果输入没有明确错误码、提示文案、状态值或阈值，不补写具体值，只写输入可支撑的保守预期。
- 接口类 TC 不写完整裸 URL，使用 `接口=METHOD /path`、`参数名=参数值`、`响应状态=...` 等字段片段。
- E2E 测试点生成端到端主流程 TC，其他规则、异常、接口、权限、状态、回滚或补偿 TC 保留在同级测试点下。

## 禁止项

- 不新增、删除、合并或改写分析方案中的 `SC-*` 与 `TP-*`。
- 不输出 schemaVersion 2.0 之外的结构字段。
- 不输出 schemaVersion 2.0 之外的编号或术语。
- 不输出自动化脚本、SQL 修改脚本或真实生产数据。
- 不编造需求或设计方案没有说明的业务事实。
