# 测试设计方案标准

本文档定义 `test-design-agent` 的核心输出粒度：`测试设计方案`。它回答 how to test，在已评审测试分析方案的基础上，为每个普通测试点明细或失败类型明细补充代表性条件、数据、状态或组合。

## 分层关系

```text
需求 + 可选设计方案
  -> 测试场景
      -> 测试点
          -> 测试点明细
              -> 失败类型明细（仅分析方案中已有第四层时继承）
                  -> 测试设计项
              -> 测试设计项（普通测试点明细）
                  -> 完整测试用例（不由本 Agent 输出）
```

## 核心定义

| 对象 | 定义 | test-design-agent 是否输出 |
|---|---|---|
| 测试场景 | 从已评审测试分析方案继承的业务使用、系统触发或专项质量验证情境 | 是，继承 |
| 测试点 | 从已评审测试分析方案继承的规则、路径、风险、接口契约、状态或质量关注点 | 是，继承 |
| 测试点明细 | 从已评审测试分析方案继承的规则分支、路径分支、状态分支、权限分支、接口契约分支或风险分支 | 是，继承 |
| 失败类型明细 | 从已评审测试分析方案继承的非成功分支第四层，用于区分不同失败来源或失败类型 | 是，继承 |
| 测试设计项 | 基于测试点明细选择的代表性条件、数据、状态或组合，回答 how to test | 是 |
| 预期结果 | 需求或设计方案明确支持的简短判定结果；依据不足时固定写 `待人工分析确认` | 是 |
| 完整测试用例 | 可执行产物，包含前置步骤、测试步骤、测试数据和完整预期结果 | 否 |

## 术语与缩写

主交付件只使用中文术语和固定缩写，不展开英文全名。

| 中文术语 | 固定缩写/ID | ID 规则 |
|---|---|---|
| 测试场景 | `SC` | 继承分析方案，`SC-001` 起连续编号 |
| 测试点 | `TP` | 继承分析方案，`TP-001` 起连续编号 |
| 测试点明细 | `TP-*-*` | 继承分析方案，例如 `TP-001-001` |
| 失败类型明细 | `TP-*-*-*` | 继承分析方案，例如 `TP-001-002-001` |
| 测试设计项 | `TDI` | `TDI-001` 起全局连续编号 |

不得在主交付件中使用 `TD-*`、`TC-*`、`TCT-*`、`TI-*`、`ITP-*` 或 `ITDI-*` 作为编号体系。

## 测试设计项字段

每个普通测试点明细下必须使用固定表格。若分析方案中某个非成功测试点明细已拆出 `TP-*-*-*`，则固定表格必须挂在第四层失败类型明细下，不挂在父级 `TP-*-*` 下。

```markdown
| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-001 | <代表性条件、数据、状态或组合> | <明确预期结果或待人工分析确认> |
```

| 字段 | 要求 |
|---|---|
| 测试设计项 ID | 使用 `TDI-001` 形式，全局连续编号 |
| 条件/数据/状态/组合 | 说明覆盖该测试点明细的代表性条件、数据、状态或组合，不写步骤 |
| 预期结果 | 明确、简短、可由需求/设计方案支撑；依据不足时写 `待人工分析确认` |

## 粒度规则

- 测试点明细回答“这个测试点下有哪些规则分支或行为分支”。
- 测试设计项回答“这个分支用哪些代表性条件、数据、状态或组合覆盖”。
- 普通测试点明细至少应有一个测试设计项。
- `E2E场景测试` 从分析方案继承为独立同级测试点，只维护端到端主流程成功闭环设计项；不得把其他规则、异常、接口、权限、状态、回滚或补偿设计项挂到 E2E 测试点下。
- 如果分析方案包含接口测试或集成覆盖场景，测试设计方案必须继承其接口优先组织结构：先目标接口、端点、消息、回调、集成点或通用接口范围，再契约维度叶子节点，再补充 `TDI-*`。不得把多个接口的代表性条件混在无法定位目标接口的泛化测试点下。
- 如果测试分析方案中某个非成功测试点明细存在 `TP-*-*-*` 第四层，不得合并或删除第四层；每个失败类型明细至少应有一个测试设计项。
- 如果测试分析方案中的单一弱结果分支停留在 `TP-*-*`，例如未注册、未找到、返回空列表、count=0、无记录、回滚或补偿状态确认，测试设计方案直接在该 `TP-*-*` 下生成测试设计项，不为了设计阶段机械新增第四层。
- 设计阶段发现分析方案缺少接口归属、E2E 误挂分支或第四层拆分不合理时，应记录输入质量问题，必要时回到 `test-analysis-agent` 修正，不在测试设计方案中静默改写分析层级。
- 如果多个输入取值代表同一等价类、同一业务判定和同一风险，可合并为一个测试设计项。
- 如果输入取值代表不同边界、不同错误类型、不同状态迁移、不同权限判定或不同接口契约，应拆成多个测试设计项。
- 测试设计项不应包含前置步骤、点击路径、接口调用脚本、SQL、自动化断言或执行数据清单。

## 示例

```markdown
### SC-001 订单下发

#### TP-001 E2E场景测试

##### TP-001-001 订单下发主流程成功闭环

- 测试点详情：验证订单下发场景的端到端主流程能够从请求接收到订单处理结果完成闭环。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-001 | 订单下发主流程满足需求定义的必要前置条件、必填字段和有效业务状态 | 订单下发成功 |

#### TP-002 验证下发订单 ID 长度规则

##### TP-002-001 下发订单 ID 满足长度要求

- 测试点详情：验证下发订单 ID 符合需求定义的长度规则时，系统能够正常识别并处理订单下发请求。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-002 | 下发订单 ID 总长度等于 13 位 | 下发成功 |

##### TP-002-002 下发订单 ID 不满足长度要求

###### TP-002-002-001 下发订单 ID 长度小于规则要求

- 测试点详情：验证下发订单 ID 长度短于需求定义的长度规则时，系统能够识别为无效订单 ID 并拒绝处理订单下发请求。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-003 | 下发订单 ID 总长度小于 13 位 | 待人工分析确认 |

###### TP-002-002-002 下发订单 ID 长度大于规则要求

- 测试点详情：验证下发订单 ID 长度长于需求定义的长度规则时，系统能够识别为无效订单 ID 并拒绝处理订单下发请求。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-004 | 下发订单 ID 总长度大于 13 位 | 待人工分析确认 |
```

弱结果分支直接承接示例：

```markdown
#### TP-003 接口：GET /customers/?telephone_exact={phone}

##### TP-003-001 未注册 MSISDN 返回空结果

- 测试点详情：验证查询客户接口在 MSISDN 未注册时返回空结果。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-005 | telephone_exact 为未注册但格式有效的 MSISDN | 返回 count=0；若错误处理规则未说明则待人工分析确认 |
```

接口场景继承示例：

```markdown
### SC-002 客户查询接口

#### TP-004 接口：GET /customers/?telephone_exact={phone}

##### TP-004-001 有效 MSISDN 返回客户数据

- 测试点详情：验证查询客户接口在 MSISDN 已注册时返回客户详情。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-006 | telephone_exact 为已注册且格式有效的 MSISDN | 返回 count=1 和设计方案明确的客户详情字段 |

##### TP-004-002 telephone_exact 参数不满足格式要求

###### TP-004-002-001 参数缺失

- 测试点详情：验证查询客户接口在缺少 telephone_exact 参数时的错误处理。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-007 | 请求中不传 telephone_exact 参数 | 待人工分析确认 |

###### TP-004-002-002 参数格式非法

- 测试点详情：验证查询客户接口在 telephone_exact 参数格式非法时的错误处理。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-008 | telephone_exact 为包含非数字字符的 MSISDN | 待人工分析确认 |
```

## 预期结果规则

预期结果不是完整测试用例里的长清单，只写设计项级简短判定。

适合写入：

- 下发成功。
- 下发失败。
- 订单取消成功，订单状态更新为已取消。
- 请求被拒绝，返回需求或设计方案明确的错误码。
- 不生成重复支付记录。
- 待人工分析确认。

必须写 `待人工分析确认` 的情况：

- 需求和设计方案没有说明错误提示。
- 需求和设计方案没有说明错误码。
- 需求和设计方案没有说明失败后的状态变化。
- 需求和设计方案没有说明接口返回内容、消息发送结果或数据记录变化。
- 需求和设计方案存在冲突，无法确定哪个结果应作为判定依据。

不适合写入：

- 具体操作步骤。
- 完整测试数据表。
- 接口调用代码或自动化断言脚本。
- 编造出来的错误码、提示文案、状态枚举、接口字段或数据库字段。
- “按需求”“同上”“见设计方案”等非自包含占位。

## 禁止项

- 不输出前置步骤、测试步骤、操作步骤或自动化脚本。
- 不使用旧版主交付件字段作为主输出表头；字段禁用清单以 `bin/lint-test-design-solution.py` 为准。
- 不设置 `未明确规则` 章节。
- 不设置独立待确认信息清单。
- 不使用 Markdown 加粗语法，例如 `**文本**` 或 `__文本__`。
- 不把“正常/异常/校验通过/功能正确”作为测试设计项主体。
- 不编造需求或设计方案没有给出的阈值、状态、错误码、错误提示、接口路径或业务规则。
