# 测试设计方案标准

本文档定义 `test-design-agent` 的核心输出粒度：`测试设计方案`。它回答 how to test，在已评审测试分析方案的基础上，为每个测试点明细补充代表性条件、数据、状态或组合。

## 分层关系

```text
需求 + 可选设计方案
  -> 测试场景
      -> 测试点
          -> 测试点明细
              -> 测试设计项
                  -> 完整测试用例（不由本 Agent 输出）
```

## 核心定义

| 对象 | 定义 | test-design-agent 是否输出 |
|---|---|---|
| 测试场景 | 从已评审测试分析方案继承的业务使用、系统触发或专项质量验证情境 | 是，继承 |
| 测试点 | 从已评审测试分析方案继承的规则、路径、风险、接口契约、状态或质量关注点 | 是，继承 |
| 测试点明细 | 从已评审测试分析方案继承的规则分支、路径分支、状态分支、权限分支、接口契约分支或风险分支 | 是，继承 |
| 测试设计项 | 基于测试点明细选择的代表性条件、数据、状态或组合，回答 how to test | 是 |
| 预期结果 | 需求或设计方案明确支持的简短判定结果；依据不足时固定写 `待人工分析确认` | 是 |
| 完整测试用例 | 可执行产物，包含前置步骤、测试步骤、测试数据和完整预期结果 | 否 |

## 术语与缩写

主交付件只使用中文术语和固定缩写，不展开英文全名。

| 中文术语 | 固定缩写/ID | ID 规则 |
|---|---|---|
| 测试场景 | `SC` | 继承分析方案，`SC-001` 起连续编号 |
| 测试点 | `TP` | 继承分析方案，`TP-001` 起连续编号 |
| 测试点明细 | `TP-*-*` | 继承分析方案，例如 `TP-001-001` |
| 测试设计项 | `TDI` | `TDI-001` 起全局连续编号 |

不得在主交付件中使用 `TD-*`、`TC-*`、`TCT-*`、`TI-*`、`ITP-*` 或 `ITDI-*` 作为编号体系。

## 测试设计项字段

每个测试点明细下必须使用固定表格：

```markdown
| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-001 | <代表性条件、数据、状态或组合> | <明确预期结果或待人工分析确认> |
```

| 字段 | 要求 |
|---|---|
| 测试设计项 ID | 使用 `TDI-001` 形式，全局连续编号 |
| 条件/数据/状态/组合 | 说明覆盖该测试点明细的代表性条件、数据、状态或组合，不写步骤 |
| 预期结果 | 明确、简短、可由需求/设计方案支撑；依据不足时写 `待人工分析确认` |

## 粒度规则

- 测试点明细回答“这个测试点下有哪些规则分支或行为分支”。
- 测试设计项回答“这个分支用哪些代表性条件、数据、状态或组合覆盖”。
- 一个测试点明细至少应有一个测试设计项。
- 如果多个输入取值代表同一等价类、同一业务判定和同一风险，可合并为一个测试设计项。
- 如果输入取值代表不同边界、不同错误类型、不同状态迁移、不同权限判定或不同接口契约，应拆成多个测试设计项。
- 测试设计项不应包含前置步骤、点击路径、接口调用脚本、SQL、自动化断言或执行数据清单。

## 示例

```markdown
### SC-001 订单下发

#### TP-001 验证下发订单 ID 长度规则

##### TP-001-001 下发订单 ID 满足长度要求

- 测试点详情：验证下发订单 ID 符合需求定义的长度规则时，系统能够正常识别并处理订单下发请求。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-001 | 下发订单 ID 总长度等于 13 位 | 下发成功 |

##### TP-001-002 下发订单 ID 不满足长度要求

- 测试点详情：验证下发订单 ID 不符合需求定义的长度规则时，系统能够拦截或拒绝订单下发请求。

| 测试设计项 ID | 条件/数据/状态/组合 | 预期结果 |
|---|---|---|
| TDI-002 | 下发订单 ID 总长度小于 13 位 | 待人工分析确认 |
| TDI-003 | 下发订单 ID 总长度大于 13 位 | 待人工分析确认 |
```

## 预期结果规则

预期结果不是完整测试用例里的长清单，只写设计项级简短判定。

适合写入：

- 下发成功。
- 下发失败。
- 订单取消成功，订单状态更新为已取消。
- 请求被拒绝，返回需求或设计方案明确的错误码。
- 不生成重复支付记录。
- 待人工分析确认。

必须写 `待人工分析确认` 的情况：

- 需求和设计方案没有说明错误提示。
- 需求和设计方案没有说明错误码。
- 需求和设计方案没有说明失败后的状态变化。
- 需求和设计方案没有说明接口返回内容、消息发送结果或数据记录变化。
- 需求和设计方案存在冲突，无法确定哪个结果应作为判定依据。

不适合写入：

- 具体操作步骤。
- 完整测试数据表。
- 接口调用代码或自动化断言脚本。
- 编造出来的错误码、提示文案、状态枚举、接口字段或数据库字段。
- “按需求”“同上”“见设计方案”等非自包含占位。

## 禁止项

- 不输出前置步骤、测试步骤、操作步骤或自动化脚本。
- 不使用旧版主交付件字段作为主输出表头；字段禁用清单以 `bin/lint-test-design-solution.py` 为准。
- 不设置 `未明确规则` 章节。
- 不设置独立待确认信息清单。
- 不把“正常/异常/校验通过/功能正确”作为测试设计项主体。
- 不编造需求或设计方案没有给出的阈值、状态、错误码、错误提示、接口路径或业务规则。
