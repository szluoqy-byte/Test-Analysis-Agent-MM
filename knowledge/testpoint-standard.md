# 测试点标准

## 定义

测试点是对验证特性的细化，用直观、明确、无歧义的语言，描述被测对象在特定场景下的某一功能、规则或行为。测试点不是测试用例。

## 测试点必须包含

- ID。
- 模块。
- 验证目标。
- 类型。
- 使用的方法。
- 需求依据。
- 级别。
- 风险或备注。

## 测试点不得包含

- 前置条件。
- 分步骤操作。
- 具体测试数据清单。
- 完整预期结果。
- 自动化代码。

## 标准类型

以下列表是唯一标准取值，输出中的 `类型` 必须从这里选择：

- 功能正确性
- 业务规则
- 异常容错
- 边界值
- 状态迁移
- 权限角色
- 数据一致性
- 接口契约
- 兼容性
- 性能容量
- 安全风控

类型的适用信号和常见分析方法如下：

| 类型 | 适用信号 | 常见方法 |
|---|---|---|
| 功能正确性 | 主行为、可观察结果、核心功能路径 | 需求可测性、场景流、风险驱动 |
| 业务规则 | 条件、限制、优先级、互斥、默认规则 | 决策表、等价类、风险驱动 |
| 异常容错 | 失败、超时、重试、回滚、中断恢复 | 场景流、状态迁移、数据一致性 |
| 边界值 | 阈值、数量、金额、时间、长度、枚举 | 边界值、等价类 |
| 状态迁移 | 生命周期、审批流、终态、重复事件 | 状态迁移 |
| 权限角色 | 角色、租户、归属、数据范围、审批权限 | 权限矩阵、安全风控 |
| 数据一致性 | 多对象变更、缓存、统计、搜索、日志、副作用 | 数据一致性、场景流 |
| 接口契约 | API、字段、响应、错误码、回调、幂等 | 接口契约 |
| 兼容性 | 版本、平台、渠道、开关、配置组合 | 组合兼容 |
| 性能容量 | 并发、批量、吞吐、容量、耗时边界 | 风险驱动、边界值 |
| 安全风控 | 越权、隐私、敏感操作、风控策略 | 风险驱动、权限矩阵 |

## 标准方法

以下列表是唯一标准取值，输出中的 `方法` 必须从这里选择：

- 风险驱动
- 需求可测性
- 边界值
- 等价类
- 状态迁移
- 决策表
- 场景流
- 权限矩阵
- 接口契约
- 数据一致性
- 组合兼容
- 错误推测

方法的用途和输出证据要求如下：

| 方法 | 用途 | 输出应体现 |
|---|---|---|
| 风险驱动 | 识别高损失、高概率或高回归价值区域 | 风险原因、建议级别、优先覆盖对象 |
| 需求可测性 | 判断需求是否可验证 | 可验证对象、缺失条件、待确认问题 |
| 边界值 | 覆盖边界点和边界两侧 | 边界内、边界点、边界外 |
| 等价类 | 用代表性类别替代穷举 | 有效类、无效类、默认类、特殊类 |
| 状态迁移 | 覆盖状态对象的合法和非法变化 | 源状态、事件、目标状态、非法迁移、终态 |
| 决策表 | 覆盖多条件组合和结果 | 条件组合、动作/结果、默认或冲突分支 |
| 场景流 | 覆盖主流程、备选流程和异常流程 | 参与方、关键路径、中断恢复 |
| 权限矩阵 | 覆盖角色、资源、动作和范围 | 允许/拒绝关系、越权风险 |
| 接口契约 | 覆盖请求、响应、错误和兼容契约 | 字段、错误码、幂等、超时、回调 |
| 数据一致性 | 覆盖数据对象和副作用一致性 | 主数据、派生数据、缓存、日志、补偿 |
| 组合兼容 | 覆盖多因子交互和兼容关系 | 因子、取值、关键组合、不兼容组合 |
| 错误推测 | 用常见缺陷模式补充风险覆盖 | 失败模式、触发条件、确认问题 |

## 类型与方法选择规则

- `类型` 描述测试点要验证的质量维度；`方法` 描述该测试点如何被分析出来。二者可以不同。
- 同一测试点只填写一个主类型和一个主要方法；多个方法共同支撑时，在方法证据摘要中关联。
- 如果需求触发多个方法，优先选择能解释该测试点核心风险的方法。
- `错误推测` 只能补充风险覆盖，不能替代需求依据；缺少依据时标记为风险确认点或待确认问题。

## 粒度示例

- 过粗：`验证登录功能正常`。
- 合适：`验证登录表单在密码错误场景下的登录失败处理和失败提示符合需求`。
- 过细：`输入 abc 点击登录检查提示`。
- 方法可见：`方法=决策表`，`测试点=验证不同会员等级与优惠券状态组合下的优惠适用规则`。

## 粒度判定

| 粒度 | 特征 | 处理 |
|---|---|---|
| 过粗 | 只写功能名或“正常/正确”，无法看出场景和验证特性 | 拆成对象、场景和规则 |
| 合适 | 一个被测对象、一个关键场景、一类验证特性 | 保留 |
| 过细 | 只因具体输入值、按钮或执行动作不同而拆分 | 合并为边界、等价类或场景点 |
| 混杂 | 同时覆盖多个模块、角色、接口或风险类型 | 按主要对象或风险拆分 |

## 需求依据规则

- 优先使用需求标题、规则句、表格行、接口字段或状态描述。
- 依据不能只写“需求文档”“业务规则”“见上文”。
- 如果测试点来自历史缺陷或通用缺陷模式，必须标记为风险确认点，并说明当前需求是否有支撑。
- 如果依据不足但风险重要，输出待确认问题，不把推测写成已确认规则。

## 反例库

| 问题 | 反例 | 修正方向 |
|---|---|---|
| 过粗 | `验证订单功能正常` | 明确被测对象、场景和验证特性 |
| 过细 | `输入 100 元点击提交检查结果` | 合并为金额边界或等价类测试点 |
| 用例化 | `先登录，再进入订单页，点击取消按钮` | 去掉步骤，描述验证目标 |
| 无依据 | `验证管理员可以强制取消所有订单` | 如果需求未说明，改为待确认问题 |
| 方法不匹配 | `类型=权限角色，方法=边界值` | 按实际分析方法填写权限矩阵 |
| 风险备注空泛 | `风险较高` | 说明资损、越权、不可逆、数据一致性等原因 |

## 表达结构

测试点文本优先使用以下结构：

```text
验证 <被测对象> 在 <特定场景> 下的 <某一功能/规则/行为> 是否符合需求
```

描述约束：

- 被测对象：具体到功能组件、业务对象、接口、状态对象或数据对象，避免只写系统名。
- 场景：说明触发条件、用户角色、状态、输入域、流程分支、异常条件或兼容环境。
- 验证特性：说明要验证的功能、业务规则、状态迁移、契约、权限或数据一致性。
- `测试点`：用自然语言把被测对象、场景和验证特性组合成无歧义验证目标。

## ID 与级别

- ID 格式：`TP-001`、`TP-002`，按顺序递增。
- 级别取值：`Level 0`、`Level 1`、`Level 2`、`Level 3`、`Level 4`。

## 级别定义

本系统不生成测试用例；以下定义沿用测试用例执行分级语义，映射为测试点后续转用例、版本验证和回归选择时继承的重要度。

- `Level 0`：核心。最核心的功能用例，建议每个转测试的版本都验证；执行失败意味着版本核心功能受损，没有继续验证的价值。
- `Level 1`：关键。涉及系统特性的关键功能、关键可靠性等内容的用例，建议每个迭代验证；执行失败即特性内某个关键功能点测试出现阻塞问题。
- `Level 2`：重要。覆盖系统所有重要功能的用例，建议 TR 点或对外发布版本进行完整验证，以保障系统功能正常实现。
- `Level 3`：一般。版本全量测试较为完整的测试用例，建议版本变更较大、需要全量验证覆盖时，根据版本修改点涉及范围，选择变更较大的特性相关部分或全部用例作为回归范围。
- `Level 4`：生僻。对于较生僻的应用场景和预置条件，是版本不常用场景的用例，建议新特性首次验证使用；验证通过后，大多数情况不需要回归执行。
