# 基于风险的测试设计

## 方法定义

基于风险的测试设计根据失败概率、业务影响、可恢复性、用户影响范围和历史缺陷情况，决定测试深度、标题项等级、覆盖优先级和补充场景。它是上层策略，通常叠加在基于规格的主模式之上。

风险设计不直接替代判定表、状态转换或场景测试；它决定哪些规则必须更深、更早、更严格地测。

## 适用场景

- 资金、安全、合规、隐私、权限、审计。
- 不可逆操作，例如删除、结算、支付、发放、关闭。
- 高用户影响或核心主链路。
- 历史高发缺陷或线上事故区域。
- 失败后难恢复、难发现或影响扩散快的功能。

## 风险评估维度

| 维度 | 判断问题 |
|---|---|
| 业务影响 | 失败是否影响资金、客户、合规或核心流程 |
| 发生概率 | 该场景是否复杂、变更多、历史缺陷多 |
| 可检测性 | 失败是否容易被发现 |
| 可恢复性 | 失败后是否能回滚、补偿或修复 |
| 影响范围 | 影响单用户、批量用户还是全局系统 |
| 安全合规 | 是否涉及越权、敏感数据、审计责任 |

## 风险审视原则

- 风险优先：高损失、不可逆、权限敏感、数据敏感行为需要更强覆盖。
- 依据优先：风险标题项必须追踪到需求陈述、memory 或明确的风险确认点。
- 异常优先：不能只覆盖主流程，还要覆盖失败、超时、重试、回滚、重复、空值和未授权路径。
- 状态优先：生命周期对象要检查合法迁移、非法迁移、重复触发和终态约束。
- 数据一致性优先：关注数据创建、更新、删除、同步、回滚、可见性和审计。
- 权限优先：角色、数据范围、归属关系、租户隔离和默认权限是高风险区域。
- 不脑补：需求不明确时输出待确认问题，不把猜测混入已确认标题项。

## 风险评分启发

评分只用于辅助排序和定级，不替代需求依据。若风险来自通用经验而非需求或 memory，应标记为风险确认点。

| 分数 | 判定 |
|---|---|
| 0 | 无明显风险或仅展示影响 |
| 1 | 单一低损失影响，可快速恢复 |
| 2 | 影响常用路径、重要数据或关键角色 |
| 3 | 影响核心链路、资损、越权、不可逆或外部客户 |

| 总分 | 建议等级 |
|---|---|
| 8 分及以上，或任一维度为 3 且涉及核心链路 | `Level 0` |
| 5 到 7 分，或任一维度为 3 | `Level 1` |
| 3 到 4 分 | `Level 2` |
| 1 到 2 分 | `Level 3` |
| 0 分且低频或生僻 | `Level 4` |

## 设计步骤

1. 识别测试点的风险对象和失败后果。
2. 判断风险等级并映射标题项等级。
3. 选择主规格模式生成基础标题项。
4. 对高风险点补充以下场景：
   - 主路径成功。
   - 关键异常拦截。
   - 边界和临界条件。
   - 权限和防护。
   - 幂等、补偿、审计。
5. 调整标题项优先级和覆盖深度。
6. 对无法可靠验证的高风险信息生成待确认问题。

## 标题项派生规则

| 风险类型 | 补充标题项方向 |
|---|---|
| 资金风险 | 金额边界、重复扣款、退款补偿、审计记录 |
| 权限风险 | 越权访问、角色切换、租户隔离、数据归属 |
| 合规风险 | 必填留痕、审批链路、敏感数据展示 |
| 不可逆操作 | 二次确认、撤销限制、误操作防护 |
| 高用户影响 | 降级、回滚、批量失败、通知 |
| 历史高发 | 回归标题项、异常保护、日志追踪 |

## 等级映射

| 风险判断 | 建议等级 |
|---|---|
| 失败会导致版本核心功能受损，且没有继续验证价值 | Level 0 |
| 失败会阻塞特性内关键功能、关键可靠性或关键业务链路 | Level 1 |
| 失败会影响系统重要功能，需要在 TR 点或对外发布版本完整验证 | Level 2 |
| 失败影响一般功能，适合在版本变更较大或全量验证时纳入回归 | Level 3 |
| 失败只影响低频应用场景或特殊预置条件，适合新特性首次验证后按需回归 | Level 4 |

## 等级调整规则

- 需求涉及资金、权限、数据删除、不可逆状态、跨系统回调时，至少评估为 `Level 1`，除非需求明确说明影响极低。
- 同时涉及核心链路和不可逆、资损、越权风险时，优先评估为 `Level 0`。
- 只有用户体验、展示、低频配置且失败可快速恢复时，才考虑 `Level 3` 或 `Level 4`。
- 覆盖支付、结算、库存、权限核心隔离、审批发布等核心链路时，至少上调到 `Level 1`。
- 涉及跨系统回调、异步最终一致、批量不可逆操作时，至少上调到 `Level 1`。
- 同时影响多个用户、多个租户或外部客户时，至少上调到 `Level 1`。
- 历史缺陷或 memory 中确认过反复出现的问题，可上调一级。
- 缺少日志、告警、对账或恢复信号且失败难以恢复时，可上调一级。
- 仅影响文案、展示排序、低频配置且可快速恢复时，可下调到 `Level 3` 或 `Level 4`。
- 需求明确说明为实验性、灰度小流量且有关闭开关时，可下调一级，但仍需覆盖关闭和回滚。
- 风险只来自通用缺陷模式而当前需求没有支撑时，不直接上调；写为风险确认点或待确认问题。

## 数量控制

- 高风险测试点可以从一个测试点派生多条标题项。
- 低风险测试点不因为风险模式叠加而扩大标题项数量。
- 风险补充标题项必须有独立失败后果，不能只是换个名称。
- 如果风险只能通过监控或审计验证，应在判定关注中明确观察对象。

## 输入条件与数据依赖关注

- 准备高风险对象，例如金额、权限、敏感数据、批量数据。
- 明确操作是否可逆，是否需要二次确认。
- 准备审计、日志或补偿记录的观察入口。

## 标题项生成关注

- 覆盖真实风险触发动作。
- 对不可逆操作，明确确认或取消动作。
- 对权限风险，使用不同角色或租户触发。
- 对资金风险，关注重复、边界和失败恢复。

## 判定关注

- 风险被阻断或被正确控制。
- 数据不被破坏、不重复、不泄露。
- 审计、日志、通知和补偿记录完整。
- 失败时系统保持安全状态。
- 成功时关键业务结果准确。

## 常见误区

- 把“高风险”只体现为高等级，不增加覆盖深度。
- 只测成功路径，忽略防护、审计和补偿。
- 生成大量低价值风险标题项，挤占核心场景。
- 未说明风险失败后果，导致等级缺乏依据。

## 标题项示例

| 风险信号 | 标题项建议 | 判定关注 |
|---|---|---|
| 资金 | 验证支付请求重复提交时不会重复扣款 | 扣款幂等且有审计记录 |
| 权限 | 验证无权限用户访问他人订单时被拦截 | 数据不泄露且记录访问失败 |
| 不可逆 | 验证删除关键数据前系统要求二次确认 | 取消确认时数据保持不变 |
