# 测试用例公共写作标准

本文定义所有 `test-design-solution.json` 中 `TC-*` 都必须遵守的公共写作规范。GUI、API、CLI 等执行形态差异化要求由 `knowledge/test-case-writing-styles/` 补充；差异化风格不得放宽本文的公共约束。

本文示例只说明字段写法，不构成业务事实、接口契约、页面结构、命令名称、测试数据或预期结果依据。

## 基本原则

- 风格一致：同一方案内的标题、前置条件、测试数据、步骤动作、步骤预期和最终预期应使用一致的表达方式。
- 用词一致：同一对象、角色、状态、接口、页面、字段或命令在同一 run 中应使用同一名称。
- 精确：动作应说明执行者、动作、对象和参数；预期应说明观察对象、属性和期望值或期望方向。
- 简洁：用例只保留执行和判定所必需的信息，不写产品常识、测试指导书细节或无关说明。
- 易懂：优先从测试执行者、用户、外部调用方或测试工具视角描述动作。
- 易确认：预期必须可观察、可判定，不依赖执行者自行猜测。

## title

- 标题应表达“对象 + 条件/动作 + 预期方向”，具体到一个可独立执行和判定的测试实例。
- 不写抽象标签，例如“有效金额测试”“异常场景测试”“接口测试”。
- 不把多个互斥条件合并到一个标题中，例如“金额为空/超长/非法字符校验”应拆为多个 TC。

## preconditions[]

- 写执行前必须已经满足的环境、账号、角色、权限、配置、依赖服务和数据状态。
- 前置条件只写起点状态，不写执行步骤、系统处理结果或最终断言。
- 如果输入依据不足，使用稳定数据槽位或 `待人工确认`，不得编造真实账号、状态、配置或生产数据。

## testData[]

- 每项使用 `{name, value, description}`。
- `name` 写字段名、参数名、控件标签、命令参数、配置项或稳定数据槽位。
- `value` 写具体值或稳定数据槽位；不得只写“有效值”“非法值”“错误数据”。
- `description` 写该值的业务含义、等价类、边界、枚举、状态或异常类型。
- 多个互斥输入条件不得塞进同一个 TC 的 `testData[]`；应拆成独立 TC。

## steps[].action

- 只写用户、测试人员、外部调用方或测试工具可执行的动作或取数动作。
- 动作表达优先使用“操作者/工具 + 动作 + 对象 + 参数”的结构。
- 不写系统判断、系统处理、系统返回、系统取消、系统释放、系统写入、检查项、断言项或观察结论。
- 不使用“执行操作”“进行处理”“完成测试”“检查结果”这类无法执行或无法定位的泛化动作。
- 需要验证响应体、数据库、消息、日志、文件或领域事件时，action 写“调用/查询/读取/拉取/订阅/打开/执行”等取数动作，具体检查写入同一步 `expected`。
- 重复步骤只能用于同一测试实例内的轮询、重试、分页或批量项处理；如果重复代表多组替代数据、多个角色、多个状态或多条独立路径，必须拆成独立 TC。

## steps[].expected

- 写当前步骤完成后可观察、可判定的结果。
- 预期表达优先使用“观察/检查对象 + 属性/字段/状态 + 期望值或期望方向”的结构。
- 系统行为、状态变化、数据写入、响应字段、页面提示、日志内容、消息事件和文件变化都应写入 `expected`。
- 不写“正常”“正确”“符合预期”“校验通过”这类无可判定对象的结论。
- 如果输入没有说明具体错误码、提示文案、状态值或输出文本，不补造具体值，只写输入可支撑的保守预期。

## expectedResult

- 写 TC 的最终业务判定或最终契约判定，不重复枚举所有步骤。
- 必须有当前用户指令、rules、需求、设计、分析方案、动态来源或可直接推出的业务不变量支撑。
- 依据不足时使用保守预期，例如“请求被拒绝，系统不产生成功态数据变更”。

## sourceRefs[]

- 来源引用必须能追溯到需求、设计、分析方案、rules、动态来源或用户明确指令。
- `description` 写依据摘要，不写生成过程说明。
- 不得用风格文件中的示例作为业务依据。

## 表达质量要求

### 语法表达

- 操作类内容写入 `steps[].action`，表达为可执行动作，例如“测试人员调用接口=POST /path；Body.amount=1000.00”。
- 赋值类内容通常写入 `preconditions[]` 或 `testData[]`，表达为对象、属性和取值，例如“配置项 roaming_limit=ENABLE”。
- 检查类内容写入 `steps[].expected` 或 `expectedResult`，不得单独写成 action。
- 重复类内容只在同一实例内确有轮询、重试、分页或批量项处理时使用，并应明确重复范围和退出条件；否则拆分 TC。

### 用词一致

- 优先使用需求、设计、rules、分析方案、项目词库或动态来源中的术语。
- 同一对象不得在同一方案中混用多个同义词，例如同一对象不应同时写成“手机”“移动台”“移动终端”，除非输入明确区分。
- 如果存在项目级词库或命名约束，以可见 project knowledge/rules 为准。
- 不自行创造缩写、别名或产品术语。

### 精确性

- 动作必须让执行者明确知道做什么、对哪个对象做、使用什么参数或值。
- 预期必须让执行者明确知道观察哪个对象、哪个字段/属性/状态，以及期望值或期望方向。
- 不写 `设置功能开关`、`检查资源没有泄露` 这类缺少对象、取值或观察方式的描述。
- 当输入只说明验证目标但缺少执行细节时，用稳定槽位或 `待人工确认` 表达缺口，不补造具体命令、控件、接口或字段。

### 简洁性

- 单个 TC 的步骤应保持简洁，通常不超过 7 步；超过 7 步时应优先检查是否混入多个独立路径、准备过程或冗余指导。
- E2E 或 GUI 主流程如确有必要可以超过 7 步，但每一步都必须是完成该测试实例所必需的动作或观察点。
- 不把产品基础知识、测试工具计算过程、测试指导书详细过程或无关背景写进 TC。
- 如果某个复杂准备动作已有测试指导书、脚本或环境约定支撑，可在前置条件中用稳定引用表达，不展开全部细节。

### 易懂性

- 优先从测试执行者、用户、外部调用方或测试工具视角描述动作。
- 不优先使用底层消息名、协议字段或内部缩写替代用户可理解动作，除非当前 TC 明确是 API、协议或命令行契约测试。
- 对 API/CLI 专项用例，可以保留技术字段和参数，但动作主体仍必须清楚说明由谁或什么工具执行。

### 易确认性

- 预期必须写清检查对象、字段/属性/状态和期望值或期望方向。
- 不写 `话单正确`、`消息流程正确`、`接口正常`、`结果正确` 这类无法直接判定的描述。
- 如果具体字段值或输出内容缺少依据，写输入可支撑的保守预期或 `待人工确认`，不得编造。

## 禁止项

- 不编造业务事实、接口路径、字段、状态、角色、阈值、错误码、错误提示、页面控件、命令参数或生产数据。
- 不输出自动化脚本、SQL 修改脚本或平台导入文件。
- 不把同一 TC 写成多个互斥路径、多个角色切换、多个状态切换或多组替代输入的集合。
