# 测试分析核心方法论

本文档是本 Agent 的测试分析核心事实源，统一定义分析边界、稳定术语、层级关系、分析维度和主交付件落点。它用于指导 `requirement-testability`、`testing-method-router`、专项分析 skill、`testpoint-generation`、`testcase-title-outline-generation` 和质量门禁。

本 Agent 的主交付件是 `测试用例标题大纲`，输出结构固定为：

```text
需求 + 设计方案
  -> 测试场景
      -> 场景测试条件
      -> 测试点
          -> 测试用例标题项
```

本 Agent 不输出完整测试用例、前置步骤、测试步骤、完整预期结果或自动化脚本。

## 稳定术语

| 术语 | 含义 | 备注 |
|---|---|---|
| 需求文档 | 输入给 Agent 的 Markdown 产品、系统或业务需求说明 | 可以与设计方案一起输入 |
| 设计方案 | 可选输入，用于补充接口、字段、状态、权限、数据依赖、配置和非功能约束 | 不得编造缺失设计事实 |
| 需求依据 | 测试场景、测试点或标题项对应的需求标题、段落、表格行、规则或风险确认点 | 用于可追踪性 |
| 方法证据 | 专项测试方法分析后的 `ME-*` 证据摘要 | 用于证明测试理论被实际应用 |
| 记忆上下文包 | 每次分析前从长期 memory 和 project/personal 补充中筛选出的上下文摘要 | 写入 `outputs/runs/<run-id>/process/context-pack.md` |
| 测试场景 | 从需求和设计方案中识别出的业务使用、系统触发或专项质量验证情境 | 使用 `SC-*` |
| 场景测试条件 | 绑定在测试场景上的共用入口、角色、前置条件、数据因子和业务设计约束 | 服务后续标题项生成 |
| 测试点 | 场景下需要验证的规则、路径、风险、接口契约、状态或质量关注点 | 使用 `TP-*` 或 `ITP-*` |
| 测试用例标题项 | 由测试点结合设计模式派生出的标题级验证项 | 使用 `TCT-*` |

## 核心边界

| 阶段 | 回答的问题 | 主要产物 | 不做什么 |
|---|---|---|---|
| 测试分析 | 测什么、为什么测、覆盖哪些条件和风险 | 测试场景、场景测试条件、测试点、接口测试点、待确认问题 | 不写完整测试步骤、具体执行数据和完整预期结果 |
| 标题大纲生成 | 每个测试点应派生哪些测试用例标题项、依赖哪些输入条件和数据 | 测试用例标题项、输入条件与数据依赖、判定关注 | 不写完整测试步骤、完整预期结果和自动化脚本 |
| 执行级用例细化 | 怎么测、用哪些数据、步骤和预期来测 | 不由本 Agent 输出 | 不在本仓库维护执行级用例写作知识 |

## 层级边界

### 测试场景

测试场景应描述“谁/什么系统动作，在什么入口、流程或触发条件下，完成什么业务目标”。

合适的测试场景通常满足以下特征：

- 来源于需求中的业务流程、用户任务、系统触发、外部交互或端到端业务链路。
- 具有明确执行主体，例如用户、管理员、定时任务、外部系统或系统组件。
- 具有明确入口、流程或触发条件。
- 具有明确业务目标。
- 场景下的测试点能够共用主要入口、角色、前置条件、测试数据因子和业务设计约束。

如果执行主体、入口、业务目标或核心规则明显不同，应拆成不同测试场景。

### 场景测试条件

场景测试条件承载该场景下测试点共用的信息，适合包含：

- 场景入口/触发方式：页面路径、菜单入口、接口入口、任务触发方式。
- 执行用户/角色：用户、管理员、系统任务、外部系统或权限身份。
- 前置条件：场景级共用环境、配置开关、依赖服务、账号权限或数据准备方式。
- 测试数据因子：状态集合、枚举值、取值区间、字段约束、数据对象和会影响分支判断的数据因素。
- 业务设计约束：需求或设计文档已明确的业务规则、状态流转、权限限制、数量范围或处理原则。

场景测试条件不是完整测试用例的前置步骤，也不展开具体边界值、组合矩阵或状态迁移矩阵。

### 测试点

测试点应写到“要验证什么”的程度，不写成“怎么验证”。

测试点应满足：

- 挂在某个测试场景下。
- 表达一个明确的规则、风险、路径、条件或质量关注点。
- 可以引用场景测试条件中的业务设计约束、角色、状态和数据因子。
- 不展开具体执行路径、测试步骤、测试数据取值或完整预期结果。

测试点不应包含：

- 测试设计方法名称，例如边界值、判定表、状态转换、组合测试。
- 已展开的方法产物，例如边界值集合、组合矩阵、状态迁移矩阵。
- 具体操作步骤，例如“点击 A，再点击 B”。
- 完整预期结果。

### 测试用例标题项

测试用例标题项位于测试点之后，是标题级验证项，可以包含：

- 测试用例标题。
- 覆盖意图。
- 级别。
- 输入条件与数据依赖。
- 判定关注。
- 待确认信息。

标题项不应包含前置步骤、测试步骤、完整预期结果、具体执行数据表或自动化脚本。

当用户只需要“下发订单 ID 总长度为 13 位”“下发订单 ID 总长度为 10 位”这类粒度时，应输出为测试用例标题项，而不是完整测试用例。

## 粒度判断

| 判断问题 | 倾向层级 |
|---|---|
| 是否来自需求中的业务使用、系统触发或外部交互情境 | 测试场景 |
| 是否能说明执行主体、入口/触发方式和业务目标 | 测试场景 |
| 是否承载一组共用入口、角色、前置条件、数据因子和业务设计约束 | 场景测试条件 |
| 是否只表达一条需要验证的规则、风险、路径或条件 | 测试点 |
| 是否是一个标题级验证目标，并包含条件摘要和判定关注 | 测试用例标题项 |
| 是否已经写出具体数据、操作步骤和完整预期结果 | 不属于本 Agent 输出 |
| 是否只是一个按钮、菜单、字段或取值 | 通常不是场景，需归入约束、入口或数据因子 |

## 测试分析维度

| 分析维度 | 关注对象 | 典型方法/Skill | 主交付件落点 |
|---|---|---|---|
| 需求可测性 | 需求目标、验收标准、可观察结果、歧义和缺口 | `requirement-testability` | 需求信息、待确认信息、场景目标 |
| 风险与优先级 | 失败模式、影响范围、资损/越权/不可逆/历史缺陷 | `risk-based-test-analysis` | 级别、风险/备注、待确认信息 |
| 业务场景与流程 | 用户旅程、系统触发、主流程、备选流程、异常流程 | `scenario-flow-analysis` | `SC-*` 场景、场景入口/触发方式、场景目标 |
| 数据域与边界 | 金额、数量、时间、状态、枚举、格式、容量 | `boundary-equivalence-analysis` | 测试数据因子、业务设计约束、规则级测试点 |
| 业务规则组合 | 多条件、多角色、多状态、开关共同决定结果 | `decision-table-analysis` | 业务设计约束、规则组合测试点、待确认信息 |
| 状态与生命周期 | 初始状态、中间状态、终态、非法迁移、重试、超时、补偿 | `state-transition-analysis` | 测试数据因子、业务设计约束、状态规则测试点 |
| 权限与数据范围 | 角色、资源、动作、数据归属、租户、审批权限 | `permission-role-analysis` | 执行用户/角色、权限边界测试点、待确认信息 |
| 接口与契约 | API、字段、错误码、鉴权、幂等、回调、超时、版本兼容 | `interface-contract-analysis` | 接口测试清单、接口测试详情、接口补充说明 |
| 数据一致性 | 主数据、派生数据、缓存、统计、搜索、导出、日志、外部系统 | `data-consistency-analysis` | 数据因子、业务设计约束、数据一致性测试点 |
| 组合与兼容 | 平台、版本、配置、渠道、语言地区、feature flag | `combinatorial-compatibility-analysis` | 测试数据因子、兼容性场景、关键组合测试点 |
| 非功能质量属性 | 性能、可靠性、安全、易用性、服务化、部署 | `risk-based-test-analysis`、`testpoint-generation` | 场景测试类型、专项场景、指标/约束/待确认信息 |
| 经验与缺陷模式 | 历史缺陷、错误猜测、检查清单、缺陷分类 | `risk-based-test-analysis`、`knowledge/testcase-design-patterns/experience-based/error-guessing-checklist.md` | 风险/备注、补充测试点、待确认信息 |

## 方法与维度的关系

- 分析维度回答“这段需求从哪个角度需要被看见”。
- 测试方法回答“用什么分析手段识别测试条件和覆盖项”。
- 测试点回答“这个场景下要验证什么”。
- 测试用例标题项回答“围绕该测试点应该拆出哪些标题、依赖哪些条件、观察哪些判定方向”。

边界值、等价类、决策表、状态迁移等在业界常被称为测试设计技术；在本 Agent 中，它们只作为识别测试条件、覆盖项和标题拆分方向的分析手段。方法产物可以保留在过程报告中，但主交付件只呈现业务规则、数据因子、场景条件、验证目标、标题项和必要的数据依赖。

## 主交付件落点规则

| 分析发现 | 主交付件写到哪里 | 不应写成 |
|---|---|---|
| 业务目标和范围 | `需求信息`、`本次不覆盖内容` | 见原始需求 |
| 用户旅程、系统触发、跨系统流程 | `测试场景清单`、`场景入口/触发方式` | 点击路径步骤 |
| 角色、资源、权限边界 | `执行用户/角色`、权限测试点 | 账号级测试数据 |
| 状态集合、枚举、金额/数量/时间范围 | `测试数据因子` | 具体用例数据表 |
| 业务规则、异常处理、约束 | `业务设计约束`、测试点 | 判定表行、边界值清单 |
| 接口、字段、错误码、幂等、回调 | `接口测试清单`、`接口测试详情`、接口补充说明 | 具体请求报文步骤 |
| 未确认但影响设计的问题 | `待确认信息` | 当作已确认规则 |
| 高风险或历史缺陷启发 | `风险/备注`、待确认信息 | 编造需求没有的规则 |

## 常见误区

| 误区 | 问题 | 调整方式 |
|---|---|---|
| 把每条规则都写成测试场景 | 场景过细，无法承载共用约束 | 将规则放入同一业务场景下的测试点 |
| 先写一堆测试点再归类场景 | 场景来源被反转，容易脱离需求业务流程 | 先从需求识别场景，再拆测试点 |
| 测试点写成具体操作步骤 | 粒度过细，提前进入用例编写 | 上收为验证目标 |
| 测试点写成测试方法 | 混淆测试点分析和标题大纲生成阶段 | 测试点只写待验证规则，标题项设计模式由标题大纲生成阶段选择 |
| 场景测试条件缺少业务设计约束 | 后续标题项难以写出可判定关注 | 补充需求或设计文档已明确的规则、状态流转、权限限制或处理原则 |

## 质量要求

- 每个重要需求片段至少落到一个测试场景、接口对象、测试点或待确认问题。
- 每个必选分析维度要有方法证据、测试点承接或待确认问题解释。
- 主交付件必须自包含，不能要求后续细化时回读原始需求、过程报告、memory、context-pack 或内部 knowledge。
- 主交付件不能泄漏方法产物，例如边界值清单、等价类清单、判定表、组合矩阵或状态迁移矩阵。
- 待确认信息只保留会影响后续标题项理解、评审或细化的问题，已回答或低价值偏好问题不得保留。
