# 测试分析核心方法论

本文档是本 Agent 的测试分析核心事实源，统一定义分析边界、稳定术语、层级关系、分析维度和主交付件落点。它用于指导 `requirement-testability`、`testing-method-router`、专项分析 skill、`testpoint-generation`、`test-design-solution-generation` 和质量门禁。

本 Agent 的主交付件是 `测试设计方案`，输出结构固定为：

```text
需求 + 设计方案
  -> 测试场景
      -> 测试点
          -> 测试设计项
```

本 Agent 不输出完整测试用例、前置步骤、测试步骤、自动化脚本或执行数据清单。

## 稳定术语

| 术语 | 含义 | 备注 |
|---|---|---|
| 需求文档 | 输入给 Agent 的 Markdown 产品、系统或业务需求说明 | 可以与设计方案一起输入 |
| 设计方案 | 可选输入，用于补充接口、字段、状态、权限、数据依赖、配置和非功能约束 | 不得编造缺失设计事实 |
| 需求依据 | 测试场景、测试点或测试设计项对应的需求标题、段落、表格行、规则或风险确认点 | 用于可追踪性 |
| 方法证据 | 专项测试技术分析后的 `ME-*` 证据摘要 | 用于证明测试技术被实际应用 |
| 记忆上下文包 | 每次分析前从长期 memory 和 project/personal 补充中筛选出的上下文摘要 | 写入 `outputs/runs/<run-id>/process/context-pack.md` |
| 测试场景 | 从需求和设计方案中识别出的业务使用、系统触发或专项质量验证情境 | 使用 `SC-*` |
| 测试点 | 场景下需要验证的规则、路径、风险、接口契约、状态或质量关注点 | 使用 `TP-*` |
| 测试设计项 | 由测试点结合测试技术派生出的代表性条件、数据、状态或组合 | 使用 `TDI-*` |
| 预期结果 | 需求或设计方案明确支持的简短判定结果；依据不足时写 `待人工分析确认` | 不展开完整用例预期清单 |
| 测试技术 | 用于支持测试分析和测试设计的方法或启发，例如等价类、边界值、判定表、状态转换、错误推测和风险驱动 | 维护在 `knowledge/test-techniques/` |

## 主交付件缩写

主交付件只使用中文术语和固定缩写，不展开英文全名。

| 中文术语 | 固定缩写 | ID 规则 |
|---|---|---|
| 测试场景 | `SC` | `SC-001` 起连续编号 |
| 测试点 | `TP` | `TP-001` 起连续编号 |
| 测试设计项 | `TDI` | `TDI-001` 起全局连续编号 |

`TD-*`、`TC-*`、`TCT-*`、`TI-*`、`ITP-*`、`ITDI-*` 不作为主交付件编号体系使用。

## 核心边界

| 阶段 | 回答的问题 | 主要产物 | 不做什么 |
|---|---|---|---|
| Test Analysis 测试分析 | what to test：测什么、为什么测、覆盖哪些条件和风险 | 测试场景、测试点、方法证据、过程缺口候选 | 不写完整测试步骤、具体执行数据和测试设计项表 |
| Test Design 测试设计 | how to test this point：每个测试点用哪些代表性条件、数据、状态或组合覆盖 | 测试设计项、预期结果 | 不写完整测试步骤、自动化脚本和执行数据清单 |
| Test Technique 测试技术 | 用什么方法分析和设计 | 等价类、边界值、判定表、状态转换、风险驱动等方法证据 | 技术产物不直接泄漏到主交付件 |
| 执行级用例细化 | 怎么执行、用哪些数据、步骤和完整预期来测 | 不由本 Agent 输出 | 不在本仓库维护执行级用例写作知识 |

## 测试技术使用边界

测试技术可同时支持测试分析和测试设计，但两个阶段的产物不同：

| 测试技术使用位置 | 输入 | 输出 | 边界 |
|---|---|---|---|
| 测试分析层 | 需求片段、设计方案事实、context pack、触发信号 | 分析维度、测试技术路由、`ME-*` 方法证据、测试点候选、过程缺口候选 | 回答 what to test，不把边界值清单、判定表或状态矩阵直接写入主交付件 |
| 测试点生成层 | 方法证据、测试点候选、风险与设计事实 | 场景、`TP-*` 测试点 | 将技术产物上收为可理解的业务验证目标 |
| 测试设计层 | 场景化测试点、需求/设计事实、方法证据摘要 | `TDI-*` 测试设计项、预期结果 | 回答 how to cover，不生成执行步骤、自动化脚本或数据清单 |

## 层级边界

### 测试场景

测试场景应描述“谁/什么系统动作，在什么入口、流程或触发条件下，完成什么业务目标”。

合适的测试场景通常满足以下特征：

- 来源于需求中的业务流程、用户任务、系统触发、外部交互或端到端业务链路。
- 具有明确执行主体，例如用户、管理员、定时任务、外部系统或系统组件。
- 具有明确入口、流程或触发条件。
- 具有明确业务目标。
- 场景下的测试点能够共享主要入口、角色、业务对象或设计约束。

如果执行主体、入口、业务目标或核心规则明显不同，应拆成不同测试场景。

### 测试点

测试点应写到“要验证什么”的程度，不写成“怎么验证”。

测试点应满足：

- 挂在某个测试场景下。
- 表达一个明确的规则、风险、路径、条件或质量关注点。
- 可以引用场景说明中的业务设计约束、角色、状态和数据因子。
- 不展开具体执行路径、测试步骤、测试数据取值或完整预期结果。

测试点不应包含：

- 测试技术名称，例如边界值、判定表、状态转换、组合测试。
- 已展开的方法产物，例如边界值集合、组合矩阵、状态迁移矩阵。
- 具体操作步骤，例如“点击 A，再点击 B”。
- 完整预期结果。

### 测试设计项

测试设计项位于测试点之后，是代表性设计项，可以包含：

- 条件：字段长度、范围、枚举、格式、金额、数量、时间窗口。
- 数据：业务对象、数据依赖、主子关系、缓存/数据库一致性前提。
- 状态：订单状态、审批状态、任务状态、终态、非法迁移。
- 组合：角色 + 状态 + 配置、渠道 + 版本 + 开关、接口字段组合。

测试设计项不应包含前置步骤、测试步骤、接口调用代码、自动化脚本或执行数据表。

当用户只需要“下发订单 ID 总长度为 13 位”“下发订单 ID 总长度为 10 位”这类粒度时，应输出为测试设计项，而不是完整测试用例。

## 预期结果边界

预期结果只写设计级简短判定，不展开完整用例预期清单。

| 情况 | 写法 |
|---|---|
| 需求明确成功行为 | 写明确成功结果，例如“订单下发成功” |
| 需求明确失败行为 | 写明确失败结果，例如“订单下发失败” |
| 需求明确状态变化 | 写状态变化，例如“订单状态更新为已取消” |
| 需求明确错误码或提示 | 写明确错误码或提示 |
| 需求未说明错误提示、状态变化、错误码或返回内容 | 写 `待人工分析确认` |

不得为上述缺口新增 `未明确规则` 章节，也不得在主交付件创建待确认信息清单。

## 粒度判断

| 判断问题 | 倾向层级 |
|---|---|
| 是否来自需求中的业务使用、系统触发或外部交互情境 | 测试场景 |
| 是否只表达一条需要验证的规则、风险、路径或条件 | 测试点 |
| 是否表达代表性条件、数据、状态或组合 | 测试设计项 |
| 是否已经写出具体数据、操作步骤和完整预期结果 | 不属于本 Agent 输出 |
| 是否只是一个按钮、菜单、字段或取值 | 通常不是场景，需归入约束、入口、测试点或测试设计项 |

## 测试分析维度

| 分析维度 | 关注对象 | 典型测试技术/Skill | 主交付件落点 |
|---|---|---|---|
| 需求可测性 | 需求目标、验收标准、可观察结果、歧义和缺口 | `requirement-testability` | 需求范围、场景目标、过程缺口 |
| 风险与优先级 | 失败模式、影响范围、资损/越权/不可逆/历史缺陷 | `risk-based-test-analysis` | 测试点、关键测试设计项 |
| 业务场景与流程 | 用户旅程、系统触发、主流程、备选流程、异常流程 | `scenario-flow-analysis` | `SC-*` 场景、测试点 |
| 数据域与边界 | 金额、数量、时间、状态、枚举、格式、容量 | `boundary-equivalence-analysis` | 规则级测试点、边界类测试设计项 |
| 业务规则组合 | 多条件、多角色、多状态、开关共同决定结果 | `decision-table-analysis` | 规则组合测试点、组合类测试设计项 |
| 状态与生命周期 | 初始状态、中间状态、终态、非法迁移、重试、超时、补偿 | `state-transition-analysis` | 状态规则测试点、状态类测试设计项 |
| 权限与数据范围 | 角色、资源、动作、数据归属、租户、审批权限 | `permission-role-analysis` | 权限边界测试点、角色/数据范围设计项 |
| 接口与契约 | API、字段、错误码、鉴权、幂等、回调、超时、版本兼容 | `interface-contract-analysis` | 接口契约测试点、字段/错误/幂等设计项 |
| 数据一致性 | 主数据、派生数据、缓存、统计、搜索、导出、日志、外部系统 | `data-consistency-analysis` | 数据一致性测试点、数据依赖设计项 |
| 组合与兼容 | 平台、版本、配置、渠道、语言地区、feature flag | `combinatorial-compatibility-analysis` | 兼容性场景、关键组合设计项 |
| 非功能质量属性 | 性能、可靠性、安全、易用性、服务化、部署 | `risk-based-test-analysis`、`testpoint-generation` | 专项场景、指标/约束/设计项 |
| 经验与缺陷模式 | 历史缺陷、错误猜测、检查清单、缺陷分类 | `risk-based-test-analysis`、`knowledge/test-techniques/experience-based/error-guessing-checklist.md` | 风险测试点、经验补充设计项 |

## 主交付件落点规则

| 分析发现 | 主交付件写到哪里 | 不应写成 |
|---|---|---|
| 业务目标和范围 | `## 1. 需求范围` | 见原始需求 |
| 用户旅程、系统触发、跨系统流程 | `### 场景 SC-*` | 点击路径步骤 |
| 角色、资源、权限边界 | 场景说明、权限测试点、测试设计项 | 账号级测试数据 |
| 状态集合、枚举、金额/数量/时间范围 | 测试点、测试设计项 | 具体用例数据表 |
| 业务规则、异常处理、约束 | 测试点、测试设计项 | 判定表行、边界值清单 |
| 接口、字段、错误码、幂等、回调 | 接口相关场景/测试点/测试设计项 | 具体请求报文步骤 |
| 未确认但影响预期结果的问题 | 对应设计项 `预期结果 = 待人工分析确认` | 单独 `未明确规则` 章节 |
| 高风险或历史缺陷启发 | 测试点、关键测试设计项 | 编造需求没有的规则 |

## 常见误区

| 误区 | 问题 | 调整方式 |
|---|---|---|
| 把每条规则都写成测试场景 | 场景过细，无法承载共用约束 | 将规则放入同一业务场景下的测试点 |
| 先写一堆测试点再归类场景 | 场景来源被反转，容易脱离需求业务流程 | 先从需求识别场景，再拆测试点 |
| 测试点写成具体操作步骤 | 粒度过细，提前进入用例编写 | 上收为验证目标 |
| 测试设计项写成“验证功能正常” | 不能表达代表性条件、数据、状态或组合 | 改为具体条件，例如“订单 ID 总长度为 13 位” |
| 需求没有错误码却写具体错误码 | 编造业务事实 | 预期结果改为 `待人工分析确认` |

## 质量要求

- 每个重要需求片段至少落到一个测试场景、测试点、测试设计项或过程缺口。
- 每个必选分析维度要有方法证据、测试点承接或过程缺口解释。
- 主交付件必须自包含，不能要求后续细化时回读原始需求、过程报告、memory、context-pack 或内部 knowledge。
- 主交付件不能泄漏方法产物，例如边界值清单、等价类清单、判定表、组合矩阵或状态迁移矩阵。
- 主交付件不能出现 `未明确规则` 章节。
- 依据不足的预期结果必须使用 `待人工分析确认`。
