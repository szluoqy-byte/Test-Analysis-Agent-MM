# 测试分析核心方法论

本文档是本仓库的测试分析与测试设计核心事实源，统一定义分析边界、稳定术语、层级关系、分析维度和主交付件落点。它用于指导 `requirement-testability`、`testing-method-router`、专项分析 skill、`testpoint-generation`、`test-analysis-solution-generation`、`test-design-solution-generation` 和质量门禁。

本 Agent 的主交付件是 `测试分析方案`，输出结构固定为：

```text
需求 + 可选设计方案
  -> 测试场景
      -> 测试点
          -> 测试点明细
              -> 失败类型明细（仅非成功测试点明细）
```

`test-analysis-agent` 不输出 `TDI-*` 测试设计项；`test-design-agent` 输出 `TDI-*` 测试设计项，但不输出完整测试用例、前置步骤、测试步骤、自动化脚本或执行数据清单。非成功路径的第四层由 `TP-*-*` 测试点明细触发，不由 `TP-*` 测试点主题触发。

## 稳定术语

| 术语 | 含义 | 备注 |
|---|---|---|
| 需求文档 | 输入给 Agent 的 Markdown 产品、系统或业务需求说明 | 可以与设计方案一起输入 |
| 设计方案 | 可选输入，用于补充接口、字段、状态、权限、数据依赖、配置和非功能约束 | 不得编造缺失设计事实 |
| 需求依据 | 测试场景、测试点或测试点明细对应的需求标题、段落、表格行、规则或风险确认点 | 用于可追踪性 |
| 方法证据 | 专项测试技术分析后的 `ME-*` 证据摘要 | 用于证明测试技术被实际应用 |
| 记忆上下文包 | 每次分析前从长期 memory 和 project/personal 补充中筛选出的上下文摘要 | 写入 `outputs/runs/<run-id>/process/context-pack.md` |
| 测试场景 | 从需求和设计方案中识别出的业务使用、系统触发或专项质量验证情境 | 使用 `SC-*` |
| 测试点 | 场景下需要验证的规则、路径、风险、接口契约、状态或质量关注点 | 使用 `TP-*` |
| 测试点明细 | 测试点下的规则分支、路径分支、状态分支、权限分支、接口契约分支或风险分支 | 使用 `TP-*-*` |
| 失败类型明细 | 非成功测试点明细下的失败来源、失败类型或异常路径拆分 | 使用 `TP-*-*-*`，仅非成功测试点明细需要 |
| 预期结果 | 需求或设计方案明确支持的简短判定结果；依据不足时写 `待人工分析确认` | 不展开完整用例预期清单 |
| 测试设计项 | 测试设计层基于普通测试点明细或失败类型明细选择的代表性条件、数据、状态或组合 | 使用 `TDI-*`，由 `test-design-agent` 输出 |
| 测试技术 | 用于支持测试分析和测试设计的方法或启发，例如等价类、边界值、判定表、状态转换、错误推测和风险驱动 | 维护在 `knowledge/test-techniques/` |

## 主交付件缩写

主交付件只使用中文术语和固定缩写，不展开英文全名。

| 中文术语 | 固定缩写/ID | ID 规则 |
|---|---|---|
| 测试场景 | `SC` | `SC-001` 起连续编号 |
| 测试点 | `TP` | `TP-001` 起连续编号 |
| 测试点明细 | `TP-*-*` | 继承测试点 ID，例如 `TP-001-001` |
| 失败类型明细 | `TP-*-*-*` | 继承测试点明细 ID，例如 `TP-001-002-001` |
| 测试设计项 | `TDI` | `TDI-001` 起全局连续编号，仅用于测试设计方案 |

`TDI-*` 不作为测试分析方案编号体系使用；`TD-*`、`TC-*`、`TCT-*`、`TI-*`、`ITP-*`、`ITDI-*` 不作为本仓库主交付件编号体系使用。

## 核心边界

| 阶段 | 回答的问题 | 主要产物 | 不做什么 |
|---|---|---|---|
| Test Analysis 测试分析 | what to test：测什么、为什么测、覆盖哪些规则分支和风险 | 测试场景、测试点、测试点明细、非成功失败类型明细、方法证据、过程缺口候选 | 不写完整测试步骤、具体执行数据和测试设计项表 |
| Test Design 测试设计 | how to test this point：每个普通测试点明细或失败类型明细用哪些代表性条件、数据、状态或组合覆盖 | 测试设计项、设计级预期结果 | 不写完整测试步骤、自动化脚本和执行数据清单 |
| Test Technique 测试技术 | 用什么方法分析和设计 | 等价类、边界值、判定表、状态转换、风险驱动等方法证据 | 技术产物不直接泄漏到主交付件 |
| 执行级用例细化 | 怎么执行、用哪些数据、步骤和完整预期来测 | 不由本 Agent 输出 | 不在本仓库维护执行级用例写作知识 |

## 测试技术使用边界

测试技术可同时支持测试分析和测试设计，但两个阶段的产物不同：

| 测试技术使用位置 | 输入 | 输出 | 边界 |
|---|---|---|---|
| 测试分析层 | 需求片段、设计方案事实、context pack、触发信号 | 分析维度、测试技术路由、`ME-*` 方法证据、测试点候选、过程缺口候选 | 回答 what to test，不把边界值清单、判定表或状态矩阵直接写入主交付件 |
| 测试点生成层 | 方法证据、测试点候选、风险与设计事实 | 场景、`TP-*` 测试点 | 将技术产物上收为可理解的业务验证目标 |
| 测试分析方案生成层 | 场景化测试点、需求/设计事实、方法证据摘要 | `TP-*-*` 测试点明细、预期结果 | 识别分析分支，不生成 TDI、执行步骤、自动化脚本或数据清单 |
| 测试设计层 | 评审后的测试分析方案、需求/设计事实、测试技术 | `TDI-*` 测试设计项 | 由 `test-design-agent` 承接普通 `TP-*-*` 或失败类型 `TP-*-*-*`，不由测试分析方案输出 |

## 层级边界

### 测试场景

测试场景应描述“谁/什么系统动作，在什么入口、流程或触发条件下，完成什么业务目标”。

合适的测试场景通常满足以下特征：

- 来源于需求中的业务流程、用户任务、系统触发、专项质量目标或端到端业务链路。
- 具有明确执行主体，例如用户、管理员、定时任务、外部系统或系统组件。
- 具有明确入口、流程或触发条件。
- 具有明确业务目标。
- 场景下的测试点能够共享主要入口、角色、业务对象或设计约束。
- 每个测试场景都应包含一个 `E2E场景测试` 测试点，覆盖该场景端到端业务主流程能否按预期完整闭环。
- `E2E场景测试` 是独立同级测试点，不是该场景下其他测试点的容器；除主流程成功闭环明细外，其他规则、异常、接口、权限、状态、回滚或补偿关注点必须拆为同级 `TP-*`。
- 如果用户任务、需求或设计方案明确要求接口测试/API 契约覆盖，接口测试或集成覆盖场景可以成立；但不因正文只是出现接口路径就默认新增接口场景。
- 接口测试或集成覆盖场景下，非 E2E 的 `TP-*` 应先按接口、端点、消息、回调或集成点组织。契约维度如字段校验、响应结构、错误码、鉴权、幂等、超时和重试，挂在对应接口 `TP-*` 下作为测试点明细或失败类型明细。
- 跨多个接口共用的规则可以作为独立 `TP-*`，但标题必须说明适用范围，例如 `通用接口鉴权规则（适用于所有外部 API）`；不得输出“状态码规则”“字段校验”“鉴权规则”这类无法判断目标接口的泛化测试点。

### 测试点

测试点应写到“要验证什么”的程度，不写成“怎么验证”。

测试点应满足：

- 挂在某个测试场景下。
- 表达一个明确的规则、风险、路径、条件或质量关注点。
- 可以引用场景说明中的业务设计约束、角色、状态和数据因子。
- 不展开具体执行路径、测试步骤、测试数据取值或完整预期结果。

### 测试点明细

测试点明细位于测试点之后，是可评审的分析分支。

测试点明细可以表达：

- 规则分支：满足规则、不满足规则、缺失规则、冲突规则。
- 路径分支：主路径、备选路径、失败路径、默认路径。
- 状态分支：允许迁移、拒绝迁移、终态保护、重复事件。
- 权限分支：允许角色、拒绝角色、越权访问、数据归属边界。
- 接口契约分支：必填字段、字段规则、鉴权、错误返回、幂等、回调。
- 风险分支：资金损失、重复处理、审计缺失、外部依赖失败。

测试点明细不应包含：

- `TDI-*` 测试设计项。
- 具体代表性边界值、枚举取值或组合矩阵。
- 前置步骤、测试步骤、接口调用代码、自动化脚本或执行数据表。

如果用户只需要“下发订单 ID 总长度为 13 位”“下发订单 ID 总长度小于 13 位”这类粒度，应由 `test-design-agent` 输出为测试设计项；`test-analysis-agent` 应输出“下发订单 ID 满足长度要求”“下发订单 ID 不满足长度要求”。

### 失败类型明细

失败类型明细只在明确非成功聚合测试点明细下出现。判断是否新增第四层，看 `TP-*-*` 测试点明细是否是失败、拒绝、不允许、不满足、非法、无效、异常、错误、超时、越权、权限限制、依赖失败、状态不允许或重复处理失败等强失败分支，而不是看 `TP-*` 测试点主题。

“未注册”“未找到”“返回空列表”“count=0”“无记录”“回滚或补偿状态确认”这类弱结果分支，如果只表达一个可判定结果，不强制新增第四层；只有它们还需要继续区分不同失败来源、异常返回或处理类型时，才拆出失败类型明细。

失败类型明细可以按以下来源拆分：

- 业务逻辑失败，例如规则不满足、状态不允许或业务约束冲突。
- 系统交互失败，例如接口返回异常、消息投递失败或回调失败。
- 外部依赖失败，例如第三方不可用、超时或返回错误。
- 数据校验失败，例如字段缺失、格式非法、长度不满足或枚举无效。
- 权限控制失败，例如角色权限不足、数据归属不匹配或租户隔离。
- 数据一致性失败，例如幂等、重复请求、补偿、回滚或副作用异常。

失败类型明细仍属于测试分析层，不输出具体代表性输入值、边界值或组合；这些由 `test-design-agent` 输出为 `TDI-*`。

## 预期结果边界

预期结果只写分析级简短判定，不展开完整用例预期清单。

| 情况 | 写法 |
|---|---|
| 需求明确成功行为 | 写明确成功结果，例如“订单下发成功” |
| 需求明确失败行为 | 写明确失败结果，例如“订单下发失败” |
| 需求明确状态变化 | 写状态变化，例如“订单状态更新为已取消” |
| 需求明确错误码或提示 | 写明确错误码或提示 |
| 需求未说明错误提示、状态变化、错误码或返回内容 | 写 `待人工分析确认` |

不得为上述缺口新增 `未明确规则` 章节，也不得在主交付件创建待确认信息清单。

## 粒度判断

| 判断问题 | 倾向层级 |
|---|---|
| 是否来自需求中的业务使用、系统触发、跨系统业务流程或专项质量目标 | 测试场景 |
| 是否只表达一条需要验证的规则、风险、路径或条件 | 测试点 |
| 是否表达测试点下的可评审规则分支、路径分支、状态分支或风险分支 | 测试点明细 |
| 是否表达非成功测试点明细下的失败来源或失败类型 | 失败类型明细 |
| 是否表达代表性条件、数据、状态或组合 | 后续测试设计项 |
| 是否已经写出具体数据、操作步骤和完整预期结果 | 不属于本 Agent 输出 |

| 分析维度 | 关注对象 | 典型测试技术/Skill | 主交付件落点 |
|---|---|---|---|
| 需求可测性 | 需求目标、验收标准、可观察结果、歧义和缺口 | `requirement-testability` | 需求范围、场景目标、过程缺口 |
| 风险与优先级 | 失败模式、影响范围、资损/越权/不可逆/历史缺陷 | `risk-based-test-analysis` | 测试点、高风险测试点明细 |
| 业务场景与流程 | 用户旅程、系统触发、主流程、备选流程、异常流程 | `scenario-flow-analysis` | `SC-*` 场景、测试点、路径明细 |
| 数据域与边界 | 金额、数量、时间、状态、枚举、格式、容量 | `boundary-equivalence-analysis` | 规则级测试点、有效/无效/边界类明细 |
| 业务规则组合 | 多条件、多角色、多状态、开关共同决定结果 | `decision-table-analysis` | 规则组合测试点、允许/拒绝/默认/冲突明细 |
| 状态与生命周期 | 初始状态、中间状态、终态、非法迁移、重试、超时、补偿 | `state-transition-analysis` | 状态规则测试点、迁移类明细 |
| 权限与数据范围 | 角色、资源、动作、数据归属、租户、审批权限 | `permission-role-analysis` | 权限边界测试点、角色/数据范围明细 |
| 接口与契约 | API、字段、错误码、鉴权、幂等、回调、超时、版本兼容 | `interface-contract-analysis` | 接口契约分析候选、字段/错误/幂等分支 |
| 数据一致性 | 主数据、派生数据、缓存、统计、搜索、导出、日志、外部系统 | `data-consistency-analysis` | 数据一致性测试点、副作用和一致性明细 |
| 组合与兼容 | 平台、版本、配置、渠道、语言地区、feature flag | `combinatorial-compatibility-analysis` | 兼容性场景、关键组合风险明细 |
| 非功能质量属性 | 性能、可靠性、安全、易用性、服务化、部署 | `risk-based-test-analysis`、`testpoint-generation` | 专项场景、指标/约束明细 |
| 经验与缺陷模式 | 历史缺陷、错误猜测、检查清单、缺陷分类 | `risk-based-test-analysis`、`knowledge/test-techniques/experience-based/error-guessing-checklist.md` | 风险测试点、经验补充明细 |

## 主交付件落点规则

| 分析发现 | 主交付件写到哪里 | 不应写成 |
|---|---|---|
| 业务目标和范围 | `## 1. 需求范围` | 见原始需求 |
| 用户旅程、系统触发、跨系统流程 | `### SC-*` | 点击路径步骤 |
| 角色、资源、权限边界 | 场景说明、权限测试点、测试点明细 | 账号级测试数据 |
| 状态集合、枚举、金额/数量/时间范围 | 测试点、测试点明细 | 具体用例数据表 |
| 业务规则、异常处理、约束 | 测试点、测试点明细 | 判定表行、边界值清单 |
| 接口、字段、错误码、幂等、回调 | 作为接口契约分析信号进入主交付件生成流程 | 具体请求报文步骤 |
| 明确要求接口测试且存在多个接口/端点/集成点 | 接口测试或集成覆盖场景下，先按接口、端点或集成点生成 `TP-*`，再拆契约维度 | 把所有接口字段、状态码和鉴权混在一个泛化测试点下 |
| 未确认但影响预期结果的问题 | 对应叶子分析节点 `预期结果 = 待人工分析确认` | 单独 `未明确规则` 章节 |
| 高风险或历史缺陷启发 | 测试点、关键测试点明细 | 编造需求没有的规则 |
| 非成功分支的不同失败来源 | `TP-*-*` 下的 `TP-*-*-*` 失败类型明细 | 把所有失败混在一条明细或把 TP 写成非成功主题 |

## 常见误区

| 误区 | 问题 | 调整方式 |
|---|---|---|
| 把每条规则都写成测试场景 | 场景过细，无法承载共用约束 | 将规则放入同一业务场景下的测试点 |
| 先写一堆测试点再归类场景 | 场景来源被反转，容易脱离需求业务流程 | 先从需求识别场景，再拆测试点 |
| 测试点写成具体操作步骤 | 粒度过细，提前进入用例编写 | 上收为验证目标 |
| 测试点明细写成具体数据值 | 提前进入测试设计 | 上收为“满足/不满足某规则”这类分析分支 |
| 测试点明细写成“验证功能正常” | 不能表达规则分支或风险分支 | 改为具体分支，例如“订单 ID 满足长度要求” |
| 需求没有错误码却写具体错误码 | 编造业务事实 | 预期结果改为 `待人工分析确认` |

## 质量要求

- 每个重要需求片段至少落到一个测试场景、测试点、测试点明细或过程缺口。
- 每个必选分析维度要有方法证据、测试点承接或过程缺口解释。
- 主交付件必须自包含，不能要求后续细化时回读原始需求、过程报告、memory、context-pack 或内部 knowledge。
- 主交付件不能泄漏方法产物，例如边界值清单、等价类清单、判定表、组合矩阵或状态迁移矩阵。
- 主交付件不能出现 `TDI-*`、测试设计项表或 `未明确规则` 章节。
