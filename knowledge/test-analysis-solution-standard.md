# 测试分析方案标准

本文档定义 `test-analysis-agent` 的核心输出粒度：`测试分析方案`。它回答 what to test，产物停留在测试场景、测试点和测试点明细，不输出 `TDI-*` 测试设计项。

## 分层关系

```text
需求 + 可选设计方案
  -> 测试场景
      -> 测试点
          -> 测试点明细
              -> 失败类型明细（仅非成功测试点明细需要）
              -> 测试设计项（由 test-design-agent 输出）
                  -> 完整测试用例（不由本 Agent 输出）
```

## 核心定义

| 对象 | 定义 | 本 Agent 是否输出 |
|---|---|---|
| 测试场景 | 从需求和设计方案中识别出的业务使用、系统触发或专项质量验证情境 | 是 |
| 测试点 | 场景下需要验证的规则、路径、风险、接口契约、状态或质量关注点，回答 what to test | 是 |
| 测试点明细 | 测试点下可评审的规则分支、路径分支、状态分支、权限分支、接口契约分支或风险分支 | 是 |
| 失败类型明细 | 仅用于非成功测试点明细下，继续拆分不同失败来源、失败类型或异常路径 | 是，仅非成功分支需要 |
| 预期结果 | 需求或设计方案明确支持的简短判定结果；依据不足时固定写 `待人工分析确认` | 是 |
| 测试设计项 | 基于测试点明细选择代表性条件、数据、状态或组合，回答 how to test | 否 |
| 完整测试用例 | 可执行产物，包含前置步骤、测试步骤、测试数据和完整预期结果 | 否 |

## 术语与缩写

主交付件只使用中文术语和固定缩写，不展开英文全名。

| 中文术语 | 固定缩写/ID | ID 规则 |
|---|---|---|
| 测试场景 | `SC` | `SC-001` 起连续编号 |
| 测试点 | `TP` | `TP-001` 起连续编号 |
| 测试点明细 | `TP-*-*` | 继承测试点 ID，例如 `TP-001-001` |
| 失败类型明细 | `TP-*-*-*` | 继承测试点明细 ID，例如 `TP-001-002-001` |

不得在主交付件中使用 `TDI-*`、`TD-*`、`TC-*`、`TCT-*`、`TI-*`、`ITP-*` 或 `ITDI-*` 作为编号体系。

## 测试点明细字段

普通测试点明细必须使用标题和固定字段，不使用表格。

```markdown
##### TP-001-001 <测试点明细>

- 测试点详情：<说明该分支需要验证什么。>

- 预期结果：<明确预期结果或待人工分析确认>
```

| 字段 | 要求 |
|---|---|
| 测试点明细标题 | 使用 `TP-001-001` 形式，并以分析层分支命名 |
| 测试点详情 | 说明要验证的规则、路径、状态、权限、接口契约或风险，不写步骤 |
| 预期结果 | 明确、简短、可由需求/设计方案支撑；依据不足时写 `待人工分析确认` |

非成功测试点明细必须继续新增第四层，第四层才承载 `测试点详情` 和 `预期结果`：

```markdown
##### TP-001-002 <非成功测试点明细>

###### TP-001-002-001 <失败类型明细>

- 测试点详情：<说明该失败类型需要验证什么。>

- 预期结果：<明确预期结果或待人工分析确认>
```

## 粒度规则

- 测试点回答“这个场景下要验证哪类规则或行为”。
- 测试点明细回答“这个测试点下有哪些可评审的规则分支或行为分支”。
- 每个测试场景必须包含一个 `E2E场景测试` 测试点，用于覆盖该场景端到端业务主流程是否能够按预期完整闭环。
- 测试点明细不展开具体代表性数据、边界值、组合矩阵或执行数据。
- 如果某个分支只是具体输入值不同，应保留给后续测试设计项，不在测试分析方案中拆得过细。
- 如果不同分支有不同业务判定、权限判定、状态判定、接口契约或风险后果，应拆成不同测试点明细。
- 成功路径或普通规则分支停留在 `TP-*-*`，由该层直接承载 `测试点详情` 和 `预期结果`。
- 如果 `TP-*-*` 是非成功测试点明细，例如失败、拒绝、不允许、非法、异常、超时、越权、权限限制、依赖失败或重复处理失败，必须新增 `TP-*-*-*` 第四层。
- `TP-*-*-*` 用于拆分失败类型，按需覆盖业务逻辑、系统交互、外部依赖、异常返回、数据校验、权限控制、状态限制、接口契约和数据一致性等失败来源。
- 不把 `TP-*` 测试点本身定义为“非成功路径主题”；是否需要第四层由具体 `TP-*-*` 测试点明细决定。

## 示例

```markdown
### SC-001 订单下发

#### TP-001 E2E场景测试

##### TP-001-001 订单下发主流程成功闭环

- 测试点详情：验证订单下发场景的端到端主流程能够从请求接收到订单处理结果完成闭环。

- 预期结果：订单下发成功。

#### TP-002 验证下发订单 ID 长度规则

##### TP-002-001 下发订单 ID 满足长度要求

- 测试点详情：验证下发订单 ID 符合需求定义的长度规则时，系统能够正常识别并处理订单下发请求。

- 预期结果：下发成功。

##### TP-002-002 下发订单 ID 不满足长度要求

###### TP-002-002-001 下发订单 ID 长度小于规则要求

- 测试点详情：验证下发订单 ID 长度短于需求定义的长度规则时，系统能够识别为无效订单 ID 并拒绝处理订单下发请求。

- 预期结果：下发失败；具体错误处理待人工分析确认。

###### TP-002-002-002 下发订单 ID 长度大于规则要求

- 测试点详情：验证下发订单 ID 长度长于需求定义的长度规则时，系统能够识别为无效订单 ID 并拒绝处理订单下发请求。

- 预期结果：下发失败；具体错误处理待人工分析确认。
```

`test-design-agent` 可以在 `TP-002-002-001` 和 `TP-002-002-002` 下补充 `TDI-*`，例如缺 1 位、缺多位、多 1 位或多多位等代表性条件。`test-analysis-agent` 不输出这些设计项。

## 预期结果规则

预期结果不是完整测试用例里的长清单，只写分析级简短判定。

适合写入：

- 订单下发成功。
- 订单下发失败。
- 订单取消成功，订单状态更新为已取消。
- 请求被拒绝，返回需求或设计方案明确的错误码。
- 不生成重复支付记录。
- 待人工分析确认。

必须写 `待人工分析确认` 的情况：

- 需求和设计方案没有说明错误提示。
- 需求和设计方案没有说明错误码。
- 需求和设计方案没有说明失败后的状态变化。
- 需求和设计方案没有说明接口返回内容、消息发送结果或数据记录变化。
- 需求和设计方案存在冲突，无法确定哪个结果应作为判定依据。

不适合写入：

- 具体操作步骤。
- 完整测试数据表。
- 具体代表性边界值或组合矩阵。
- 接口调用代码或自动化断言脚本。
- 编造出来的错误码、提示文案、状态枚举、接口字段或数据库字段。
- “按需求”“同上”“见设计方案”等非自包含占位。

## 禁止项

- 不输出前置步骤、测试步骤、操作步骤或自动化脚本。
- 不输出 `TDI-*` 或 `测试设计项`。
- 不使用旧版主交付件字段作为主输出表头；字段禁用清单以 `bin/lint-test-analysis-solution.py` 为准。
- 不设置 `未明确规则` 章节。
- 不设置独立待确认信息清单。
- 不把测试技术名称直接塞进测试点明细，例如“边界值测试订单 ID”。
- 不把“正常/异常/校验通过/功能正确”作为测试点明细主体。
- 不编造需求或设计方案没有给出的阈值、状态、错误码、错误提示、接口路径或业务规则。
