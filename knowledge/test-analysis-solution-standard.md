# 测试分析方案标准

测试分析方案回答 what to test，只输出：

```text
测试场景 SC -> 测试点 TP
```

它不输出测试用例、测试数据、步骤或预期结果。

## 层级边界

| 层级 | 编号 | 定义 | 是否输出 |
|---|---|---|---|
| 测试场景 | `SC-*` | 业务场景树，最多 3 层，用于表达业务路径、角色路径、接口/集成路径或状态路径 | 是 |
| 测试点 | `TP-*` | 某个叶子场景下需要验证的规则、路径、状态、权限、接口契约或风险目标 | 是 |
| 测试用例 | `TC-*` | 可执行实例，包含前置、数据、步骤和预期 | 否 |

`SC-*` 示例：`SC-001`、`SC-001-001`、`SC-001-001-001`。非叶子场景只作为分组，只有叶子场景挂 `testPoints[]`。

`TP-*` 在 run 内全局唯一且增量稳定，不按场景重置。首次生成从 `TP-001` 开始；补充分析时保留既有编号，新 TP 从历史最大编号后追加，退役编号不复用。每个叶子场景必须包含 `E2E场景测试` 测试点。

生成过程必须先产出并评审 `process/scenario-tree.json`。该过程产物只包含冻结 SC 树，不得包含 `testPoints[]`；SC 通过 review 后，TP 阶段只能在既有叶子 SC 下填写 `process/test-point-slices/<SC-ID>.json`，不得反向改写 SC。

## 测试点字段

每个测试点至少包含：

```json
{
  "id": "TP-001",
  "title": "E2E场景测试",
  "objective": "验证该叶子场景端到端业务主流程是否完整闭环。",
  "basisRefs": [
    {"source": "requirements.md", "location": "章节", "description": "依据摘要"}
  ]
}
```

`objective` 必须说明要验证什么，不写具体执行步骤或最终预期。

测试技术和专项方法只作为生成参考，不进入主交付字段。不要为了贴合某个方法而输出 `methodRefs[]`；TP 是否成立只看需求、设计、规则、动态来源或明确风险依据是否能支撑。

## 粒度规则

- 场景用于组织业务路径；测试点用于表达验证目标；测试用例由设计阶段生成。
- 复杂业务路径优先拆分 SC 树，最多 3 层。
- 同一叶子场景下的 TP 应是同级验证目标，不把异常、接口、权限、状态、补偿等全部塞进 E2E。
- 接口/API 明确时，TP 标题应能定位接口、端点、消息、回调或集成点。
- 不同预期结果不要求在分析阶段拆出子层；具体预期由设计阶段 TC 承载。

## 禁止项

- 不输出 `TC-*`。
- 不输出 `expectedResult`、`preconditions`、`testData`、`steps`。
- 不输出 schemaVersion 2.0 之外的结构字段。
- 不输出 schemaVersion 2.0 之外的编号或术语。
- 不把测试点写成“验证功能正常”“异常流程覆盖”这类空泛表达。
- 不把测试点写成具体数据值或操作步骤。
