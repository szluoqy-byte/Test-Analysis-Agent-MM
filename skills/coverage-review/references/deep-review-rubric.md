# 深度语义评审与专家评分

本文件是 `coverage-review` 的私有参考。仅在用户明确要求深度评估、任务参数声明 deep review，或覆盖审查发现高风险但无法定性时使用；默认单次报告不执行专家评分。

## 1. 深度语义检查

### 目的

检查测试分析方案和测试设计方案是否真正支撑后续完整用例编写，并在过程报告中体现测试技术、风险分层和需求追踪，而不是只满足结构。

结构、编号、字段、禁用术语、Markdown 语法和固定章节不在本门禁中重复判断；这些规则以对应 lint 脚本和 `bin/check-artifact-consistency.py` 的结果为准。

### 语义检查项

- 必选测试技术是否落到测试分析方案中的场景、测试点或测试点明细，或是否有过程缺口解释。
- 必选测试技术是否有方法分析证据，或是否有过程缺口解释。
- 适用的测试分析维度是否落到主交付件，而不是只留在过程报告。
- 测试场景、测试点和测试点明细是否符合 `knowledge/test-analysis-solution-standard.md` 的层级边界；测试设计项是否符合 `knowledge/test-design-solution-standard.md` 的承接边界。
- 过程报告中的测试点类型和方法是否来自 `knowledge/testpoint-standard.md`。
- 过程报告与测试分析方案是否不冲突。
- 测试分析方案是否自包含，是否把后续测试设计必须知道的业务规则、状态集合、角色权限、接口契约和预期结果依据写入主交付件。
- 测试设计方案是否自包含，是否把完整用例细化必须知道的代表性条件、数据、状态、组合和预期结果写入主交付件。
- 适用 rules 是否被遵守；rules 与输入文档冲突时是否记录 rules 覆盖输入原因。
- `预期结果` 是否有需求/设计依据，依据不足时是否写 `待人工分析确认`。
- 主交付件是否没有 `未明确规则` 章节。
- 需求依据是否过于宽泛。
- 方法证据是否使用 `ME-*` 格式并关联 `TP-*` 或过程缺口。
- 质量门禁是否存在失败项。
- 深度评估开启时，专家评分是否达到 `10/12`，且任一维度不得为 `0`。

### 建议命令

```bash
bin/lint-test-analysis-solution.py ${PROJECT_ROOT}/outputs/runs/<run-id>/deliverables/test-analysis-solution.md
bin/lint-test-design-solution.py ${PROJECT_ROOT}/outputs/runs/<run-id>/deliverables/test-design-solution.md
bin/check-artifact-consistency.py ${PROJECT_ROOT}/outputs/runs/<run-id>
skills/coverage-review/scripts/semantic-testpoint-check.py ${PROJECT_ROOT}/outputs/runs/<run-id>/reports/test-analysis-report.md
```

`bin/smoke-test-analysis.py` 是框架回归和示例 fixture smoke 检查，不属于单次测试分析/测试设计方案的 review 阶段；只有修改 Agent、skill、knowledge、template、quality gate、bin 脚本或示例 fixture 时才需要运行。

上述命令只提供确定性结果。模型型语义检查不得再次逐条复核脚本已经输出通过的结构项。

### 失败条件

- 必选测试技术没有场景、测试点或测试点明细承接，且没有过程缺口解释。
- 必选测试技术没有方法证据，且没有过程缺口解释。
- 适用分析维度没有在需求范围、场景、测试点或测试点明细中体现。
- 测试分析方案把前置步骤、测试步骤、操作步骤或自动化脚本提前写入主交付件。
- 测试设计方案把前置步骤、测试步骤、操作步骤、执行数据清单或自动化脚本提前写入主交付件。
- 测试分析方案依赖“见原始需求”“见设计方案”“按需求实现”“同上”等泛化占位。
- 过程报告和测试分析方案中的测试点表达冲突。
- 质量门禁结果存在 `失败`。
- 适用 rules 未被执行，且没有当前用户明确指令覆盖说明。
- 深度评估开启时，专家评分低于通过线或存在 0 分维度。
- 需求没有说明错误提示、状态变化或错误码，但预期结果编造了具体值。

### 警告条件

- 测试点风险备注过于泛化。
- 需求依据只写“需求文档”等宽泛来源。
- 测试点类型和测试技术明显不匹配。
- 大量测试点明细预期结果为 `待人工分析确认`，说明需求或设计方案判定依据不足。

## 2. 专家评审评分标准

覆盖审查阶段使用本评分标准。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 需求理解 | 遗漏主要模块 | 捕获模块但遗漏规则 | 捕获模块、规则、角色、状态、数据和接口 |
| 测试技术应用 | 主要是泛化测试点 | 使用了部分技术 | 技术选择合适，并在输出中可见 |
| 风险深度 | 没有风险级别 | 有级别但理由浅 | 高风险区域有更强覆盖和清晰备注 |
| 可追踪性 | 多数点无依据 | 大多可追踪 | 每条都有具体依据或标记为风险确认点 |
| 非用例化 | 输出像步骤用例 | 大体是测试点 | 始终保持中等粒度测试点 |
| 覆盖完整性 | 只覆盖正向主流程 | 有部分反向覆盖 | 相关时覆盖主流程、异常、边界、状态、权限、数据和接口 |

### 评分细则

| 维度 | 2 分要求 |
|---|---|
| 需求理解 | 模块、角色、规则、状态、接口、数据对象和非范围均有体现；缺口转成待确认问题 |
| 测试技术应用 | 测试技术路由表完整，必选技术有 `ME-*` 证据或待确认解释 |
| 风险深度 | 高损失、不可逆、权限、数据一致性、外部依赖和历史缺陷有优先覆盖 |
| 可追踪性 | 每条测试点有具体需求依据或明确风险确认点，依据不泛化 |
| 非用例化 | 不含前置条件、操作步骤、测试数据清单和完整预期结果 |
| 覆盖完整性 | 覆盖主路径、异常路径、边界、状态、权限、接口、数据和必要非功能风险 |

### 通过线

- 任一维度不得为 `0`。
- 总分至少 `10/12`。
- 低于通过线时，如果原因是输出质量不足，必须修正；如果原因是需求缺失，必须保留待确认问题。

### 失败处理

- `需求理解` 为 0：回到需求结构化阶段，不能直接修测试点。
- `测试技术应用` 为 0：补测试技术路由和方法证据，再重新生成测试点。
- `可追踪性` 或 `非用例化` 为 0：属于输出质量问题，必须修正后再发布。
- 因需求缺失导致无法满分时，最终报告必须保留刷新后的待确认问题。
