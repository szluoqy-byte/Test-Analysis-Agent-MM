# 测试点生成 Skill

本 skill 在需求结构化、设计方案分析、测试技术路由和专项分析之后使用，负责把内部分析结果整理成场景化测试点。该结果交给 `test-analysis-solution-generation` 继续扩展为 `测试分析方案`。

模板只定义输出结构和占位；场景边界、测试类型、非用例化和方法证据等背景知识由本 skill 按需读取 `knowledge/`，不要把知识文件引用或长篇定义写入主输出模板。

本项目的主交付件是测试分析方案。场景化测试点必须把后续测试点明细生成需要的需求摘要、范围边界、入口、角色、业务约束、设计方案约束、接口契约和判定依据写清楚，不依赖后续阶段回读原始需求或过程产物。

## 输入

- 结构化需求模型。
- 设计方案事实摘要，包括接口、字段、状态、权限、数据依赖、配置开关、异常处理和非功能指标。
- `testing-method-router` 输出的测试技术路由表。
- 分析维度覆盖表。
- `ME-*` 方法分析证据摘要。
- 风险分析结果。
- 边界/等价类、状态、决策表、场景流、权限、接口、数据一致性、组合兼容等分析结果。
- 记忆上下文包中命中的 project/personal 风险画像、覆盖策略、术语映射、模板偏好、个人关注点和 oracle 补充。
- `process/context-pack.md` 中绑定到 `testpoint-generation` 的 project knowledge 文件，例如测试设计因子库、测试设计模式库、风险画像、Oracle 或覆盖策略。
- `knowledge/testpoint-standard.md`。
- `knowledge/test-analysis-methodology.md`。
- `knowledge/basic-test-types.md`。
- `knowledge/test-techniques/README.md`。
- `templates/test-analysis-solution-template.md`。
- 如需保留过程审查信息，可同时参考 `templates/final-report-template.md`。

## 生成步骤

1. 读取 context pack 的“项目知识阶段绑定”。如果存在绑定到 `testpoint-generation` 的 project knowledge，先按来源文件、相关章节、关键词或标题读取，不全量复制大文件。
2. 先按用户任务、业务流程、系统触发或专项质量目标识别 `SC-*` 测试场景；如果当前任务、需求或设计方案明确要求接口测试/API 契约覆盖，或存在可独立验证的接口/消息/回调清单，可生成接口或集成覆盖场景，但不得仅因正文出现接口路径就强制新增接口场景。
3. 为每个场景填写 `场景名称`、`场景目标`、`场景入口/触发方式`、`执行用户/角色` 和 `业务与设计约束`；场景名称应是业务行为，不是方法名或测试点分类。
4. 每个场景必须保留一个 `E2E场景测试` 测试点，用于覆盖该场景对应的端到端业务主流程能否按预期完整闭环。`E2E场景测试` 是独立同级 `TP-*`，不是场景内其他测试点的容器。
5. 将内部测试点候选归入最合适的场景，并写成“要验证什么”的无歧义验证目标；除端到端主流程闭环以外，其他业务规则、异常处理、接口契约、权限、状态、数据校验、补偿或回滚关注点必须生成独立同级 `TP-*`，不得挂在 `E2E场景测试` 下。
6. `TP-*` 仍表示测试点主题，不把 `TP-*` 本身写成“非成功路径主题”。
7. 使用绑定的测试设计因子、业务测试设计模式、风险画像或 Oracle 补充识别遗漏的业务入口、数据因子、状态、接口、观察点或风险测试点；补充项必须能追踪到需求、设计方案、context pack 或项目知识来源。
8. 场景测试点使用 `TP-001` 起连续编号；接口、消息、定时任务或批处理内容如果最终形成测试点，也使用统一 `TP-*` 编号，不另起接口专用编号体系。
9. 当某个场景属于接口测试或集成覆盖场景时，先按接口、端点、消息、回调或集成点生成同级 `TP-*`，再在该 `TP-*` 下拆字段契约、响应契约、错误码、鉴权、幂等、超时、重试和副作用等 `TP-*-*`。`TP-*` 标题必须标明目标接口或范围，例如 `接口：POST /customers/{customer_id}/transactions/`、`接口：获取认证 Token`、`集成点：SteamaCo 支付交易创建` 或 `通用接口鉴权规则（适用于所有外部 API）`。
10. 接口测试场景中的泛化主题不得直接作为 `TP-*`，例如“状态码规则”“鉴权规则”“字段校验”必须挂到明确接口、集成点或通用接口范围下，避免后续测试点明细无法判断瞄准哪个接口。
11. 单独识别需要验证的接口契约维度，作为后续主交付件生成的分析候选；页面观察点或不需独立验证的内部调用不要强行列入。
12. 接口契约候选只描述接口契约、字段、规则、错误码、鉴权、幂等、性能或可靠性目标。
13. 去重并合并过细测试点；如果多个测试点只因具体输入值、按钮或步骤不同而拆分，应上收为规则、条件或风险。
14. 对每个重要分析维度检查是否已落到需求信息、场景、测试点或过程缺口候选。
15. 对每个 `必选` 测试技术检查是否已落到场景测试点、方法证据或过程缺口候选。
16. 检查主输出自包含性：如果某条测试点或后续测试点明细需要依赖原始需求、设计方案、过程报告或 memory 才能理解，应把必要背景上收进场景说明或测试点描述。
17. 如果使用了 project/personal 补充，必须把后续测试点明细生成需要知道的业务上下文、风险原因、个人关注点或判定依据写入主交付件；不得要求后续项目回读 `*/projects/<project-key>/` 或 `*/user/`。
18. 记录本阶段 project knowledge 应用状态。

## 标准来源

- 内部分析的 `类型`、`方法/测试技术`、粒度和非用例化约束以 `knowledge/testpoint-standard.md` 为准。
- 测试分析、测试设计边界、场景层级、分析维度和主交付件落点以 `knowledge/test-analysis-methodology.md` 为准。
- 测试点类型以 `knowledge/basic-test-types.md` 为准。
- 预期结果与 Oracle 启发以 `knowledge/test-techniques/README.md` 为准；依据不足时后续测试点明细统一写 `待人工分析确认`。
- project/personal 补充以当前 run 的 `process/context-pack.md` 为准，只能补充风险画像、覆盖策略、术语映射、模板偏好、个人关注点和 oracle，不改变上述核心标准来源；personal 不得作为项目事实。
- 绑定到本阶段的 project knowledge 必须读取并留痕；如果未应用，必须使用 `not_applicable`、`insufficient_evidence`、`conflict_with_requirement` 或 `deferred_to_review` 解释。

## 合并规则

- 多个专项测试技术产出的候选指向同一被测对象、同一场景和同一验证特性时，合并为一个测试点。
- 合并后在过程报告中 `方法` 填写最能解释该测试点来源的主要测试技术；主交付件中不输出 `方法`，其他支撑技术保留在方法证据摘要中。
- 同一业务对象在不同风险维度下需要分别验证时，不强行合并。
- 风险确认点可以生成测试点，但主交付件不写待确认章节；后续测试点明细若缺少判定依据，预期结果写 `待人工分析确认`。
- 不把候选表中的临时列带入最终测试分析方案。

## 输出契约

场景化测试点作为中间结构进入 `${PROJECT_ROOT}/outputs/runs/<run-id>/deliverables/test-analysis-solution.md`，由 `test-analysis-solution-generation` 在同一主交付件中扩展为测试点明细。

- `## 1. 需求范围`
- `## 2. 测试场景与测试点`

主交付件中的测试点使用标题表达：

```markdown
### SC-001 <测试场景名称>

#### TP-001 <测试点>
```

过程报告如包含扁平测试点明细，必须复用同一批场景和测试点，不得与主交付件冲突。

如本阶段绑定了 project knowledge，过程报告追加应用记录：

| 来源文件 | 当前阶段 | 应用状态 | 应用位置 | 说明 |
|---|---|---|---|---|

## 约束

- 不写操作步骤、具体测试数据或完整预期结果清单。
- 不使用 `操作步骤`、`测试数据`、`前置步骤`、`自动化脚本` 作为列名。
- 主交付件只允许测试点明细使用 `预期结果` 字段。
- 每个测试场景必须包含 `E2E场景测试` 测试点。
- `E2E场景测试` 只承载端到端主流程闭环验证，不承载异常、失败、接口错误、数据校验、权限、状态、回滚或补偿分支。
- 不把边界值、等价类、判定表、组合矩阵、状态迁移矩阵等测试技术名称或方法产物写入主交付件测试点；这些只保留在过程分析证据中。
- 每条测试点是对验证特性的细化，必须明确被测对象、特定场景和某一功能/规则/行为。
- 每个 `必选` 测试技术必须产出至少一个测试点或一个过程缺口问题。
- 每个测试点应能在过程报告中追溯到一个需求依据和一个方法证据；不在主交付件中新增证据列。
- 缺少判定依据时，不隐藏问题，交给后续测试点明细的 `预期结果 = 待人工分析确认` 承接。
- 不为了凑数量拆出只有输入值、按钮或页面元素不同的测试点。
- 不因为需求或设计方案出现接口路径、请求字段、响应字段或错误码，就预设所有需求都必须新增接口测试场景；但一旦当前任务或输入明确要求接口测试，必须先按接口、端点、消息、回调或集成点组织 `TP-*`，再拆契约维度。
- 不使用 `正常`、`异常`、`校验通过` 这类无法单独表达验证特性的描述作为测试点主体。
- 如果 context pack 中的 project/personal 补充不足，只能按 context pack 记录的来源或当前需求明确指向的文件补读相关章节，并在过程报告或风险备注中记录来源；不得全目录搜索或全量复制大文件。
