# 测试分析方案生成

本 skill 直接从输入事实模型、测试技术路由、专项方法参考和 `ME-*` 方法证据生成 `测试分析方案`。它同时负责生成 `SC-*` 测试场景、`TP-*` 测试点、`TP-*-*` 测试点明细，以及必要的 `TP-*-*-*` 失败类型明细；不再依赖独立测试点生成中间阶段。

它使用本仓库内置的 `knowledge/test-techniques/` 测试技术库识别需要覆盖的规则分支、路径分支、状态分支、权限分支、接口契约分支和风险分支，但不输出具体代表性条件、数据、状态组合或 `TDI-*`。

## 路径解析规则

- 本 skill 中所有 `knowledge/...`、`templates/...`、`quality-gates/...` 路径均为仓库根目录相对路径。
- 读取测试技术时，先读取 `knowledge/test-techniques/README.md`，再按 README 路由读取同目录下的具体技术文件。
- 工作流边界读取 `knowledge/test-workflow-boundaries.md`；测试分析方案粒度和结构细则读取 `knowledge/test-analysis-solution-standard.md`。
- 输出 JSON 结构读取 `templates/test-analysis-solution-json-template.json`；Markdown 模板仅作为渲染样式参考。

## 职责边界

- 输出“这个测试点下有哪些可评审的分析分支”，不输出“每个分支用什么代表性数据去测”。
- 生成测试场景和测试点，并把输入事实、方法证据、测试点候选和风险分析结果上收为可理解的业务验证目标。
- 为每个测试点明细补充 `预期结果`。
- 保留测试场景、测试点、测试点明细的层级关系；仅当 `TP-*-*` 是非成功测试点明细时新增第四层失败类型明细。
- 不生成 `TDI-*` 测试设计项。
- 不生成前置步骤、测试步骤、自动化脚本或执行数据清单。
- 不在主交付件输出 `覆盖意图`、`级别`、`判定关注`、`待确认信息` 或 `输入条件与数据依赖`。

## 输入

- 输入事实模型，尤其是事实清单、需求-设计映射、约束/条件、可观察结果和缺口/冲突。
- `testing-method-router` 输出的分析维度覆盖表、测试技术路由表和专项方法参考选择结果。
- `context-pack.json` 中与本次相关的项目事实、历史缺陷和输出偏好。
- `process/context-pack.json` 中绑定到 `test-analysis-solution-generation` 的 project knowledge 文件，例如测试设计因子库、测试设计模式库、风险画像、Oracle、路由说明或覆盖策略。
- `ME-*` 方法分析证据摘要。
- 专项方法参考产出的测试点候选、接口契约候选、技术缺口候选和按源补读记录。
- `process/clarification-session.json` 中已收口的过程缺口候选。

## 生成步骤

1. 读取 context pack 的“项目知识阶段绑定”。如果存在绑定到 `test-analysis-solution-generation` 的 project knowledge，先按来源文件、相关章节、关键词或标题读取，不全量复制大文件。
2. 按用户任务、业务流程、系统触发或专项质量目标识别 `SC-*` 测试场景；场景名称应是业务行为，不是方法名或测试点分类。
3. 为每个场景保留必要上下文：场景目标、入口/触发方式、执行用户/角色、业务与设计约束、接口或数据依赖。主交付件必须自包含，不依赖后续读者回读原始需求、设计方案、结构化过程记录或 memory 才能理解测试点。
4. 每个场景必须保留一个 `E2E场景测试` 测试点，用于覆盖该场景对应的端到端业务主流程能否按预期完整闭环。`E2E场景测试` 是独立同级 `TP-*`，不是场景内其他测试点的容器。
5. 将方法证据、专项方法参考候选、风险分析结果、接口契约候选和输入事实归入最合适的场景，并写成“要验证什么”的无歧义验证目标；除端到端主流程闭环以外，其他业务规则、异常处理、接口契约、权限、状态、数据校验、补偿或回滚关注点必须生成独立同级 `TP-*`。
6. 使用绑定的测试设计因子、业务测试设计模式、风险画像或 Oracle 补充识别遗漏的业务入口、数据因子、状态、接口、观察点或风险测试点；补充项必须能追踪到当前用户明确指令、适用 rules、需求、设计方案、context pack 或项目知识来源。
7. 接口、消息、定时任务或批处理内容如果最终形成测试点，也使用统一 `TP-*` 编号，不另起接口专用编号体系；接口契约候选只描述接口契约、字段、规则、错误码、鉴权、幂等、性能或可靠性目标。
8. 当某个场景属于接口测试或集成覆盖场景时，先按接口、端点、消息、回调或集成点生成同级 `TP-*`，再在该 `TP-*` 下拆字段契约、响应契约、错误码、鉴权、幂等、超时、重试和副作用等 `TP-*-*`。`TP-*` 标题必须标明目标接口或范围，例如 `接口：POST /customers/{customer_id}/transactions/`、`接口：获取认证 Token`、`集成点：SteamaCo 支付交易创建` 或 `通用接口鉴权规则（适用于所有外部 API）`。
9. 接口测试场景中的泛化主题不得直接作为 `TP-*`，例如“状态码规则”“鉴权规则”“字段校验”必须挂到明确接口、集成点或通用接口范围下，避免后续测试点明细无法判断瞄准哪个接口。
10. 按 `knowledge/test-analysis-solution-standard.md` 检查输入是否满足 `测试场景 -> 测试点 -> 测试点明细` 的层级关系；如果候选已写成完整用例、具体数据值、按钮动作或步骤，先上收为验证目标。
11. 按 `knowledge/test-analysis-solution-standard.md` 确认测试点明细粒度：测试点明细应是分析层分支，不是测试设计项、用例标题、测试步骤或数据清单。
12. 对每条测试点识别主要信号：流程、边界、枚举、字段格式、字段长度、组合、判定、周期、状态、权限、接口、历史缺陷、风险或质量属性。
13. 按 `knowledge/test-techniques/README.md` 选择适用测试技术。测试技术用于识别应覆盖的分支，不作为主交付件字段输出。
14. 结合绑定的测试设计因子、业务测试设计模式或 Oracle，提取对当前测试点有用的规则分支、路径分支、状态分支、权限分支、接口契约分支、风险分支和预期结果依据；不得因为项目知识存在就编造需求或设计方案未说明的业务事实。
15. 去重并合并过细测试点；如果多个测试点只因具体输入值、按钮或步骤不同而拆分，应上收为规则、条件或风险。同一业务对象在不同风险维度下确实需要分别验证时，可以保留独立测试点。
16. 对每个重要分析维度检查是否已落到需求范围、场景、测试点、测试点明细或过程缺口候选；对每个 `必选` 测试技术检查是否已落到主交付件、方法证据或过程缺口候选。
17. 基于场景、测试点、需求事实和设计方案事实，生成 1-N 个测试点明细：
   - 每个测试场景必须包含一个 `E2E场景测试` 测试点，并且该测试点只能生成 1 个端到端主流程成功闭环测试点明细。
   - `E2E场景测试` 是场景下独立同级 `TP-*`，不是场景内其他规则、异常、接口、权限、状态、回滚或补偿分支的容器。
   - 当场景属于接口测试或集成覆盖场景时，非 E2E 的 `TP-*` 必须先标明目标接口、端点、消息、回调、集成点或通用接口范围，再在其下生成契约维度明细。不得把“状态码规则”“鉴权规则”“字段校验”这类泛化主题直接作为无法定位目标接口的 `TP-*`。
   - 主路径或核心成功分支至少 1 个测试点明细。
   - 明确边界、枚举、状态、权限、接口错误码、组合或异常处理时，先抽象成分析分支。
   - 同一测试点下仅具体取值不同但业务判定一致的内容，不在本阶段拆成多条具体数据明细。
   - 当不同分支对应不同业务判定、状态变化、权限结果、接口契约或风险后果时，应拆成不同测试点明细。
18. 当某个 `TP-*-*` 测试点明细是明确非成功聚合分支时，必须在其下新增 `TP-*-*-*` 第四层失败类型明细：
   - 明确非成功聚合分支通常包含“失败”“拒绝”“不允许”“不满足”“非法”“无效”“异常”“错误”“超时”“权限限制”“依赖失败”“状态不允许”“重复提交失败”等强失败语义，例如“不满足长度要求”“权限拒绝”“非法状态下不允许取消”。
   - 第四层按失败类型继续拆分，例如长度过短、长度过长、缺少必填字段、状态不允许、权限不足、外部依赖返回异常、接口超时、重复请求导致幂等处理。
   - “未注册”“未找到”“count=0”“列表为空”“空结果”“回滚/补偿状态确认”这类单一结果分支，如果需求或设计方案只表达一种可判定结果，优先作为普通 `TP-*-*` 叶子明细，不为了通过校验机械新增第四层。
   - 只有当上述弱结果分支还需要继续区分不同失败来源或异常类型时，才新增第四层。
   - 只有第四层叶子节点承载 `description` 和 `expectedResult`；父级非成功测试点明细作为分组，不写测试设计项。
   - 成功路径或普通规则分支不新增第四层。
19. 测试点明细命名使用分析化表达，优先写成“<对象/字段/状态> 满足/不满足 <规则>”或“<角色/状态/配置> 下 <业务动作> 被允许/被拒绝”，例如：
   - 下发订单 ID 满足长度要求。
   - 下发订单 ID 不满足长度要求。
   - 已支付订单重复提交取消请求。
   - 普通用户访问管理员专属配置入口。
20. `预期结果` 的生成规则：
   - 如果需求或设计方案明确了成功、失败、拦截、状态变化、错误提示、错误码、返回内容、记录变化或消息发送结果，写成简短预期结果。
   - 如果只能判断“应该有结果”但不知道具体错误提示、状态变化、错误码或数据记录，写 `待人工分析确认`。
   - 不得为了让预期结果看起来完整而编造错误码、提示文案、状态枚举、接口响应结构或数据库字段。
21. 去重：如果两个叶子节点的验证分支和预期结果相同，只保留一个；如果只是措辞不同，不得重复输出。
22. 记录本阶段 project knowledge 应用状态。
23. 按 `templates/test-analysis-solution-json-template.json` 写入 `deliverables/test-analysis-solution.json`，保持 `测试场景 -> 测试点 -> 测试点明细` 层级；非成功测试点明细按 `测试场景 -> 测试点 -> 测试点明细 -> 失败类型明细` 输出。不要手工写 `test-analysis-solution.md`，由 `bin/render-run-markdown.py` 生成。

## 输出格式

每个场景下使用 JSON 表达以下结构。`E2E场景测试` 固定作为场景主流程测试点，只维护一个端到端主流程成功闭环明细；普通规则、异常处理、接口契约、权限、状态、数据校验、回滚或补偿分支必须拆为同级 `TP-*`，不得挂在 `E2E场景测试` 下。普通/成功测试点明细和非成功测试点明细可以属于同一个业务测试点主题。若场景是接口测试或集成覆盖场景，非 E2E 的 `TP-*` 必须先按目标接口、端点、消息、回调或集成点组织。

```json
{
  "id": "SC-001",
  "title": "<测试场景名称>",
  "fields": [
    {"field": "场景目标", "content": "<场景目标>"}
  ],
  "testPoints": [
    {
      "id": "TP-001",
      "title": "E2E场景测试",
      "details": [
        {
          "id": "TP-001-001",
          "title": "<端到端主流程测试点明细>",
          "description": "<说明该场景端到端业务主流程需要验证什么。>",
          "expectedResult": "<业务主流程按预期完整闭环或待人工分析确认>",
          "failureDetails": []
        }
      ]
    },
    {
      "id": "TP-002",
      "title": "<测试点>",
      "details": [
        {
          "id": "TP-002-001",
          "title": "<普通/成功测试点明细>",
          "description": "<说明该规则分支、路径分支、状态分支或风险分支需要验证什么。>",
          "expectedResult": "<明确预期结果或待人工分析确认>",
          "failureDetails": []
        },
        {
          "id": "TP-002-002",
          "title": "<非成功测试点明细>",
          "failureDetails": [
            {
              "id": "TP-002-002-001",
              "title": "<失败类型明细>",
              "description": "<说明该失败类型需要验证什么。>",
              "expectedResult": "<明确预期结果或待人工分析确认>"
            }
          ]
        }
      ]
    }
  ]
}
```

接口测试或集成覆盖场景的推荐结构：

```json
{
  "id": "TP-002",
  "title": "接口：GET /customers/?telephone_exact={phone}",
  "details": [
    {
      "id": "TP-002-001",
      "title": "有效 MSISDN 返回客户数据",
      "description": "验证查询客户接口在 MSISDN 已注册时返回客户详情。",
      "expectedResult": "返回 count=1 和客户详情，具体字段以设计方案为准。",
      "failureDetails": []
    },
    {
      "id": "TP-002-002",
      "title": "未注册 MSISDN 返回空结果",
      "description": "验证查询客户接口在 MSISDN 未注册时返回空结果。",
      "expectedResult": "返回 count=0；若错误处理规则未说明则待人工分析确认。",
      "failureDetails": []
    }
  ]
}
```

接口、消息、定时任务或批处理内容如果最终形成测试点，仍使用 `TP-*` 测试点编号；测试点标题必须让后续读者知道目标接口或适用范围，不另起 `ITP-*` 或 `ITDI-*`。主交付件只使用中文术语和缩写，不展开英文全名。

## 与 test-design-agent 的边界

- 当前 skill 可以识别“满足长度要求”和“不满足长度要求”。
- 当“不满足长度要求”属于明确非成功聚合明细时，当前 skill 可以继续拆出“长度短于规则要求”“长度长于规则要求”等失败类型明细。
- 当明细只是单一弱结果分支，例如“未注册 MSISDN 返回空结果”或“交易引用未找到返回 count=0”，当前 skill 可停留在 `TP-*-*`，不强制新增第四层。
- 当前 skill 不输出“长度等于 13 位”“长度小于 13 位 1 位”“长度大于 13 位 1 位”等代表性设计条件。
- `test-design-agent` 可以在评审后的测试分析方案上，为每个普通 `TP-*-*` 或失败类型 `TP-*-*-*` 补充 `TDI-*` 和代表性条件、数据、状态或组合。

## 高标准示例来源

详细测试技术示例由 `knowledge/test-techniques/**/*.md` 维护。当前 skill 只复用其中的分析思想和分支识别方法，不照搬其中的 `TDI-*` 设计项示例到主交付件。

## 约束

- 不输出 `前置步骤`、`测试步骤`、`操作步骤`、`执行数据`、`自动化脚本` 等字段。
- 不输出旧版主交付件字段；字段禁用清单以 `bin/lint-test-analysis-solution.py` 为准。
- 主交付件不使用 Markdown 加粗语法，例如 `**文本**` 或 `__文本__`。
- 不输出 `TDI-*`、`测试设计项` 或测试设计项表格。
- 不把“正向/异常”作为测试点明细正文；必须写清楚规则分支或行为分支。
- 不把 `E2E场景测试` 当作场景内容器；除端到端主流程成功闭环明细外，其他测试点明细必须挂到独立同级 `TP-*`。
- 接口测试或集成覆盖场景下，不输出无法定位目标接口的泛化 `TP-*`；接口契约、字段、错误码、鉴权、幂等、超时或重试必须挂到明确接口、集成点或通用接口范围下。
- 不为了凑数量生成重复测试点明细。
- 不强制每个具体输入值都生成独立测试点明细；具体取值留给 `test-design-agent`。
- 如果覆盖补全依赖的枚举值、容量阈值、兼容范围、目标语言、性能指标、错误码、错误提示或异常处理规则缺失，预期结果写 `待人工分析确认`，不编造具体取值。
- 绑定到本阶段的 project knowledge 必须读取并留痕；如果未应用，必须使用 `not_applicable`、`insufficient_evidence`、`conflict_with_requirement` 或 `deferred_to_review` 解释。
