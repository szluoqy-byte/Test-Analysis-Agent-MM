# 测试分析方案独立评审

本 skill 是项目内的独立评审 Agent。根据仓库规则，不创建插件级评审 agent；评审角色通过本 skill、quality gate 和确定性脚本实现。

## 输入

- `outputs/runs/<run-id>/deliverables/test-analysis-solution.md`。
- 需求文档和可选设计方案文档摘要。
- `process/context-pack.md`。
- `process/clarification-session.md`。
- 方法证据和测试点生成结果。
- `process/context-pack.md` 中绑定到 `test-analysis-solution-review` 的 project checklist、评审清单或其他评审类 project knowledge。
- `knowledge/test-analysis-solution-standard.md`。
- `quality-gates/test-analysis-solution-check.md`。

## 评审维度

| 维度 | 通过标准 |
|---|---|
| 结构 | 主输出按 `测试场景 -> 测试点 -> 测试点明细` 组织 |
| 标题 | 场景使用 `SC-*`，测试点使用 `TP-*`，测试点明细使用 `TP-*-*` |
| 粒度 | 测试点明细是分析层分支，不是步骤、标题口号、具体数据项或测试设计项 |
| 预期结果 | 有明确需求/设计依据；依据不足时精确写 `待人工分析确认` |
| 缺口处理 | 不出现 `未明确规则` 章节，不出现独立待确认信息清单 |
| 设计项边界 | 不出现 `TDI-*`、`测试设计项` 或测试设计项表格 |
| 旧字段清理 | 不出现 `覆盖意图`、`级别`、`判定关注`、`输入条件与数据依赖`、`待确认信息` 等旧字段 |
| 非用例化 | 不出现前置步骤、测试步骤、操作步骤、自动化脚本或接口调用代码 |
| 自包含 | 后续人工评审和 `test-design-agent` 能直接理解测试场景、测试点和测试点明细 |

## 评审步骤

1. 读取 context pack 的“项目知识阶段绑定”。如果存在绑定到 `test-analysis-solution-review` 的 project knowledge，先按来源文件、相关章节、关键词或标题读取，不全量复制大文件。
2. 检查主交付件路径是否为 `deliverables/test-analysis-solution.md`。
3. 检查一级标题是否声明 `测试分析方案`。
4. 检查是否存在 `## 1. 需求范围` 和 `## 2. 测试场景与测试点`。
5. 检查是否存在 `## 3. 未明确规则`、`待确认信息` 或旧版主交付件章节；存在则判为失败。
6. 对每个 `#### TP-*`，检查后续是否至少有一个 `##### TP-*-*` 测试点明细。
7. 对每个测试点明细，检查是否包含 `- 测试点详情：` 和 `- 预期结果：`。
8. 检查测试点明细是否过度下钻到具体代表性数据、边界值或组合；如果是，建议上收为分析分支并把具体数据留给 `test-design-agent`。
9. 当测试点明细明显是失败、拒绝、异常或边界分支，但需求或设计方案未提供错误提示、状态变化或错误码时，要求预期结果写 `待人工分析确认`。
10. 按绑定的 project checklist 或评审清单检查是否存在项目级漏覆盖；无法直接判断的检查项记录为 `insufficient_evidence`，不得编造成已确认缺陷。
11. 检查是否有编造的错误码、状态、提示文案、接口字段或阈值；无法溯源时要求改为 `待人工分析确认`。
12. 记录本阶段 project knowledge 应用状态，输出评审结论和逐项修正建议。

|---|---|---|---|
| 结构 | 通过/警告/失败 |  |  |

| 测试点明细粒度 | 通过/警告/失败 |  |  |
| 预期结果依据 | 通过/警告/失败 |  |  |
| 缺口兜底 | 通过/警告/失败 |  |  |
| TDI 泄漏 | 通过/警告/失败 |  |  |
| 旧字段清理 | 通过/警告/失败 |  |  |
| 非用例化 | 通过/警告/失败 |  |  |

如本阶段绑定了 project knowledge，追加应用记录：

| 来源文件 | 当前阶段 | 应用状态 | 应用位置 | 说明 |
|---|---|---|---|---|

结论必须明确为：

- `通过`：可以进入覆盖审查。
- `需修正`：必须先修正主交付件再进入覆盖审查。

## 约束

- 不新增测试点明细，除非评审任务明确要求直接修复。
- 不编造需求或设计方案事实。
- 不把过程缺口写回主交付件章节。
- 不用 `待确认`、`TBD`、`见设计方案` 替代 `待人工分析确认`。
- 不引入 `TDI-*` 或测试设计项。
- 绑定到本阶段的 project knowledge 必须读取并留痕；如果未应用，必须使用 `not_applicable`、`insufficient_evidence` 或 `conflict_with_requirement` 解释。
