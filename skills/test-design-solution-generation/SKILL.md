# 测试设计方案生成

本 skill 负责从 `testpoint-generation` 产出的测试场景、场景测试条件、场景测试点和接口测试点生成 `测试设计方案`。它使用本仓库内置的 `knowledge/test-techniques/` 测试技术库，在测试设计阶段回答“如何用代表性条件、数据、状态或组合覆盖测试点”。

## 路径解析规则

- 本 skill 中所有 `knowledge/...`、`templates/...`、`quality-gates/...` 路径均为仓库根目录相对路径。
- 读取测试技术时，先读取 `knowledge/test-techniques/README.md`，再按 README 路由读取同目录下的具体技术文件。
- 粒度边界读取 `knowledge/test-analysis-methodology.md` 和 `knowledge/test-design-solution-standard.md`。
- 输出结构读取 `templates/test-design-solution-template.md`。

## 职责边界

- 输出“应该用哪些测试设计项覆盖测试点”，不输出完整用例正文。
- 为每个测试设计项补充 `预期结果`。
- 保留测试点到测试设计项的层级关系。
- 不生成前置步骤、测试步骤、自动化脚本或执行数据清单。
- 不在主交付件输出 `覆盖意图`、`级别`、`判定关注`、`待确认信息` 或 `输入条件与数据依赖`。

## 输入

- 测试场景清单、场景测试条件、场景测试点和接口测试点。
- 结构化需求模型。
- 设计方案事实摘要，尤其是接口、字段、状态、权限、数据依赖、配置开关、异常处理和非功能指标。
- `context-pack.md` 中与本次相关的项目事实、历史缺陷和输出偏好。
- `process/context-pack.md` 中绑定到 `test-design-solution-generation` 的 project knowledge 文件，例如测试设计因子库、测试设计模式库、Oracle 或覆盖策略。
- `ME-*` 方法分析证据摘要。
- `process/clarification-session.md` 中已收口的过程缺口候选。

## 生成步骤

1. 读取 context pack 的“项目知识阶段绑定”。如果存在绑定到 `test-design-solution-generation` 的 project knowledge，先按来源文件、相关章节、关键词或标题读取，不全量复制大文件。
2. 按 `knowledge/test-analysis-methodology.md` 检查输入是否满足 `测试场景 -> 测试点` 的层级关系；如果测试点已写成完整用例，先上收为验证目标。
3. 按 `knowledge/test-design-solution-standard.md` 确认测试设计项粒度：测试设计项应是代表性条件、数据、状态或组合，不是用例标题、测试步骤或数据清单。
4. 对每条测试点识别主要信号：流程、边界、枚举、字段格式、字段长度、组合、判定、周期、状态、权限、接口、历史缺陷、风险或质量属性。
5. 按 `knowledge/test-techniques/README.md` 选择适用测试技术。测试技术用于选择代表性设计项，不作为主交付件字段输出。
6. 结合绑定的测试设计因子、业务测试设计模式或 Oracle，提取对当前测试点有用的代表性条件、数据、状态、组合和预期结果依据；不得因为项目知识存在就编造需求或设计方案未说明的业务事实。
7. 基于场景测试条件、需求事实和设计方案事实，生成 1-N 个测试设计项：
   - 主路径或核心成功条件至少 1 个测试设计项。
   - 明确边界、枚举、状态、权限、接口错误码、组合或异常处理时，按风险拆出独立测试设计项。
   - 同一验证目标只是输入值不同且系统处理结果一致的，可合并为一个测试设计项，并用简洁条件表达取值范围。
   - 当具体输入值代表不同边界、分支、错误类型或风险定位方向时，应拆分成不同测试设计项。
8. 测试设计项命名使用条件化表达，优先写成“<对象/字段/状态/组合> 为 <代表条件>”，例如：
   - 下发订单 ID 总长度为 13 位。
   - 下发订单 ID 总长度小于 13 位。
   - 订单已支付状态下重复提交取消请求。
   - 普通用户访问管理员专属配置入口。
9. `预期结果` 的生成规则：
   - 如果需求或设计方案明确了成功、失败、拦截、状态变化、错误提示、错误码、返回内容、记录变化或消息发送结果，写成简短预期结果。
   - 如果只能判断“应该有结果”但不知道具体错误提示、状态变化、错误码或数据记录，写 `待人工分析确认`。
   - 不得为了让预期结果看起来完整而编造错误码、提示文案、状态枚举、接口响应结构或数据库字段。
10. 去重：如果两个测试设计项的条件、数据、状态、组合和预期结果相同，只保留一个；如果只是措辞不同，不得重复输出。
11. 记录本阶段 project knowledge 应用状态。
12. 按 `templates/test-design-solution-template.md` 写入主交付件，保持 `测试场景 -> 测试点 -> 测试设计项` 层级。

## 输出格式

每个测试点下使用以下表格：

| 测试设计项 ID | 测试设计项 | 预期结果 |
|---|---|---|
| TDI-001 | <代表性条件、数据、状态或组合> | <明确预期结果或待人工分析确认> |

接口、消息、定时任务或批处理测试点仍使用 `TP-*` 测试点编号和 `TDI-*` 测试设计项全局连续编号，不另起 `ITP-*` 或 `ITDI-*`。主交付件只使用中文术语和缩写，不展开英文全名。

如本阶段绑定了 project knowledge，过程报告追加应用记录：

| 来源文件 | 当前阶段 | 应用状态 | 应用位置 | 说明 |
|---|---|---|---|---|

## 高标准示例来源

详细示例由 `knowledge/test-techniques/**/*.md` 维护。生成测试设计项时，应优先读取当前测试点命中的主测试技术文件，并参考其中“测试场景 + 规格摘要 + 测试点 + 测试设计项 + 设计要点”的示例粒度；本 skill 不重复维护大段示例，避免 skill 与 knowledge 分叉。

## 约束

- 不输出 `前置步骤`、`测试步骤`、`操作步骤`、`执行数据`、`自动化脚本` 等字段。
- 不输出旧版主交付件字段；字段禁用清单以 `bin/lint-test-design-solution.py` 为准。
- 不把“正向/异常”作为测试设计项正文；必须写清楚代表性条件、数据、状态或组合。
- 不为了凑数量生成重复测试设计项。
- 不强制每个测试点只生成一条测试设计项；高风险、边界、状态、权限、接口和组合测试点可以生成多条。
- 不强制每个具体输入值都生成独立测试设计项；仅当输入值代表不同边界、分支、错误类型或风险定位方向时才拆分。
- 如果覆盖补全依赖的枚举值、容量阈值、兼容范围、目标语言、性能指标、错误码、错误提示或异常处理规则缺失，预期结果写 `待人工分析确认`，不编造具体取值。
- 绑定到本阶段的 project knowledge 必须读取并留痕；如果未应用，必须使用 `not_applicable`、`insufficient_evidence`、`conflict_with_requirement` 或 `deferred_to_review` 解释。
