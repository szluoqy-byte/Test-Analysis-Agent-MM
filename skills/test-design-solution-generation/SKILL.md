# 测试设计方案生成

本 skill 负责从已评审 `测试分析方案` 生成 `测试设计方案`。它承接 `SC-* / TP-* / TP-*-*`；如果分析方案中存在非成功测试点明细的 `TP-*-*-*` 第四层，则继续承接第四层，并在叶子节点下生成 `TDI-*` 测试设计项。

测试设计项回答“如何覆盖这个测试点明细”：用哪些代表性条件、具体数据值、数据槽位、状态、接口返回或组合进行设计。它不是完整测试用例，不包含前置步骤、测试步骤、自动化脚本或执行数据清单。`预期结果` 继承并保留在普通测试点明细或失败类型明细层，`TDI-*` 下一层不再重复写预期结果。

## 路径解析规则

- 本 skill 中所有 `knowledge/...`、`templates/...`、`quality-gates/...` 路径均为仓库根目录相对路径。
- 读取测试技术时，先读取 `knowledge/test-techniques/README.md`，再按 README 路由读取同目录下的具体技术文件。
- 工作流边界读取 `knowledge/test-workflow-boundaries.md`；分析方案承接和设计方案粒度细则读取 `knowledge/test-analysis-solution-standard.md` 和 `knowledge/test-design-solution-standard.md`。
- 输出 JSON 结构读取 `templates/test-design-solution-json-template.json`；Markdown 模板仅作为渲染样式参考。

## 职责边界

- 保留测试分析方案中的场景、测试点、测试点明细和已有失败类型明细，不擅自重排、合并或新增分析层级。
- 不重新判定第四层是否应该存在；设计阶段只继承分析方案的叶子结构，发现分析层级缺口时记录输入质量问题。
- 为每个普通测试点明细或失败类型明细补充 1-N 个 `TDI-*`。
- 为每个普通测试点明细或失败类型明细保留一条从分析方案继承的 `预期结果`。
- `TDI-*` 只输出条件、数据、状态、接口返回或组合，不输出子级 `预期结果`。
- 不输出完整测试用例正文、前置步骤、测试步骤、自动化脚本或执行数据清单。
- 不在主交付件输出 `覆盖意图`、`级别`、`判定关注`、`待确认信息` 或 `输入条件与数据依赖`。

## 输入

- 已评审测试分析方案，优先读取 `outputs/runs/<run-id>/deliverables/test-analysis-solution.json`；迁移期只有 Markdown 时先解析或转换成 JSON。
- 输入事实模型或原始需求摘要。
- 输入事实模型中的设计事实，尤其是接口、字段、状态、权限、数据依赖、配置开关、异常处理和非功能指标。
- `process/context-pack.json` 中 `sources[]` 对 `test-design-solution-generation` 可见的 project/personal 动态来源，例如测试设计因子、项目测试设计模式、Oracle、风险画像和输出偏好。
- `process/clarification-session.json` 中已收口的过程缺口候选。

## 生成步骤

1. 读取 `process/context-pack.json`，筛选 `availableStages` 包含 `test-design-solution-generation` 或 `"*"` 的动态来源；如需使用，按来源文件、相关章节、关键词或标题读取正文，不全量复制大文件。
2. 按 `knowledge/test-analysis-solution-standard.md` 检查输入是否保持 `测试场景 -> 测试点 -> 测试点明细` 层级；如果非成功测试点明细存在 `TP-*-*-*` 第四层，必须保留该层级；如果单一弱结果分支停留在 `TP-*-*`，直接把该明细作为叶子分析节点，不为了设计阶段机械新增第四层。如果分析方案已经把数据值写进测试点明细，不继续放大错误，应记录输入质量问题并上收为设计项候选。
3. 按 `knowledge/test-design-solution-standard.md` 确认设计项粒度：测试设计项应是代表性条件、具体数据值、数据槽位、状态、接口返回或组合，不是用例标题口号、测试步骤或数据清单。
4. 对每个叶子分析节点识别主要设计信号：普通分支的叶子是 `TP-*-*`，非成功分支的叶子是 `TP-*-*-*`。设计信号包括边界、等价类、枚举、字段格式、字段长度、组合、判定、周期、状态、权限、接口、历史缺陷、风险或质量属性。
   - 普通 `TP-*-*` 叶子包括成功分支、普通规则分支和“未注册返回空结果”“未找到返回 count=0”“列表为空”“回滚状态确认”等单一弱结果分支。
   - 已拆出 `TP-*-*-*` 的失败类型明细才是非成功聚合分支的设计叶子，`TDI-*` 不挂在父级 `TP-*-*` 下。
   - 如果分析方案包含接口测试或集成覆盖场景，必须继承分析方案中按接口、端点、消息、回调、集成点或通用接口范围组织的 `TP-*`，不得把多个接口的设计项混到一个无法定位目标接口的泛化测试点下。
5. 按 `knowledge/test-techniques/README.md` 选择适用测试技术。测试技术用于选择代表性设计项，不作为主交付件字段输出。
6. 结合可见动态来源中的测试设计因子、业务测试设计模式或 Oracle，提取对当前测试点明细有用的代表性条件、具体数据值、数据槽位、状态、组合和判定依据；不得因为动态来源存在就编造需求或设计方案未说明的业务事实。
7. 基于叶子分析节点、需求事实和设计方案事实生成 `TDI-*`：
   - 满足规则或主路径的明细至少生成 1 个代表性成功数据组合。
   - 不满足规则、失败路径、权限拒绝、非法状态、接口错误或依赖异常的明细，按不同边界、错误类型、状态、权限、接口返回或风险定位方向拆分。
   - 同一验证目标只是输入值不同且系统处理结果一致的，可合并为一个设计项，并用简洁条件表达取值范围。
   - 当具体输入值代表不同边界、分支、错误类型或风险定位方向时，应拆分成不同设计项。
8. 测试设计项内容使用数据化表达，优先写成“字段=值；状态=值；依赖=值；接口返回=值”的组合，例如：
   - `orderId=ORD2026052801；总长度=13位`。
   - `orderId=ORD202605280；总长度=12位`。
   - `orderId=ORD20260528001；总长度=14位`。
   - `订单状态=已支付；操作=重复提交取消请求`。
   - `用户角色=普通用户；访问入口=管理员专属配置入口`。
   - `amount=1000.00；category=PAY；customer_id=AGT_CUSTOMER_001`。
   - `telephone_exact=%2B225070000001；数据依赖=AGT已注册客户`。
   - `接口=GET /customers/；telephone_exact=%2B225070000001；响应状态=HTTP 500`。
9. 对每条 `TDI-*` 做内容归一化：
   - 不写结果式或动作式表达，例如“发送通知”“显示错误提示”“自动填充”“接口调用正确”“系统完成支付流程”“删除成功”。这些内容应留在测试点详情或预期结果中；`TDI-*` 只保留可设计的条件、数据、状态、接口返回或依赖组合。
   - 如果同类设计项在不同场景、渠道、操作或接口下复用，必须补充差异维度，例如 `场景=Add Payment`、`渠道=APP`、`操作=Delete Favorite`、`接口=POST /payments/`、`数据依赖=预验证已失败`。
   - 如果发现两个 `TDI-*` 的正文完全相同，先判断是否其实代表同一覆盖对象；若是则去重，若不是则补充能说明差异的字段片段。
10. 接口契约类叶子节点必须结合已明确字段约束展开代表性设计项：
   - 字段格式、长度、精度、枚举、必填、唯一性、鉴权、幂等、状态码、错误码和依赖返回都可以成为设计信号。
   - 如果设计明确 `amount` 为两位小数、`category=PAY`、`customer_id` 必填，除有效组合外，按适用性补充 `amount=1000`、`amount=1000.0`、`amount=1000.001`、`amount=abc`、`category=REFUND`、`缺少customer_id` 等代表性契约分支。
   - 不编造输入未说明的字段、枚举、错误码、错误提示或真实生产数据。
11. 超时、回滚、补偿或外部依赖恢复类叶子节点必须把分支条件写成可观察组合，例如 `查询返回count=1；payment_status=SUCCESS`、`查询返回count=0；payment_status=FAILED`、`查询超时；payment_status=TIMEOUT`、`查询返回count>1；处理状态=待人工分析确认`，不要只写“接口超时”“补偿成功”。
12. 接口类 `TDI-*` 不得输出完整裸 URL，例如 `GET https://api.example.com/customers/?telephone_exact=...`；必须拆成 `接口=METHOD /path`、`参数名=参数值`、`响应状态=...` 等同一物理行字段片段，避免 Markdown 转脑图时被链接解析或换行破坏层级。
13. `预期结果` 的生成规则：
   - 从上游测试分析方案继承普通测试点明细或失败类型明细层的预期结果。
   - 如果补读需求或设计方案后能确认分析方案中的 `待人工分析确认`，可以在同一叶子节点的 `预期结果` 中收敛为明确判定，但必须有依据。
   - 如果只能判断“应该拦截/失败/不允许”但不知道具体错误提示、状态变化、错误码或数据记录，保留 `待人工分析确认`。
   - 如果同一叶子节点下不同 TDI 需要不同预期结果，说明分析层粒度不足，记录输入质量问题并建议回到测试分析阶段拆分；不要在 TDI 下一层追加预期结果。
   - 不得为了让预期结果看起来完整而编造错误码、提示文案、状态枚举、接口响应结构或数据库字段。
14. 去重：如果两个测试设计项的条件、数据、状态和组合相同，只保留一个；如果只是措辞不同，不得重复输出；如果确实属于不同业务流，必须补充场景、渠道、操作、接口或数据依赖等差异维度。
15. 记录本阶段动态来源应用状态。
16. 按 `templates/test-design-solution-json-template.json` 写入 `deliverables/test-design-solution.json`，保持普通分支 `测试场景 -> 测试点 -> 测试点明细 -> 测试设计项` 层级；非成功分支保持 `测试场景 -> 测试点 -> 测试点明细 -> 失败类型明细 -> 测试设计项` 层级。不要手工写 `test-design-solution.md`，由 `bin/render-run-markdown.py` 生成。

## 输出格式

每个叶子分析节点下在 JSON 中使用 `designItems` 数组表达 `TDI-*`，不使用测试设计项表格。渲染后的 Markdown 由 `bin/render-run-markdown.py` 生成列表节点，不手工维护。

```json
{
  "id": "TP-001-001",
  "title": "<测试点明细或失败类型明细>",
  "description": "<来自测试分析方案的测试点详情。>",
  "expectedResult": "<明确预期结果或待人工分析确认>",
  "failureDetails": [],
  "designItems": [
    {
      "id": "TDI-001",
      "content": "<代表性条件、数据、状态或组合>"
    }
  ]
}
```

如果测试分析方案中存在 `TP-*-*-*` 失败类型明细，测试设计项列表必须挂在该第四层下，而不是挂在父级 `TP-*-*` 下。

接口、消息、定时任务或批处理测试点仍使用 `TP-*` 测试点编号和 `TDI-*` 测试设计项全局连续编号，不另起 `ITP-*` 或 `ITDI-*`。如果分析方案中已按接口或集成点组织 `TP-*`，设计方案必须保持该组织方式，让每个 `TDI-*` 能明确追溯到目标接口或通用接口范围。主交付件只使用中文术语和缩写，不展开英文全名。

如本阶段读取了动态来源，必须在结构化过程记录、主交付件 JSON 的来源/应用字段或后续 review/coverage JSON 中追加应用记录：

| 来源文件 | 当前阶段 | 应用状态 | 应用位置 | 说明 |
|---|---|---|---|---|

## 高标准示例来源

详细示例由 `knowledge/test-techniques/**/*.md` 维护。生成测试设计项时，应优先读取当前测试点明细命中的主测试技术文件，并参考其中“测试场景 + 规格摘要 + 测试点 + 测试设计项 + 设计要点”的示例粒度；本 skill 不重复维护大段示例，避免 skill 与 knowledge 分叉。

## 约束

- 不输出 `前置步骤`、`测试步骤`、`操作步骤`、`执行数据`、`自动化脚本` 等字段。
- 不输出旧版主交付件字段；字段禁用清单以 `bin/lint-test-design-solution.py` 为准。
- 主交付件不使用 Markdown 加粗语法，例如 `**文本**` 或 `__文本__`。
- 主交付件不使用测试设计项表格；`TDI-*` 必须作为 `designItems[]` 挂在对应叶子分析节点下。
- `TDI-*` 下一层不写 `预期结果`；预期结果只保留在普通测试点明细或失败类型明细层。
- `TDI-*` 必须保持同一物理行，不得把条件、URL 查询串或接口返回拆成下一行续写。
- `TDI-*` 不得包含 `http://` 或 `https://` 裸链接；接口类设计项应拆成 `接口=METHOD /path；参数名=参数值；响应状态=...`。
- 不把设计阶段发现的遗漏范围直接新增为 `SC-*`、`TP-*`、`TP-*-*` 或 `TP-*-*-*`；需要新增分析层级时，登记过程问题并建议回到 `@test-analysis-agent`。
- 不把“正向/异常”作为测试设计项正文；必须写清楚代表性条件、数据、状态或组合。
- 不把“有效MSISDN”“有效金额”“错误PIN”“接口超时”等抽象标签作为最终 TDI；应补充具体取值、数据槽位、接口模拟返回或状态组合。
- 不把“发送通知”“显示提示”“自动填充”“接口调用正确”“处理成功”“删除成功”等结果或动作表达作为最终 TDI；应改写为条件、数据、状态、接口返回或依赖组合。
- 不重复输出无差异维度的相同 TDI；同类条件在不同业务流中复用时，必须补充 `场景=`、`渠道=`、`操作=`、`接口=` 或 `数据依赖=` 等区分字段。
- 接口契约叶子节点不得只给正向有效组合；对输入已明确的字段格式、精度、枚举、必填、鉴权、幂等、超时和依赖返回，应生成代表性有效、无效、边界或异常返回组合。
- 超时、回滚、补偿和外部依赖恢复类叶子节点必须写可观察分支条件，例如查询返回数量、状态值、依赖返回或超时状态，不只写抽象“补偿成功/失败”。
- 不为了凑数量生成重复测试设计项。
- 不强制每个叶子分析节点只生成一条测试设计项；高风险、边界、状态、权限、接口和组合分支可以生成多条。
- 不强制每个具体输入值都生成独立测试设计项；仅当输入值代表不同边界、分支、错误类型或风险定位方向时才拆分。
- 如果覆盖补全依赖的枚举值、容量阈值、兼容范围、目标语言、性能指标、错误码、错误提示或异常处理规则缺失，预期结果写 `待人工分析确认`，不编造具体取值。
- 对本阶段可见且被读取的动态来源必须留痕；如果未应用，必须使用 `not_applicable`、`insufficient_evidence`、`conflict_with_requirement` 或 `deferred_to_review` 解释。
