# 测试设计方案独立评审

本 skill 是项目内的独立评审 Agent。根据仓库规则，不创建插件级 `agents/`；评审角色通过本 skill、quality gate 和确定性脚本实现。

## 输入

- `outputs/runs/<run-id>/deliverables/test-design-solution.md`。
- 需求文档和可选设计方案文档摘要。
- `process/context-pack.md`。
- `process/clarification-session.md`。
- 方法证据和测试点生成结果。
- `knowledge/test-design-solution-standard.md`。
- `quality-gates/test-design-solution-check.md`。

## 评审维度

| 维度 | 通过标准 |
|---|---|
| 结构 | 主输出按 `测试场景 -> 测试点 -> 测试设计项` 组织 |
| 表头 | 每个测试点下只使用 `测试设计项 ID | 测试设计项 | 预期结果` |
| 粒度 | 测试设计项是代表性条件、数据、状态或组合，不是步骤、标题口号或完整用例 |
| 预期结果 | 有明确需求/设计依据；依据不足时精确写 `待人工分析确认` |
| 缺口处理 | 不出现 `未明确规则` 章节，不出现独立待确认信息清单 |
| 旧字段清理 | 不出现 `覆盖意图`、`级别`、`判定关注`、`输入条件与数据依赖`、`待确认信息` 等旧字段 |
| 非用例化 | 不出现前置步骤、测试步骤、操作步骤、自动化脚本或接口调用代码 |
| 自包含 | 后续设计评审能直接理解测试场景、测试点和设计项 |

## 评审步骤

1. 检查主交付件路径是否为 `deliverables/test-design-solution.md`。
2. 检查一级标题是否声明 `测试设计方案`。
3. 检查是否存在 `## 1. 需求范围` 和 `## 2. 测试场景与测试设计`。
4. 检查是否存在 `## 3. 未明确规则`、`待确认信息` 或旧版主交付件章节；存在则判为失败。
5. 对每个 `#### 测试点 TP-*`，检查后续是否有至少一张测试设计项表。
6. 对每条 `TD-*`，检查 ID 是否连续、设计项是否具体、预期结果是否非空。
7. 当设计项明显是失败/异常/边界条件，但需求或设计方案未提供错误提示、状态变化或错误码时，要求预期结果写 `待人工分析确认`。
8. 检查是否有编造的错误码、状态、提示文案、接口字段或阈值；无法溯源时要求改为 `待人工分析确认`。
9. 输出评审结论和逐项修正建议。

## 输出

评审输出使用以下结构：

| 评审项 | 结果 | 证据 | 修正建议 |
|---|---|---|---|
| 结构 | 通过/警告/失败 |  |  |
| 表头 | 通过/警告/失败 |  |  |
| 设计项粒度 | 通过/警告/失败 |  |  |
| 预期结果依据 | 通过/警告/失败 |  |  |
| 缺口兜底 | 通过/警告/失败 |  |  |
| 旧字段清理 | 通过/警告/失败 |  |  |
| 非用例化 | 通过/警告/失败 |  |  |

结论必须明确为：

- `通过`：可以进入覆盖审查。
- `需修正`：必须先修正主交付件再进入覆盖审查。

## 约束

- 不新增测试设计项，除非评审任务明确要求直接修复。
- 不编造需求或设计方案事实。
- 不把过程缺口写回主交付件章节。
- 不用 `待确认`、`TBD`、`见设计方案` 替代 `待人工分析确认`。
