# 测试设计方案独立评审

本 skill 是 `test-design-agent` 的独立评审环节。它检查 `测试设计方案` 是否准确承接已评审 `测试分析方案`，并停留在测试设计项粒度。

## 输入

- `outputs/runs/<run-id>/deliverables/test-design-solution.md`。
- `outputs/runs/<run-id>/deliverables/test-analysis-solution.md` 或外部测试分析方案。
- 需求文档和可选设计方案文档摘要。
- `process/context-pack.md`。
- `process/clarification-session.md`。
- `process/context-pack.md` 中绑定到 `test-design-solution-review` 的 project checklist、评审清单或其他评审类 project knowledge。
- `knowledge/test-design-solution-standard.md`。
- `quality-gates/test-design-solution-check.md`。

## 评审维度

| 维度 | 通过标准 |
|---|---|
| 承接关系 | 设计方案保留分析方案中的 `SC-*`、`TP-*`、`TP-*-*` 和已有 `TP-*-*-*`，未擅自新增或改写分析层结论 |
| 结构 | 普通分支按 `测试场景 -> 测试点 -> 测试点明细 -> 测试设计项` 组织；非成功分支按 `测试场景 -> 测试点 -> 测试点明细 -> 失败类型明细 -> 测试设计项` 组织 |
| 表头 | 每个叶子分析节点下只使用 `测试设计项 ID | 条件/数据/状态/组合 | 预期结果` |
| 粒度 | 测试设计项是代表性条件、数据、状态或组合，不是步骤、标题口号或完整用例 |
| 预期结果 | 有明确需求/设计依据；依据不足时精确写 `待人工分析确认` |
| 缺口处理 | 不出现 `未明确规则` 章节，不出现独立待确认信息清单 |
| 旧字段清理 | 不出现 `覆盖意图`、`级别`、`判定关注`、`输入条件与数据依赖`、`待确认信息` 等旧字段 |
| 非用例化 | 不出现前置步骤、测试步骤、操作步骤、自动化脚本或接口调用代码 |
| 自包含 | 后续完整用例细化只读取主交付件即可理解场景、测试点明细、设计项和预期结果 |

## 评审步骤

1. 读取 context pack 的“项目知识阶段绑定”。如果存在绑定到 `test-design-solution-review` 的 project knowledge，先按来源文件、相关章节、关键词或标题读取，不全量复制大文件。
2. 检查主交付件路径是否为 `deliverables/test-design-solution.md`。
3. 检查一级标题是否声明 `测试设计方案`。
4. 检查是否存在 `## 1. 设计输入` 和 `## 2. 测试场景与测试设计`。
5. 检查是否存在 `## 3. 未明确规则`、`待确认信息` 或旧版主交付件章节；存在则判为失败。
6. 检查分析方案中已有的 `TP-*-*-*` 失败类型明细是否被完整继承；不得合并回父级 `TP-*-*`。
7. 对每个叶子分析节点检查后续是否有至少一张测试设计项表：普通分支叶子是 `TP-*-*`，非成功分支叶子是 `TP-*-*-*`。
8. 对每条 `TDI-*`，检查 ID 是否全局连续、设计项是否具体、预期结果是否非空。
9. 检查 `TDI-*` 是否挂在正确的叶子分析节点下；不得只挂在测试点、场景或非成功父级测试点明细下。
10. 当设计项明显是失败、异常、边界、越权或非法状态条件，但需求或设计方案未提供错误提示、状态变化或错误码时，要求预期结果写 `待人工分析确认`。
11. 按绑定的 project checklist 或评审清单检查是否存在项目级漏覆盖；无法直接判断的检查项记录为 `insufficient_evidence`，不得编造成已确认缺陷。
12. 检查是否有编造的错误码、状态、提示文案、接口字段、阈值或测试数据；无法溯源时要求改为 `待人工分析确认`。
13. 记录本阶段 project knowledge 应用状态，输出评审结论和逐项修正建议。

| 结构 | 通过/警告/失败 |  |  |

| 预期结果依据 | 通过/警告/失败 |  |  |
| 缺口兜底 | 通过/警告/失败 |  |  |
| 旧字段清理 | 通过/警告/失败 |  |  |

如本阶段绑定了 project knowledge，追加应用记录：

| 来源文件 | 当前阶段 | 应用状态 | 应用位置 | 说明 |
|---|---|---|---|---|

结论必须明确为：

- `通过`：可以进入覆盖审查。
- `需修正`：必须先修正主交付件再进入覆盖审查。

## 约束

- 不新增测试设计项，除非评审任务明确要求直接修复。
- 不编造需求、设计方案或测试分析方案事实。
- 不把过程缺口写回主交付件章节。
- 不用 `待确认`、`TBD`、`见设计方案` 替代 `待人工分析确认`。
- 绑定到本阶段的 project knowledge 必须读取并留痕；如果未应用，必须使用 `not_applicable`、`insufficient_evidence`、`conflict_with_requirement` 或 `deferred_to_review` 解释。
