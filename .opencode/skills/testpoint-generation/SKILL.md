# 测试点生成 Skill

本 skill 在需求结构化、设计方案分析、测试技术路由和专项分析之后使用，负责把内部分析结果整理成场景化测试点。该结果交给 `testcase-title-outline-generation` 继续扩展为 `测试用例标题大纲`。

模板只定义输出结构和占位；场景边界、测试类型、非用例化和方法证据等背景知识由本 skill 按需读取 `knowledge/`，不要把知识文件引用或长篇定义写入主输出模板。

本项目的主交付件是测试用例标题大纲。场景化测试点必须把后续标题项生成需要的需求摘要、范围边界、入口、角色、前置条件、数据因子、业务约束、设计方案约束、接口契约和待确认问题写清楚，不依赖后续阶段回读原始需求或过程产物。

## 输入

- 结构化需求模型。
- 设计方案事实摘要，包括接口、字段、状态、权限、数据依赖、配置开关、异常处理和非功能指标。
- `testing-method-router` 输出的测试技术路由表。
- 分析维度覆盖表。
- `ME-*` 方法分析证据摘要。
- 风险分析结果。
- 边界/等价类、状态、决策表、场景流、权限、接口、数据一致性、组合兼容等分析结果。
- 记忆上下文包中命中的 project/personal 风险画像、覆盖策略、术语映射、模板偏好、个人关注点和 oracle 补充。
- `knowledge/testpoint-standard.md`。
- `knowledge/test-analysis-methodology.md`。
- `knowledge/basic-test-types.md`。
- `knowledge/test-techniques/README.md`。
- `templates/testcase-title-outline-template.md`。
- 如需保留过程审查信息，可同时参考 `templates/final-report-template.md`。

## 生成步骤

1. 先按用户任务、业务流程、系统触发、外部交互或专项质量目标识别 `SC-*` 测试场景；不得先罗列测试点再反向聚类场景。
2. 为每个场景填写 `场景名称`、`场景测试类型` 和 `场景目标`；场景名称应是业务行为，不是方法名或测试点分类。
3. 为每个场景补齐 `场景入口/触发方式`、`执行用户/角色`、`前置条件`、`测试数据因子`、`业务设计约束` 和 `设计方案约束`；这些字段必须能让后续标题项生成理解场景上下文，不能只写“见需求”“见设计方案”“同上”或“按需求实现”。
4. 将内部测试点候选归入最合适的场景，并写成“要验证什么”的无歧义验证目标。
5. 场景测试点使用 `knowledge/basic-test-types.md` 填写 `大类`、`子类` 和 `级别`，不得在主交付件中填写内部 `方法`。
6. 单独识别需要独立验证契约的接口，生成接口测试点；页面观察点或不需独立验证的接口不要强行列入。
7. 接口测试点只描述接口契约、字段、规则、错误码、鉴权、幂等、性能或可靠性目标。
8. 去重并合并过细测试点；如果多个测试点只因具体输入值、按钮或步骤不同而拆分，应上收为规则、条件或风险。
9. 对每个重要分析维度检查是否已落到需求信息、场景、场景测试条件、测试点、接口详情或待确认问题。
10. 对每个 `必选` 测试技术检查是否已落到场景测试点、接口测试点、方法证据或待确认问题。
11. 刷新待确认信息，移除已被需求依据、上下文包、场景条件、接口补充说明或测试点风险备注覆盖的问题。
12. 检查主输出自包含性：如果某条测试点或后续标题项需要依赖原始需求、设计方案、过程报告或 memory 才能理解，应把必要背景上收进场景测试条件、接口补充说明、风险备注或待确认信息。
13. 如果使用了 project/personal 补充，必须把后续标题项生成需要知道的业务上下文、风险原因、个人关注点或判定依据写入主交付件；不得要求后续项目回读 `*/projects/<project-key>/` 或 `*/user/`。
14. 填写完整性自检，逐项说明是否满足，不保留空说明。

## 标准来源

- 内部分析的 `类型`、`方法/测试技术`、`级别`、粒度和非用例化约束以 `knowledge/testpoint-standard.md` 为准。
- 测试分析、标题级设计边界、场景层级、分析维度和主交付件落点以 `knowledge/test-analysis-methodology.md` 为准。
- 标题大纲中的 `场景测试类型`、测试点 `大类/子类` 和接口测试类型以 `knowledge/basic-test-types.md` 为准。
- 判定关注与 Oracle 启发以 `knowledge/test-techniques/README.md` 为准。
- project/personal 补充以当前 run 的 `process/context-pack.md` 为准，只能补充风险画像、覆盖策略、术语映射、模板偏好、个人关注点和 oracle，不改变上述核心标准来源；personal 不得作为项目事实。

## 合并规则

- 多个专项测试技术产出的候选指向同一被测对象、同一场景和同一验证特性时，合并为一个测试点。
- 合并后在过程报告中 `方法` 填写最能解释该测试点来源的主要测试技术；主交付件中不输出 `方法`，其他支撑技术保留在方法证据摘要中。
- 同一业务对象在不同风险维度下需要分别验证时，不强行合并。
- 风险确认点可以生成测试点，但 `风险/备注` 或 `待确认信息` 必须说明依据不足。
- 不把候选表中的临时列带入最终标题大纲。

## 输出契约

场景化测试点作为中间结构进入 `${PROJECT_ROOT}/outputs/runs/<run-id>/deliverables/testcase-title-outline.md`，由 `testcase-title-outline-generation` 在同一主交付件中扩展为测试用例标题项。

- `## 1. 需求与设计方案信息`
- `## 2. 测试场景清单`
- `## 3. 测试场景详情`
- `## 4. 接口测试标题大纲`
- `## 5. 待确认信息`
- `## 6. 完整性自检`

场景测试点表必须使用以下列：

| 测试点 ID | 测试点 | 大类 | 子类 | 级别 | 风险/备注 |
|---|---|---|---|---|---|

接口测试点表必须使用以下列：

| 测试点 ID | 测试点 | 大类 | 子类 | 风险/备注 |
|---|---|---|---|---|

过程报告如包含扁平测试点明细，必须复用同一批场景测试点和接口测试点，不得与主交付件冲突。

## 约束

- 不写操作步骤、具体测试数据或完整预期结果。
- 场景测试条件中可以使用 `前置条件` 和 `测试数据因子`，但不得展开成可执行用例数据。
- 不使用 `操作步骤`、`测试数据`、`预期结果` 作为列名。
- 不把边界值、等价类、判定表、组合矩阵、状态迁移矩阵等测试技术名称或方法产物写入主交付件测试点；这些只保留在过程分析证据中。
- 每条测试点是对验证特性的细化，必须明确被测对象、特定场景和某一功能/规则/行为。
- 每个 `必选` 测试技术必须产出至少一个测试点或一个待确认问题。
- 每个测试点应能在过程报告中追溯到一个需求依据和一个方法证据；不在主交付件的测试点表中新增证据列。
- 缺少判定依据时，不隐藏问题，标记为“待确认”。
- 不把关键业务规则、状态集合、角色权限、接口字段、错误码、性能指标或可靠性注入条件只写在过程报告中；后续标题项生成、评审或细化需要知道的内容必须进入主交付件。
- 本阶段不触发交互；如发现缺口，写入待确认问题或风险确认点。
- 不为了凑数量拆出只有输入值、按钮或页面元素不同的测试点。
- 不使用 `正常`、`异常`、`校验通过` 这类无法单独表达验证特性的描述作为测试点主体。
- 如果 context pack 中的 project/personal 补充不足，只能按 context pack 记录的来源或当前需求明确指向的文件补读相关章节，并在过程报告或风险备注中记录来源；不得全目录搜索或全量复制大文件。
