# 测试分析方案生成

本 skill 负责从 `testpoint-generation` 产出的测试场景、场景测试条件、场景测试点和接口契约分析候选生成 `测试分析方案`。它使用本仓库内置的 `knowledge/test-techniques/` 测试技术库识别需要覆盖的规则分支、路径分支、状态分支、权限分支、接口契约分支和风险分支，但不输出具体代表性条件、数据、状态组合或 `TDI-*`。

## 路径解析规则

- 本 skill 中所有 `knowledge/...`、`templates/...`、`quality-gates/...` 路径均为仓库根目录相对路径。
- 读取测试技术时，先读取 `knowledge/test-techniques/README.md`，再按 README 路由读取同目录下的具体技术文件。
- 粒度边界读取 `knowledge/test-analysis-methodology.md` 和 `knowledge/test-analysis-solution-standard.md`。
- 输出结构读取 `templates/test-analysis-solution-template.md`。

## 职责边界

- 输出“这个测试点下有哪些可评审的分析分支”，不输出“每个分支用什么代表性数据去测”。
- 为每个测试点明细补充 `预期结果`。
- 保留测试场景、测试点、测试点明细的层级关系；仅当 `TP-*-*` 是非成功测试点明细时新增第四层失败类型明细。
- 不生成 `TDI-*` 测试设计项。
- 不生成前置步骤、测试步骤、自动化脚本或执行数据清单。
- 不在主交付件输出 `覆盖意图`、`级别`、`判定关注`、`待确认信息` 或 `输入条件与数据依赖`。

## 输入

- 测试场景清单、场景测试条件、场景测试点和接口契约分析候选。
- 结构化需求模型。
- 设计方案事实摘要，尤其是接口、字段、状态、权限、数据依赖、配置开关、异常处理和非功能指标。
- `context-pack.md` 中与本次相关的项目事实、历史缺陷和输出偏好。
- `process/context-pack.md` 中绑定到 `test-analysis-solution-generation` 的 project knowledge 文件，例如测试设计因子库、测试设计模式库、Oracle 或覆盖策略。
- `ME-*` 方法分析证据摘要。
- `process/clarification-session.md` 中已收口的过程缺口候选。

## 生成步骤

1. 读取 context pack 的“项目知识阶段绑定”。如果存在绑定到 `test-analysis-solution-generation` 的 project knowledge，先按来源文件、相关章节、关键词或标题读取，不全量复制大文件。
2. 按 `knowledge/test-analysis-methodology.md` 检查输入是否满足 `测试场景 -> 测试点` 的层级关系；如果测试点已写成完整用例，先上收为验证目标。
3. 按 `knowledge/test-analysis-solution-standard.md` 确认测试点明细粒度：测试点明细应是分析层分支，不是测试设计项、用例标题、测试步骤或数据清单。
4. 对每条测试点识别主要信号：流程、边界、枚举、字段格式、字段长度、组合、判定、周期、状态、权限、接口、历史缺陷、风险或质量属性。
5. 按 `knowledge/test-techniques/README.md` 选择适用测试技术。测试技术用于识别应覆盖的分支，不作为主交付件字段输出。
6. 结合绑定的测试设计因子、业务测试设计模式或 Oracle，提取对当前测试点有用的规则分支、路径分支、状态分支、权限分支、接口契约分支、风险分支和预期结果依据；不得因为项目知识存在就编造需求或设计方案未说明的业务事实。
7. 基于场景测试条件、需求事实和设计方案事实，生成 1-N 个测试点明细：
   - 每个测试场景必须包含一个 `E2E场景测试` 测试点，并至少生成一个端到端主流程成功闭环测试点明细。
   - 主路径或核心成功分支至少 1 个测试点明细。
   - 明确边界、枚举、状态、权限、接口错误码、组合或异常处理时，先抽象成分析分支。
   - 同一测试点下仅具体取值不同但业务判定一致的内容，不在本阶段拆成多条具体数据明细。
   - 当不同分支对应不同业务判定、状态变化、权限结果、接口契约或风险后果时，应拆成不同测试点明细。
8. 当某个 `TP-*-*` 测试点明细属于非成功分支时，必须在其下新增 `TP-*-*-*` 第四层失败类型明细：
   - 父级 `TP-*-*` 表达非成功分支，例如“不满足长度要求”“权限拒绝”“非法状态下不允许取消”。
   - 第四层按失败类型继续拆分，例如长度过短、长度过长、缺少必填字段、状态不允许、权限不足、外部依赖返回异常、接口超时、重复请求导致幂等处理。
   - 只有第四层叶子节点承载 `- 测试点详情：` 和 `- 预期结果：`；父级非成功测试点明细作为分组，不写测试设计项。
   - 成功路径或普通规则分支不新增第四层。
9. 测试点明细命名使用分析化表达，优先写成“<对象/字段/状态> 满足/不满足 <规则>”或“<角色/状态/配置> 下 <业务动作> 被允许/被拒绝”，例如：
   - 下发订单 ID 满足长度要求。
   - 下发订单 ID 不满足长度要求。
   - 已支付订单重复提交取消请求。
   - 普通用户访问管理员专属配置入口。
10. `预期结果` 的生成规则：
   - 如果需求或设计方案明确了成功、失败、拦截、状态变化、错误提示、错误码、返回内容、记录变化或消息发送结果，写成简短预期结果。
   - 如果只能判断“应该有结果”但不知道具体错误提示、状态变化、错误码或数据记录，写 `待人工分析确认`。
   - 不得为了让预期结果看起来完整而编造错误码、提示文案、状态枚举、接口响应结构或数据库字段。
11. 去重：如果两个叶子节点的验证分支和预期结果相同，只保留一个；如果只是措辞不同，不得重复输出。
12. 记录本阶段 project knowledge 应用状态。
13. 按 `templates/test-analysis-solution-template.md` 写入主交付件，保持 `测试场景 -> 测试点 -> 测试点明细` 层级；非成功测试点明细按 `测试场景 -> 测试点 -> 测试点明细 -> 失败类型明细` 输出。

## 输出格式

每个场景下使用以下结构。`E2E场景测试` 固定作为场景主流程测试点；普通/成功测试点明细和非成功测试点明细可以属于同一个业务测试点主题：

```markdown
#### TP-001 E2E场景测试

##### TP-001-001 <端到端主流程测试点明细>

- 测试点详情：<说明该场景端到端业务主流程需要验证什么。>

- 预期结果：<业务主流程按预期完整闭环或待人工分析确认>

#### TP-002 <测试点>

##### TP-002-001 <普通/成功测试点明细>

- 测试点详情：<说明该规则分支、路径分支、状态分支或风险分支需要验证什么。>

- 预期结果：<明确预期结果或待人工分析确认>

##### TP-002-002 <非成功测试点明细>

###### TP-002-002-001 <失败类型明细>

- 测试点详情：<说明该失败类型需要验证什么。>

- 预期结果：<明确预期结果或待人工分析确认>
```

接口、消息、定时任务或批处理内容如果最终形成测试点，仍使用 `TP-*` 测试点编号；测试点明细使用所属测试点前缀编号，不另起 `ITP-*` 或 `ITDI-*`。主交付件只使用中文术语和缩写，不展开英文全名。

如本阶段绑定了 project knowledge，过程报告追加应用记录：

## 与 test-design-agent 的边界

- 当前 skill 可以识别“满足长度要求”和“不满足长度要求”。
- 当“不满足长度要求”属于非成功测试点明细时，当前 skill 可以继续拆出“长度短于规则要求”“长度长于规则要求”等失败类型明细。
- 当前 skill 不输出“长度等于 13 位”“长度小于 13 位 1 位”“长度大于 13 位 1 位”等代表性设计条件。
- `test-design-agent` 可以在评审后的测试分析方案上，为每个普通 `TP-*-*` 或失败类型 `TP-*-*-*` 补充 `TDI-*` 和代表性条件、数据、状态或组合。

## 高标准示例来源

详细测试技术示例由 `knowledge/test-techniques/**/*.md` 维护。当前 skill 只复用其中的分析思想和分支识别方法，不照搬其中的 `TDI-*` 设计项示例到主交付件。

## 约束

- 不输出 `前置步骤`、`测试步骤`、`操作步骤`、`执行数据`、`自动化脚本` 等字段。
- 不输出旧版主交付件字段；字段禁用清单以 `bin/lint-test-analysis-solution.py` 为准。
- 主交付件不使用 Markdown 加粗语法，例如 `**文本**` 或 `__文本__`。
- 不输出 `TDI-*`、`测试设计项` 或测试设计项表格。
- 不把“正向/异常”作为测试点明细正文；必须写清楚规则分支或行为分支。
- 不为了凑数量生成重复测试点明细。
- 不强制每个具体输入值都生成独立测试点明细；具体取值留给 `test-design-agent`。
- 如果覆盖补全依赖的枚举值、容量阈值、兼容范围、目标语言、性能指标、错误码、错误提示或异常处理规则缺失，预期结果写 `待人工分析确认`，不编造具体取值。
- 绑定到本阶段的 project knowledge 必须读取并留痕；如果未应用，必须使用 `not_applicable`、`insufficient_evidence`、`conflict_with_requirement` 或 `deferred_to_review` 解释。
