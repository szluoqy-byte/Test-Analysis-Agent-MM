# 待确认问题治理 Skill

本 skill 用于决定“哪些信息缺口需要进入最终交付文件”。各阶段可以产出待确认候选问题，主流程统一去重、分级、排序和降级后，不触发中途交互，最终只把会影响后续标题项评审、细化或落地的问题写入 `deliverables/testcase-title-outline.md` 的 `## 5. 待确认信息`。

## 输入

- 当前检查点名称。
- 当前阶段产物，例如记忆上下文包、结构化需求模型、方法路由表、方法证据、标题大纲草稿或覆盖审查结果。
- 已累计的待确认候选问题。
- `${PROJECT_ROOT}/outputs/runs/<run-id>/process/context-pack.md`。
- `templates/clarification-template.md`。
- `templates/testcase-title-outline-template.md` 中的 `## 5. 待确认信息`。

## 检查点

主流程只在以下三个固定检查点调用本 skill。所有检查点都只做候选治理，不向用户提问。

| 检查点 | 位置 | 典型候选问题 | 默认处理 |
|---|---|---|---|
| `CP-INPUT` | `memory-context-builder`、`requirement-testability` 和 `design-solution-extraction` 后 | 业务域命中冲突、memory 与需求冲突、需求与设计冲突、业务规则/状态/权限/边界/接口契约/字段/数据依赖缺失 | 影响需求理解、设计事实或测试点正确性时进入候选队列 |
| `CP-ANALYSIS` | `testing-method-router` 和专项方法分析后 | 方法必要性范围、性能/安全/兼容是否展开、决策表条件、状态终态、幂等补偿、权限矩阵缺口 | 影响方法覆盖、风险级别或标题项生成时进入最终待确认 |
| `CP-REVIEW` | `coverage-review` 后 | 核心需求缺失、覆盖无法关闭、报告可用性风险 | 作为最终待确认收口 |

## 候选问题来源

各阶段只产出待确认候选，不直接调用用户交互能力：

| 来源阶段 | 允许产出候选 | 不允许做什么 |
|---|---|---|
| `memory-context-builder` | memory 冲突、业务域归属不清 | 不要求用户选择所有可能业务域 |
| `requirement-testability` | 影响需求模型的关键缺口 | 不为每个模糊词都生成问题 |
| `testing-method-router` | 影响方法必要性的范围问题 | 不为了可选方法制造待确认项 |
| 专项方法 skill | 影响决策表、状态图、权限矩阵、接口契约的关键缺口 | 不追问可作为风险备注处理的细枝末节 |
| `testpoint-generation` | 影响测试点粒度或是否保留风险确认点的问题 | 不打断生成流程 |
| `testcase-title-outline-generation` | 影响标题项、输入条件与数据依赖或判定关注的问题 | 不打断生成流程 |
| `coverage-review` | 阻断质量门禁关闭的需求缺失 | 不因普通覆盖建议制造阻断项 |

## 候选问题字段

每个候选问题应包含：

| 字段 | 说明 |
|---|---|
| 问题ID | 使用 `CQ-001` 递增 |
| checkpoint | 检查点，例如 `CP-INPUT` |
| sourceStage | 来源阶段或 skill |
| header | 12 个字以内，用于归类问题 |
| question | 面向后续设计人员的清晰问题 |
| why | 为什么必须确认 |
| impact | 不确认会影响什么 |
| options | 2 到 4 个可能处理方向，可为空但不得编造成已确认规则 |
| blockingLevel | `Blocking`、`Important` 或 `Optional` |
| priority | `P0`、`P1`、`P2` 或 `P3` |
| askPolicy | 统一写为 `DoNotAsk` |
| mustAsk | 统一写为 `否` |
| relatedRequirement | 关联需求依据 |
| memoryConflict | 如有冲突，说明冲突的 memory 来源 |

统一候选表头如下，所有阶段必须按此 schema 输出 `CQ-*` 候选：

| 问题ID | checkpoint | sourceStage | header | question | why | impact | options | blockingLevel | priority | askPolicy | mustAsk | relatedRequirement | memoryConflict |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

字段填写规则：

- `question` 必须能被后续设计或需求确认人员直接理解，避免把多个互斥问题揉在一句话里。
- `why` 说明当前信息缺口，不复述问题本身。
- `impact` 必须落到测试点正确性、覆盖范围、风险级别、方法选择或交付可用性之一。
- `options` 只表达可能方向，不得把某个选项写成已确认结论。
- `relatedRequirement` 优先写需求标题、规则句、表格行或段落摘要。
- 同一候选不能同时表达两个独立业务决策；需要拆分时拆成两个候选，再由本 skill 排序。

## 优先级规则

| 优先级 | 说明 | 默认处理 |
|---|---|---|
| `P0` | 不确认会导致核心业务规则、状态、权限、接口契约或高风险测试点错误 | 必须进入最终待确认信息 |
| `P1` | 不确认会明显影响覆盖范围、风险级别、方法选择或报告可用性 | 默认进入最终待确认信息 |
| `P2` | 不确认仍可继续，但会留下普通待确认风险 | 视影响范围进入最终待确认或风险备注 |
| `P3` | 只影响措辞、偏好或低风险补充 | 通常不进主输出，可写入过程记录 |

## 分级规则

以下情况优先标记为 `Blocking`：

- 多条件业务规则缺失，例如优惠叠加、审批优先级、互斥分支或规则优先级。
- 状态迁移不完整，例如终态是否可回退、取消后是否释放资源、失败后是否补偿。
- 权限边界不清，例如角色、租户、归属、数据范围或审批权限不同。
- 金额、数量、时间、次数、配额、阈值等边界缺失。
- 接口失败、超时、重试、幂等、回调或错误码规则缺失。
- 当前需求与 `${PROJECT_ROOT}/outputs/runs/<run-id>/process/context-pack.md` 中已确认事实冲突。
- 需求只出现“合理、快速、稳定、优化”等不可验证表达，且影响核心验收。

以下情况标记为 `Important`：

- 影响覆盖完整性，但可先作为待确认风险点继续。
- 影响可选方法是否展开，例如性能容量、安全风控、兼容性范围。
- 影响风险级别但不改变主业务规则。
- 影响报告是否可直接用于评审或发布。

以下情况标记为 `Optional`：

- 只影响措辞、报告组织或补充说明的问题。
- 不影响核心测试点生成的非关键边界。

## 去重、排序和收口

每次调用本 skill 时必须先处理候选队列：

1. 合并同一业务对象、同一规则或同一状态缺口的问题。
2. 删除已被当前需求、memory、上下文包或已有场景条件明确覆盖的问题。
3. 按 `priority`、`blockingLevel`、影响范围和需求依据清晰度排序。
4. 将 `P0/P1` 且仍未解决的问题标记为最终待确认候选。
5. 将 `P2` 问题按影响范围决定进入最终待确认信息或降级为测试点 `风险/备注`。
6. 将 `P3` 问题默认排除在主交付件之外，除非它会影响后续标题项评审、细化或落地。
7. 全流程不调用用户交互能力，不暂停主流程，不向用户发起中途确认。

排序时优先级相同的问题按以下顺序比较：

1. 影响核心业务规则、状态迁移、权限边界、接口契约或资损风险的问题优先。
2. 会改变测试方法选择的问题优先于只影响描述完整性的问题。
3. 有明确需求依据的问题优先于泛化风险问题。
4. 能一次确认后解除多个候选的问题优先。
5. 已有保守处理方案的问题可以后置为普通待确认风险。

## 最终待确认信息刷新规则

在输出 `deliverables/testcase-title-outline.md` 前，必须刷新标题大纲的 `## 5. 待确认信息`：

1. 只保留后续标题项评审、细化或落地时必须知道的问题。
2. 删除已被需求原文、设计方案、上下文包、场景测试条件、接口补充说明、测试点风险备注或标题项字段覆盖的问题。
3. 删除重复问题和只影响措辞、报告组织、偏好补充的问题。
4. `P0/P1` 未解决问题必须保留，并说明影响场景、接口或测试点。
5. 缺少明确业务规则但仍可继续分析的问题，当前处理写为“按待确认风险处理，后续设计前需确认”。
6. 没有待确认问题时，写“本次无待确认信息。”，不要保留空问题行。

最终主交付件中的待确认信息表使用以下结构：

| 问题 ID | 问题 | 影响场景/测试点/标题项 | 当前处理 |
|---|---|---|---|

`问题 ID` 使用 `Q-001` 连续编号，可以在过程记录中保留与 `CQ-*` 的映射。

## 过程记录

如存在候选问题，创建或更新 `${PROJECT_ROOT}/outputs/runs/<run-id>/process/clarification-session.md`，记录：

- 当前检查点。
- 候选问题队列。
- 去重和排序结果。
- 未进入最终待确认信息的原因。
- 刷新后的最终待确认问题。
- 是否建议沉淀到长期 memory。

该文件是运行产物，不是长期 memory，也不是后续标题项评审、细化或落地的必读文件。后续标题项评审、细化或落地只依赖 `deliverables/testcase-title-outline.md` 中的 `## 5. 待确认信息`。

## 输出

每次调用本 skill 必须输出：

- 候选问题去重结果。
- 进入最终待确认信息的 `Q-*` 问题列表。
- 降级为风险备注或过程记录的问题列表。
- 被移除的问题和移除原因。
- 是否需要刷新 `deliverables/testcase-title-outline.md` 的 `## 5. 待确认信息`。

## 失败与降级处理

- 如果候选问题缺少必要字段，先补齐字段；无法补齐时降级为待确认问题，不触发交互。
- 如果多个候选都很重要，全部进入最终待确认信息，不因数量限制丢弃高风险问题。
- 如果候选问题与需求文档冲突，以需求文档为准，同时把冲突写入待确认信息或过程记录。
- 如果候选问题只来自推测且无需求依据，不写成已确认规则；高风险时保留为待确认风险，低风险时移入过程记录。

## 约束

- 不生成测试点。
- 不生成测试用例或操作步骤。
- 不调用用户交互能力。
- 不在分析过程中向用户提问或暂停主流程。
- 不把任何候选问题伪装成用户已确认事实。
- 不把待确认问题只留在过程报告中；后续标题项评审、细化或落地必须知道的问题必须进入主交付件。
- 不把用户本次后续反馈自动写入 `memory/project-memory.md`、`memory/domains/*.md` 或 `memory/testing-experience-memory.md`。
