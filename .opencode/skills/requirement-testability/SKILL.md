# 需求可测性分析 Skill

本 skill 在生成测试点之前使用，目标是把自然语言需求转成可分析、可追踪的需求模型。

## 输入

- 原始 Markdown 需求文档。
- 记忆上下文包。
- 记忆上下文包中命中的 project/personal knowledge 补充。
- `knowledge/domain-glossary.md`。
- `knowledge/test-analysis-methodology.md`。

## 分析步骤

1. 识别需求模块和分析边界。
2. 提取参与角色、操作、业务对象、输入、输出、状态、规则、约束、异常和外部依赖。
3. 将每个需求片段标记为：可测试、部分可测试、不可测试。
4. 把模糊、缺失、冲突和不可验证表达转成“待确认问题”。
5. 保留需求依据，引用标题、表格行或段落摘要。
6. 按 `knowledge/test-analysis-methodology.md` 标记测试分析维度，例如需求可测性、风险、业务场景、数据域、规则组合、状态、权限、接口、数据一致性、组合兼容、非功能质量属性和经验缺陷模式。
7. 结合 context pack 中的 project/personal knowledge 补充识别项目特有风险、个人关注点、覆盖策略或术语映射，但不得覆盖需求文档中的明确规则；personal 不得作为项目事实或团队共识。
8. 提取测试方法触发信号，例如范围、状态、多条件规则、权限、接口、数据变化、兼容配置。
9. 将会影响测试点正确性的问题登记为待确认候选，交给 `clarification-gate` 排序和收口。

## 可测性判断

- 可测试：有可观察行为、业务规则、状态变化、校验结果、接口响应、权限差异或数据影响。
- 部分可测试：目标明确，但缺少条件、阈值、角色、结果、异常或边界。
- 不可测试：只有“好用”“快速”“稳定”“合理”等主观表达，缺少可验证标准。

## 输出

使用 `templates/requirement-model-template.md`。

结构化需求模型至少包含：

| 字段 | 说明 |
|---|---|
| 需求片段ID | 使用 `REQ-001` 递增 |
| 模块/对象 | 需求归属的功能模块、业务对象或接口 |
| 需求依据 | 标题、规则句、表格行或段落摘要 |
| 可验证行为 | 可以被观察或判定的行为、规则、状态或数据影响 |
| 分析维度 | 来自 `knowledge/test-analysis-methodology.md` 的分析维度 |
| 触发信号 | 边界、状态、决策表、权限、接口、数据一致性、组合兼容等 |
| 可测性 | 可测试、部分可测试或不可测试 |
| 缺失信息 | 影响测试分析的信息缺口 |
| 待确认候选 | 需要交给 `clarification-gate` 的候选问题 |

待确认候选只记录会影响需求模型或测试结论的问题。例如规则优先级、状态终态、角色边界、阈值、异常处理、接口契约、数据同步时机。不为单纯措辞、命名或低风险补充打断主流程。

## 约束

- 不从常识补业务规则。
- 不生成测试点、测试用例或操作步骤。
- 无法确认时，生成简洁的待确认问题。
- 不直接向用户提问。
- 不把通用测试理论写进需求模型；只记录当前需求的事实、缺口和触发信号。
- 如果 context pack 中的 project/personal 信息不足，只能按 context pack 记录的来源或当前需求明确指向的文件补读相关章节，并在需求模型或待确认候选中记录来源；不得全目录搜索或全量复制大文件。
