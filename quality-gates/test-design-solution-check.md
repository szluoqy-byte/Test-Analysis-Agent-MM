# 测试设计方案检查

用于检查 `deliverables/test-design-solution.md` 是否停留在测试设计方案粒度，并且能支撑后续完整测试用例写作。

## 必须满足

- 普通分支按 `测试场景 -> 测试点 -> 测试点明细 -> 测试设计项` 组织；非成功分支按 `测试场景 -> 测试点 -> 测试点明细 -> 失败类型明细 -> 测试设计项` 组织。
- 主输出包含 `## 1. 设计输入` 和 `## 2. 测试场景与测试设计`。
- 每个普通测试点明细至少包含 1 个测试设计项；每个失败类型明细至少包含 1 个测试设计项。
- 如果分析方案中存在 `TP-*-*-*` 失败类型明细，设计方案必须完整继承，不得合并回父级 `TP-*-*`。
- 测试设计项 ID 使用 `TDI-001` 起全局连续编号。
- 主交付件只使用中文术语和缩写 `SC`、`TP`、`TP-*-*`、`TP-*-*-*`、`TDI`，不得展开英文全名或使用其他编号体系。
- 测试设计项表包含固定列：`测试设计项 ID | 条件/数据/状态/组合 | 预期结果`。
- 测试设计项表达代表性条件、数据、状态或组合。
- 预期结果为空时不允许通过。
- 当需求和设计方案没有明确错误提示、状态变化、错误码、返回内容或记录变化时，预期结果必须写 `待人工分析确认`。
- 主输出不设置 `未明确规则` 章节。
- 主输出不设置独立待确认信息清单。

## 禁止出现

- 旧版主交付件字段；字段禁用清单以 `bin/lint-test-design-solution.py` 为准。
- 完整测试用例字段：`前置步骤`、`测试步骤`、`操作步骤`、`执行数据`、`自动化脚本`。
- 编造的错误码、错误提示、状态枚举、接口字段或数据库字段。
- `见需求`、`见设计方案`、`按需求`、`同上`、`TBD` 等非自包含占位。

## 常见失败

- 把测试设计项写成“验证功能正常”“异常场景覆盖”。
- 把 `TDI-*` 挂在测试点层、场景层或非成功父级测试点明细下，而不是具体叶子分析节点下。
- 分析方案中已有失败类型明细，设计方案却删除、合并或改写。
- 把多个互相独立的状态、权限或接口契约塞进一条测试设计项。
- 需求没有说明错误码，却写出具体错误码。
- 需求没有说明状态变化，却写出具体终态。
- 为缺口单独新增 `## 3. 未明确规则` 或待确认章节，而不是在对应设计项的预期结果写 `待人工分析确认`。
