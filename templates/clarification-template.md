# 待确认问题治理模板

本模板用于记录各阶段产生的待确认候选，并将最终仍会影响后续标题项评审、细化或落地的问题统一整理到主交付件 `deliverables/testcase-title-outline.md` 的 `## 5. 待确认信息`。

## 候选问题队列

各阶段先产出候选问题，不直接触发交互，不在分析过程中打断用户。

```markdown
| 问题ID | checkpoint | sourceStage | header | question | why | impact | options | blockingLevel | priority | askPolicy | mustAsk | relatedRequirement | memoryConflict |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
```

`问题ID` 使用 `CQ-001` 递增；`askPolicy` 统一填写 `DoNotAsk`；`mustAsk` 统一填写 `否`。无 memory 冲突时 `memoryConflict` 填写 `无`。

## 治理规则

- `P0/P1` 且仍未解决的问题必须进入最终待确认信息。
- `P2` 问题按影响范围进入最终待确认信息或降级为测试点 `风险/备注`。
- `P3` 问题默认只保留在过程记录，除非它会影响后续用例设计。
- 已被需求原文、上下文包、场景测试条件、接口补充说明或测试点风险备注覆盖的问题应移除。
- 重复问题必须合并，同一业务对象、同一规则或同一状态缺口只保留一个最清晰的问题。
- 不把候选问题写成已确认业务规则；缺少依据时必须明确“待确认”。

## 主交付件展示格式

主交付件 `## 6. 待确认信息` 使用以下结构：

```markdown
| 问题 ID | 问题 | 影响场景/测试点 | 当前处理 |
|---|---|---|---|
| Q-001 | <需要确认的问题> | <影响场景/测试点> | 按待确认风险处理，后续设计前需确认 |
```

没有待确认问题时写：

```markdown
本次无待确认信息。
```

## 问题设计要求

- 问题必须说明会影响哪些测试分析结论、场景、接口或测试点。
- 问题必须面向后续需求确认或用例设计人员可读，不依赖过程报告才能理解。
- `当前处理` 必须说明本次分析如何保守推进，例如“按待确认风险处理，后续设计前需确认”。
- 用户后续反馈不自动写入长期 memory；只有用户明确确认沉淀时，才更新 memory 源文件。
- 主交付件的“待确认信息”只保留刷新后的未解决问题，不保留已被需求或当前输出覆盖的问题。
