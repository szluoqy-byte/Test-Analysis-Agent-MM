## 生成规则

- 主输出路径固定为：`${PROJECT_ROOT}/outputs/runs/<run-id>/deliverables/test-analysis-solution.md`。
- 如保留过程分析报告，路径固定为 `${PROJECT_ROOT}/outputs/runs/<run-id>/reports/test-analysis-report.md`。
- 运行任务清单、上下文和澄清记录分别写入 `process/task-list.md`、`process/context-pack.md` 和 `process/clarification-session.md`。
- 主交付件固定使用中文术语和缩写：测试场景 `SC-*`、测试点 `TP-*`、测试点明细 `TP-*-*`，不展开英文全名。
- 测试场景 ID 使用 `SC-001` 起连续编号。
- 测试点 ID 使用 `TP-001` 起连续编号；接口、消息、定时任务或批处理测试点也统一使用 `TP-*`。
- 测试点明细 ID 使用所属测试点作为前缀，例如 `TP-001-001`、`TP-001-002`。
- 每个测试场景下必须包含一个 `E2E场景测试` 测试点，用于覆盖该场景端到端业务主流程是否按预期完整闭环。
- 主输出默认按 `测试场景 -> 测试点 -> 测试点明细` 组织；当 `TP-*-*` 测试点明细是非成功分支时，必须新增 `TP-*-*-*` 第四层承载失败类型明细。
- 测试点明细必须使用三级标题，不使用表格承载；失败类型明细使用四级标题，不使用表格承载。
- 测试点明细只表达分析层的规则分支、路径分支、状态分支、权限分支、接口契约分支或风险分支；不要展开具体代表性条件、数据、状态组合或边界取值。
- 非成功测试点明细下的第四层用于继续拆分失败类型，按需覆盖业务逻辑、系统交互、外部依赖、异常返回、数据校验、权限控制、状态限制、接口契约和数据一致性等失败来源。
- 只有非成功测试点明细才新增第四层；成功路径或普通规则分支仍停留在 `TP-*-*`。
- `预期结果` 只能写需求或设计方案明确支持的结果；如果需求和设计方案没有明确错误提示、状态变化、错误码、返回内容或记录变化，写 `待人工分析确认`。
- 主输出不设置 `未明确规则` 章节，也不设置独立待确认信息清单。
- 主输出不得出现 `TDI-*`、`测试设计项`、`测试设计项 ID` 或测试设计项表格；这些留给 `@test-design-agent`。
- 不要把内部测试技术路由、方法证据、专家评分、quality gate 结果或 memory 更新建议写入主输出。
